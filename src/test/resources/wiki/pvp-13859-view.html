DiagnosticTool.exe

修正方案：一次性系统诊断小工具

设计原则

原则说明
一次性运行双击运行 → 采集 → 出报告 → 退出，不驻留后台
聚焦阻断事件蓝屏、崩溃、死机、严重网络丢包、启动失败
不诊断性能不采集 GPU 负载曲线、温度曲线、FPS 时序
轻量单个 exe < 5MB，无依赖，采集时间 < 2 分钟

场景 A：蓝屏/死机

采集项来源诊断价值

WER 报告C:\ProgramData\Microsoft\Windows\WER\ReportArchive\Windows 错误报告详情

采集完 Minidump 后，工具可对 .dmp 文件做轻量级自动解析：

解析流程（无需完整 WinDbg，只需提取关键信息）:

├─ tcpip.sys → "网卡驱动问题"
├─ ntfs.sys / storport.sys → "硬盘/控制器故障"
├─ easyanticheat.sys / vgk.sys → "反作弊驱动冲突"
└─ dxgkrnl.sys → "DirectX / 显卡驱动问题"

三、核心采集实现

3.1 Crash/Dump 采集器

优先级最高，最先采集（保证数据不被后续操作污染）

采集步骤:
1. 扫描 C:\Windows\Minidump\*.dmp
- 按时间倒序，提取最近 10 个
- 对每个 .dmp: 解析 TIME_STAMP + BugCheckCode + 故障模块
方式: DbgHelp.dll 的 MiniDumpReadDumpStream() API
(不依赖 WinDbg，Windows 自带 DbgHelp.dll)

2. 扫描 C:\Windows\LiveKernelReports*.dmp (Watchdog Dump)
- 用于分析系统卡死/无响应 (非蓝屏死机)

3. 读取 System Event Log:
- BugCheck (EventID 1001): 蓝屏事件
- Kernel-Power (EventID 41): 意外关机/死机
- Disk (EventID 7/11/51): 磁盘错误
每个日志类型只需最近 20 条

4. 读取 Application Event Log:
- Application Error (EventID 1000): 进程崩溃
- WER (EventID 1001): Windows 错误报告
过滤进程名包含游戏进程名的记录

5. (可选) 扫描游戏目录下的 crash/error/log 文件夹
- 用户选择游戏安装路径，工具在常见路径下搜索 *.log, crash_*.txt 等

轻量级 Minidump 解析的关键代码逻辑：

调用 Windows DbgHelp API:
MiniDumpReadDumpStream() 读取以下 Stream:
- SystemInfoStream → 提取处理器架构、OS 版本
- ModuleListStream → 提取所有已加载驱动列表
- ExceptionStream → 提取异常代码、异常地址、错误模块
→ 横向对比 Module 版本，找到异常的模块

3.2 Network 采集器

采集步骤 (使用 .NET Framework 内置 API，零依赖):

1. 读取预置的游戏服务器 IP/域名列表
(工具内置，不需要联网获取)

2. 对每个目标服务器:
a. DNS 解析测试:
- Resolve-DnsName 计时 (< 100ms = 正常)
b. 连通性测试:
- TCP 尝试连接游戏端口 (TCP Socket.Connect, 超时 5s)
- 记录成功/失败，连接耗时
c. 延迟测试:
- Ping 50 次，间隔 200ms
- 统计: min/avg/max/p95 延迟, 丢包率, 抖动
d. 路由追踪 (轻量版):
- Ping TTL 从 1 递增到 30
- 记录每一跳的 IP 和延迟
- 识别丢包节点: 如果第 N 跳之后全部超时

3. 本地网络环境:
- ipconfig /all 解析为结构化数据
- 网关可达性 (ping 网关)
- DNS 服务器可达性
- 检查 Windows 防火墙出站规则是否阻止游戏端口
- 读取 hosts 文件，检查是否有被劫持的游戏域名

4. 网卡驱动信息:
- 网卡型号、驱动版本、驱动日期
- 是否有禁用/未连接的适配器

3.3 System Snapshot 采集器

采集步骤:

1. 硬件清单 (WMI 查询，一次性完成):
- Win32_Processor → CPU 型号 + 核心数
- Win32_PhysicalMemory → 内存条数 + 容量 + 频率
- Win32_VideoController → 显卡 + 驱动版本 + 日期
- Win32_DiskDrive → 磁盘型号 + 类型 (SSD/HDD)
- Win32_LogicalDisk → 各分区剩余空间
- Win32_BaseBoard → 主板型号
- Win32_ComputerSystem → 系统制造商/型号 (笔记本型号)

2. 系统环境:
- OS 版本 + Build 号 (通过 GetVersionEx + 注册表)
- 电源方案 (powercfg /getactivescheme)
- 页面文件配置 (Win32_PageFileUsage)
- 虚拟化状态 (HVCI/内存完整性是否开启)

3. 软件环境:
- 显卡驱动版本 + 日期 → 对比游戏最低要求
- 已安装杀毒软件 (SecurityCenter2 WMI namespace)
- Windows Defender 实时保护状态
- 反作弊驱动列表 (vgk.sys, easyanticheat.sys, faceit.sys 等)

4. 异常状态检查:
- Windows 更新是否有待处理的重新启动
- 磁盘是否有待处理的坏扇区
- 是否有设备管理器中显示黄色叹号的设备

五、工具最终的行为流程

玩家双击 DiagnosticTool.exe
│
├── [0-5秒] 显示界面: "正在检测您的系统..."
├── [5-30秒] 采集 Crash/Dump + EventLog
├── [30-60秒] 采集 Network (Ping+Traceroute+TCP)
├── [60-75秒] 采集 System Snapshot (WMI)
├── [75-80秒] 分析 + 匹配已知问题模式
├── [80-85秒] 生成 JSON + HTML 报告
├── [85秒] 询问: "是否将诊断报告发送给客服？"
│ 是 → 上传 JSON (可选，需网络)
│ 否 → 仅保存本地
└── [完成] 打开 HTML 报告，工具退出

六、与服务端的配合

客户端工具生成 JSON 后上传，服务端可以：

  1. 自动化分级：根据 JSON 中的问题严重性自动分类工单（蓝屏=最高优先级）
  2. 模式匹配知识库：已知 Bug（如 nvlddmkm.sys + 驱动版本 555.99 = 已知崩溃）自动匹配修复方案
  3. 批量分析：统计所有玩家的 Crash 模块分布，快速发现某次更新引入的共性 Bug

总结：方案从"实时监控"切换到"一次性诊断快照"，聚焦于蓝屏/崩溃/死机/严重丢包/启动失败五类阻断性事件，通过解析 Minidump + EventLog + 网络探测 + 系统快照，在 90 秒内生成可操作的诊断报告。
