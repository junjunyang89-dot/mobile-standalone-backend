# 同一份结果的增量更新

## 身份与依据

保持需求、场景、问题和接口的稳定 ID。用例按业务行为和预期识别，不按列表行号重新编号；新增场景分配新 ID。接口用 service+method+normalizedPath 关联，并另存网关映射、版本和别名。

每次输入保存内部依据：需求材料快照/用户补充结论、每仓库 SHA、相关 DDL/配置、分析时间、覆盖范围、原有用例与实际执行记录。内部历史不要求测试在页面选择“第几波”。

读取上一份结果后，先做需求语义变化、代码差异、公共依赖和数据结构变化的交叉影响分析。字段名称变化不一定是业务变化；路径不变也不一定无需回归。

## 合并规则

- 新业务行为：新增用例，不改动其他场景身份。
- 已有行为变化：保留 caseId；生成修订候选及受影响原因，标待复测；审核后应用内容。旧版本与旧执行结果留档。
- 原结论被已确认需求推翻：撤回/修正问题，调整依赖该假设的用例；不要直接标通过。
- 没有受影响证据且依赖链已核对：保留原用例和结果，说明沿用范围。
- 新变化可能影响但证据不足：标影响待确认，具体指出缺失依赖；不能宣称已经确定无需复测。
- 功能被删除：建议停用，保留历史关联，不物理删除旧执行记录。
- 仅需求说明新增但语义未变：补充来源，不无故重置执行结果。

执行记录至少保留 caseId、caseRevision、需求依据、各服务 SHA、环境/数据标识、时间、结果、执行证据。需求变化或依赖代码变化使旧结果不能覆盖当前行为时，保留历史结果并新增“待复测”，不覆写原通过/失败事实。

多个人工编辑/执行同时发生时，使用上次读取的 revision/hash 作为写入前提；发现变化先重新合并，不能覆盖未读取的人工修改。

## 当前报告展示

只维护一份 current-report 和 current-analysis。测试主要看到当前风险、场景/接口及新增、已调整、待复测等标签；变化原因可展开。后台 history 保存旧快照用于追溯，不额外生成提测管理流程。

审核候选合并和实际用例执行是两种状态；不得把“用户接受调整”当“测试通过”。自动分析失败时保留上一份有效报告，提示哪些新材料尚未纳入，不以空结果覆盖。
