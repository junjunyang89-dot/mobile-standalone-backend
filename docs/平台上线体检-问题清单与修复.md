# 平台上线体检：问题清单与修复

> 审计角度只有一个:**从 1 个人调试,变成 50 人跨部门共用,什么会坏。**
> 很多现在完全正常的设计,50 人一起用就会出事。

---

## 〇、先说好的部分(不用动)

审之前我以为鉴权是薄弱环节,结果是全平台写得最扎实的一块:

- `AuthFilter` 用 `UrlPathHelper.getPathWithinApplication` 而不是 `getRequestURI`
  ——后者是未解码的原始 URI,`/api/health/../platform-users` 会看着像公开接口
- 路径穿越**直接拒绝**而不是归一化后放行
- 前缀按**路径段**匹配,`/platform-users-export` 不会继承 `/platform-users` 的规则
- 账号服务查不到时 **fail-closed**(拒绝而非放行)——注释里写明了为什么
- 停用账号每个请求现查
- 前端菜单从 `/auth/me` 取,规则单一来源

还有几处设计明显是踩过坑才写成这样的,保留:

- **设备锁用 `compute` 做原子 CAS**,不是"先查后写";`renew` 也是原子的
- **派活顺序正确**:先拿锁、成功了才改库,异常路径全部 release
- **Appium 每设备独立端口**,经典的"多台 Android 撞 8200"已解决
- **模拟器不跑生产是服务端强制的,三层拦**(不是只靠前端提示)
- **页面删除有级联护栏**,注释写明"级联删会一次毁掉别人采了半天的元素"
- **secret 掩码回传保护**:前端把 `••••` 原样提交回来时不会覆盖真值

## 一、本轮已修(6 处)

### 1. 一台设备 adb 卡死 → 全平台派活永久停摆 ⭐最狠

**问题**:`@EnableScheduling` 但没配线程池大小,Spring Boot 默认 **1 根线程**,
而平台有 **8 个 `@Scheduled`** 方法共用它——其中包括派活的唯一入口
`DeviceTaskScheduler.dispatch`(3 秒一轮)和会调 adb 的设备扫描(5 秒一轮)。

`DeviceManager` 里十几处 `process.waitFor()` **没有超时**。6 台设备挂同一台机、
USB hub 常年满载,`adb shell getprop` 挂死是必然事件。

**50 人后果**:这根线程一旦阻塞,`dispatch()` 再也不会执行,所有人的排队任务全部冻结,
30 分钟后被逐个判 BLOCKED。界面上看起来是"没有可用设备",**日志里没有一条指向真正原因**,
必须重启才能恢复。

**已修**:`application.yml` 配 `spring.task.scheduling.pool.size: 4`。
4 根线程不是为了提速,是为了"一个卡住不连累其余"。

> ⚠️ **adb 的 `waitFor()` 超时我没改**——十几处分散在 `DeviceManager`,
> 改错一处会让设备探测静默失效。这条留给你安排,见第二节。

### 2. 重启后所有定时计划静默消失 ⭐最隐蔽

**问题**:Quartz 默认 RAMJobStore(进程内存),而 `schedulePlan` 只在"建计划"和
"改计划"时被调用过,**没有任何启动时的重注册**。

**50 人后果**:每次重启之后,库里计划还是 `enabled=true`、界面照样显示 cron 和
"下次执行时间"(那个时间是建计划时算好写库的),但 Quartz 里**一个 trigger 都没有**。
而你们每周都有版本迭代、重启频繁——**定时回归长期不跑,而且没有任何报错**。
等有人想起来问"上周的定时回归结果呢",已经空跑很多天了。

**已修**:新增 `ScheduleRehydrator`,在 `ApplicationReadyEvent` 时把库里启用的计划
全部重新注册。逐条 try/catch——cron 是人填的,一条脏数据不能让全部定时任务都不跑
(那症状和这个 bug 本身一模一样)。

> 放 `ApplicationReadyEvent` 而不是 `@PostConstruct`:后者在 Bean 初始化阶段就跑,
> 那时 Scheduler 可能还没启动。

### 3. 设备回收压根不运行

**问题**:`FlowRecorder.sweepExpired()` 逻辑本身是对的,但**只挂在录制自己的请求路径上**
(`start` 和 `step`)。"没人再来点录制"时它完全不运行。

**50 人后果**:有人开着录制页去开会,那台设备就一直被占着,
而排队任务在 30 分钟后判 BLOCKED。症状是**设备明明闲着,任务却全部失败**。

**已修**:改成 `@Scheduled(fixedDelay = 60_000)`。1 分钟一轮足够,sessions 是内存小 Map。

### 4. 用 POST 实现的批量销毁绕过"DELETE 要 ADMIN"

**问题**:权限按 HTTP 方法分档,前提是"销毁都走 DELETE"。但实际上:

- `POST /api-tests/cases/reimport` 会**先删光**该项目所有 `created_by` 以 `seed-` 开头的用例再重导
  ——别人在种子用例上调好的断言、提取变量、字段备注,全批物理删除,接口只返回导入条数
- `POST /screenshot-storage/cleanup?dryRun=false` 不可逆删文件(别人报告里的证据截图)

两个都只要 TESTER。

**已修**:`PermissionRules` 新增 `ADMIN_POST_SUFFIXES`
(`/reimport`、`/cleanup`、`/clear`、`/reset`、`/truncate`、`/purge`),提到 ADMIN。
和已有的 `READ_ONLY_POST_SUFFIXES` 对称:那份把"其实只是读"的 POST 降到 VIEWER,
这份把"其实是销毁"的 POST 升到 ADMIN。

### 5. 生产环境配置任何 TESTER 都能覆盖,且覆盖即永久丢失

**问题**:`ADMIN_ONLY_PREFIXES` 只有 `/platform-users` 和 `/worker-nodes` 两项。于是
`PUT /api-tests/envs/PROD`(生产 baseUrl + 默认鉴权头)和
`PUT /api-tests/envs/PROD/variables`(生产账号变量)都只要 TESTER,落库是无条件 upsert。

而 `EnvVariableService` **刻意不提供查看真值的接口**(注释里写明了),
所以 secret **覆盖即永久丢失**——没人说得出旧值是什么,也没有留痕。

**50 人后果**:一个人为了调自己那条用例把 PROD 的 baseUrl 指到预发,
全组的线上巡检结果静默变成假阳性,而报表上看不出任何异常。

**已修**:生产环境的**写操作**提到 ADMIN。只拦写——读(变量值已掩码)照旧,
否则查问题都查不了。用包含匹配因为生产段夹在路径中间(`/api-tests/envs/PROD/variables`),
但做了防误伤:`/products/p-1`、`/production-report` 不会被提权。

### 6. 生产确认的后端检查在一条路径上永远为真

**问题**:`ApiTest.vue` 传 `confirmProd: runEnv.value === 'PROD'`,
于是后端 `ApiTestRunnerService:108` 那道 `PROD 必须 confirmProd=true` 的检查
在这条路径上**永远为真,等于不存在**。

> 这一条我要更正一下我自己的审计:**那条路径其实有弹窗确认**,不是完全没护栏。
> 真正的问题是后端那道检查失去了意义——哪天有人重构掉弹窗、或者新加一个入口,
> 后端就接不住了,而那种漏洞不报错,只会安静地对生产发真实请求。

**已修**:`confirmProd` 改成来自"人真的点了确认"这件事(`prodConfirmed` 变量,
只在 `ElMessageBox.confirm` 成功后置 true),顺带在弹窗里显示用例条数。

## 二、还没修的(按优先级,都有行号)

我没有一口气全改,原因是后面这几条要么涉及**数据库变更**,要么要**改十几处分散代码**,
属于该单独安排、单独验证的变更。一次性全塞进来,出问题时分不清是哪一条引起的。

### A. 署名:`created_by` 字段存在但从不写入 ⭐建议最先做

四张表都有 `created_by`(`UiFlow:53`、`UiElement:45`、`TestCase:21`、`ApiTestCase:64`),但:

- **服务端从不写它**:`UiFlowService.create()` 兜底了 catalog / environment / enabled / sortOrder,
  **唯独没有 setCreatedBy**,字段恒为 NULL
- **由客户端提供、可伪造**:`UiFlowController:236` 直接把请求体落库
- **完全没有 `updated_by`**(全仓 grep 无结果)

身份其实拿得到——`AppPackController:117` 就有现成的 `createdBy(request)` helper,
流程/元素/用例这几个最该用的反而没用。

**为什么最先做**:50 人共用一个池子,谁建的、谁改的一律查不到,出事只能全组对口供。
**而且这是后面所有事情的前提**——没有署名,任何一条问题出了都只能靠回忆。

工作量:把那个 helper 提成公共工具,在 4 个 create 入口服务端强制盖章(忽略请求体里的该字段)。

### B. 并发编辑静默覆盖 ⭐

全仓无 `@Version`、无 `updated_at` 比对。`UiFlowMapper.xml:113` 是
`UPDATE ui_flows ... WHERE id = #{id}`,WHERE 里只有 id。而前端是**整份 steps 数组重发**
(`UiFlows.vue:3401`),不是增量。

**后果**:两人同时开同一条流程,后点保存的把前一个人加的十几步整段抹掉,
两边都看到"已更新",没有冲突提示,也没有留痕可恢复。

修法:加 `row_version INT`,`UPDATE ... WHERE id=? AND row_version=?`,
`affected==0` 返 409 + 当前最新值,前端做"别人已改,查看差异"。**需要 SQL 变更。**

### C. 元素改名/删除会静默炸掉所有人的流程 ⭐性价比最高的防呆

流程对元素是**按英文名晚绑定**(`UiFlowExecutor:798`),而元素侧:

- `UiElementService:153` 可以随意改 `nameEn`,**没有任何"有 N 条流程在引用"的检查**
- `UiElementService:185` 删除是裸 `deleteById`,零引用检查

而 `UiPageService:278` 为了防止的**正是这件事**,并且做对了,注释写着
"流程里引用它们的步骤会集体失效——现象是执行时「找不到元素」,没人会联想到是有人删了个页面"。

**页面层挡住了,元素层没挡。** 照抄过来即可,扫描逻辑 `UiFlowService.collectLocatorVariables:344`
已经会解析 steps,可复用。

### D. 零操作留痕 + 全部硬删

`PermissionRules:193` 写着"改错了能改回来,删掉的没有回退"——但**这个前提在代码里不成立**:
全仓没有 `audit` / `operation_log` / `deleted_at` / 回收站(60 多个 SQL 文件里一处都没有),
也没有版本表。所以覆盖写和删除现在**同样不可恢复**。

最小可行:加一张 `change_log`(who / entity / id / before / after / at),
只需在 4 个 update/delete 入口各挂一行。比做完整版本管理便宜得多。**需要 SQL 变更。**

### E. 定时测试计划绕过设备池,静默丢弃

`TaskDispatcher:65` 只查 `CONNECTED`、**不查设备锁**,而且 `:118` 把 deviceId 写死,
于是永远进不了队列(`TaskMapper.xml:70` 的队列条件排除了带 device_id 的行)。
设备被占时抛异常,被 `:72` 吞掉只留一行日志。

**50 人后果**:6 台设备被占满是常态,于是**几乎每次定时计划触发都会被丢掉**。
任务停在 PENDING + 已写死 deviceId,既不在队列也没人重试,界面上不是失败也不是完成——
无人值守回归静默失效,而通过率报表看不出异常。

### F. 僵尸占用被抢占,但老执行线程不会被杀

`DeviceLockService` 的 `MAX_HOLD = 2 小时`,到点抢占——但**只换了锁表里的持有者,
没有任何地方去 cancel/kill 原持有者**。`TaskService:367` 提交时丢弃了 `Future`,
没有 `cancel(true)` 通路。

**后果**:老线程仍在向同一台手机发 Appium 指令,新任务同时也在跑,
两份自动化互相点击,产出两份**看着正常、实则都不可信**的结果。

### G. 元素采集完全不加锁

`DeviceLockService` 的 `Kind.INSPECT("元素采集")` **声明了但全仓从未被 acquire**
(4 个 `tryAcquire` 调用点分别传 MANUAL / REGRESSION / RECORD / TASK)。
`DeviceInspectService:619` 只做了"读一眼就走"的 check-then-act。

**后果**:这是最高频的交互路径(你们元素录入坚持人工,50 人天天点选)。
A 在点选 → 锁表里设备仍空闲 → 3 秒内 dispatch 把任务派过去 → 人和自动化同时操作同一台手机。
被污染的 locator 会安静入库,到回放时才炸。

### H. 排队超时 30 分钟 < 人工借用上限 2 小时

`QUEUE_TIMEOUT = 30min`、`MAX_HOLD = 2h`。时间线注定是"任务先死、设备后放"。

这条**我故意没改**:把排队超时抬到 2 小时以上,意味着人要等两小时才被告知失败,
体验更差;把闲置回收缩短又可能打断正在思考的人。**这是个产品取舍,该你定。**
我的建议是给 MANUAL/RECORD 加短的无心跳回收(5 分钟),而不是动这两个常量。

### I. 流程执行不传 environment 默认打生产

`TestEnvironment.normalize` 空值返回 PROD(注释说是为了兼容存量),
而 `UiFlowController:370` 的执行接口**没有任何 confirmProd 校验**,只有前端弹窗。

`AuthFilter` 自己写了"客户端是 Electron,打开 DevTools 或直接 curl 就绕过去了"
——同一条推理对这个弹窗完全适用。

有意思的是 `AiFlowComposer:627` 已经因为同样的理由单独处理了:
"不能直接用 TestEnvironment.normalize:它对空值返回 PROD"。这个判断在执行入口也该成立。

### J. 两个待引爆的地雷(现在不炸,一改就炸)

- **`DeviceLockService` 是单实例内存锁**,注释里写明"多实例部署时需换成 DB 行锁"。
  仓库里已经有 worker 节点概念(`application-worker.yml`、`WorkerHeartbeatAgent`)。
  一旦为了扛 50 人起第二个节点,**设备互斥完全失效且不报错**。
  建议加一道启动断言:检测到多节点配置就拒绝启动,把这个约束从注释变成代码。
- **DB 连接池 `maximum-pool-size: 10`**,50 人前端轮询 + 8 个定时任务 +
  不设上限的 `newCachedThreadPool` 共用。我没有测量实际并发数,不下结论,
  但这是上线前值得先压一遍的地方。

## 五、上线前我建议的顺序

**第一批(本轮已做)** — 都是"不做会静默出事"的:
线程池、Quartz 重注册、设备回收、两处提权、生产确认。

**第二批(建议你安排,按这个顺序)**:

1. **A 署名** — 半天。后面所有事的前提,没有署名任何问题都只能靠回忆
2. **C 元素引用检查** — 半天。照抄现成模式,防呆性价比最高
3. **B 乐观锁** — 一天,需要 SQL。防"几十步被抹掉"
4. **G 元素采集加锁** — 最高频路径,但要处理会话生命周期,需要前端配合心跳
5. **E 定时计划走设备池** — 无人值守能力的根本
6. **J 多节点启动断言** — 一小时,防止将来扩容时无声出事

**H 那条(排队超时)是产品取舍,等你定。**

要我接着做第二批里的哪一条?我的建议是 **A + C**——都是半天量级、不碰数据库、能单测,
做完你们就有"谁改的"和"改了会不会炸别人"这两条基本保障,再开放给 50 人心里有底。
