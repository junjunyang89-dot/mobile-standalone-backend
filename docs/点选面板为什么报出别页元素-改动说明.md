# 点选面板为什么会报出「别的页面的元素」

## 结论先说

点选功能没有拿错页面。它拿的截图和控件树来自同一次 `snapshot`，是同一时刻的同一屏。

它做错的是另一件事：**把「元素库里某条元素的定位串里带着这个节点的 resource-id」当成了「这个节点就是那条元素」**，中间少了一步验证。

而它真正想告诉你的事实是：

> `com.pwrd.steam.esports:id/vg_function_list` 这个 resource-id，在这一屏也有；
> 你库里的「金刚位容器 / discover_icon_rail」用的就是这个 id 去定位的。

Android 的 resource-id 在不同页面反复复用是常态。所以这不是「打印了别的页面的元素」，是**你那条金刚位的定位不唯一**——面板用一种最容易让人误解的方式说了出来。

## 代码里是怎么走到这一步的

`DeviceInspectService.prependActiveLibraryHits`：点击落点下的小控件，如果元素库里有同 resource-id 的 ACTIVE 元素，就把库里那条定位**置顶推荐**，并且用库里的中文名当标题。

判断「是不是同一个」的是 `locatorBelongsToNode`，它只做字符串包含：

```java
if (val.contains(rid) || (sid != null && val.contains("/" + sid))) return true;
```

定位串里出现了这个 id，就算数。从没在当前这棵树上真的跑一次。

于是你在评论页点了一个 id 恰好也叫 `vg_function_list` 的容器，面板理直气壮地说「这是金刚位容器」。

更要命的是第二件事：后端一直在算每个定位在当前屏**命中几个节点**（`enrichMatchCounts` → `matchCount` / `unique`），接口也一直在返回，**前端从来没显示过**。最该看见的一个数字，被丢在了半路上。

## 这大概率就是金刚位滑不动的原因

`//android.widget.LinearLayout[@resource-id="com.pwrd.steam.esports:id/vg_function_list"]`

如果这条 xpath 在首页命中不止一个节点，Appium 的 `findElement` 只取**文档序第一个**。第一个不是金刚位的话：

- 元素找得到 ✅
- 手势发出去了 ✅
- 日志一片绿 ✅
- 界面上什么都没发生，或者滑到了别的东西 ❌

「元素找得到、操作也成功、界面没反应」——之前几轮排查一直卡在这里，这条线是通的。

## 改了什么

### 1. 推荐之前先在这棵树上跑一遍

`LocatorMatcher` 新增 `matches()`：不只回答「命中几个」，还回答**分别是谁、谁排第一**。然后 `prependActiveLibraryHits` 按结果分四种情况处理：

| 情况 | 处理 |
| --- | --- |
| 命中 1 个且就是你点的 | 照常置顶推荐 |
| 第 1 个就是你点的，但不止 1 个 | 推荐，但标注「本屏命中 N 个，眼下第 1 个正好是它，页面一变就会指向别的」，并给告警 |
| 命中了几个，但你点的排在第 2、3 位 | **不推荐**，改成告警：执行时 Appium 会操作第 1 个，不是这里 |
| 一个都没命中 | **不推荐**，告警：这条定位写得太死 |
| 无法校验（坐标方案、xpath 语法错） | 按老样子推荐 —— **校验不了不等于有问题**，硬判会把一批好用的元素挡在外面 |

告警显示在候选列表上方的红条里。它说的不是「这个节点怎么定位」，而是「你库里那条元素坏了」——两件事，不该挤在同一个列表里。

### 2. 把命中数显示出来

每个候选下面多一行：

- `本屏唯一` —— 灰色，常态
- `本屏命中 3 个 · 执行时只会用第 1 个，未必是你要的这个` —— **红色加粗**
- `本屏一个都没命中：这条定位现在是失效的`
- `本屏唯一性未知（这类定位没法在控件树上校验）`

后端本来就在算，这次只是让它到得了眼前。

### 3. 顺带

`count()` 改成走 `matches()`，一套逻辑；`matches()` 同时支持 Android 的 `bounds="[l,t][r,b]"` 和 iOS / 鸿蒙的 `x/y/width/height`。

## 你现在该做什么

**第一步，确认一下我的判断（10 秒）。** 重启前就能做：在同一屏点「全部评论」或「只看楼主」这几个字。

- 如果候选里出现 `text · 全部评论` —— 树是新鲜的，那么上面的诊断成立，是 id 复用。
- 如果点了没反应、或者出来的还是 `vg_function_list` —— 那就是截图和树对不上，是另一个问题，把结果发我。

**第二步，重启后端**，再点一次金刚位。现在面板会直接告诉你那条定位在本屏命中几个。

**第三步，用元素库的「页面体检」扫一遍。** 这个能力早就有了（`UiElementHealthService.probe`），算的就是同一个数，判定文案是「定位不唯一（命中 N 个）」。这类问题多半不止金刚位一个。

**定位不唯一怎么收紧**，按优先级：

1. 加上 class：`//android.widget.HorizontalScrollView[@resource-id="..."]`
2. 用祖先限定：`//*[@resource-id="首页根容器"]//*[@resource-id="vg_function_list"]`
3. 用里面的文案锚定：`//*[@resource-id="vg_function_list"][.//*[@text="完美开箱"]]`
4. 实在没辙才用 `(...)[1]` 这种下标——它跟页面结构绑死，改版必挂，属于下策

`scripts/find_scroll_container.py --text <金刚位上的某个文字>` 仍然是找对那一层最快的办法。

## 涉及文件

后端：

- `service/inspect/LocatorMatcher.java` — 新增 `matches()` 与 `Hit`；`count()` 改为复用它
- `service/DeviceInspectService.java` — 推荐前验证；新增 `HitTestResult.warnings`；`parseAndHit` / `collectHitCandidates` 透传控件树与告警

前端：

- `components/DeviceInspectDrawer.vue` — 显示命中数；候选列表上方显示告警
- `api/index.ts` — 补上 `matchCount` / `unique` / `warnings` 的类型

## 验证情况

- `LocatorMatcher` 的 15 个用例全过，其中直接复现了你这一屏：同一个 `vg_function_list` 出现两次，断言「第 1 个是评论页那个、金刚位排第 2」——也就是 Appium 会拿错的那个场景
- iOS 的 `x/y/width/height`、树上无坐标、xpath 语法错、坐标定位这四种边界都单独覆盖了，确保「校验不了」不会被误判成「失效」
- 改动涉及的两个后端文件全量 `javac`：相对补丁前基线，唯一的新错误是 `setWarnings`（Lombok 生成的 setter，本机跑不了注解处理）。**完整 `mvn compile` 还得你本地确认一次**
- 前端：Vue SFC 编译通过，`api/index.ts` 语法解析通过
