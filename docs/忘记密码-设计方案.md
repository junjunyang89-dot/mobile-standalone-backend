# 忘记密码 — 设计方案

> 状态：待评审。确认后再落代码。
> 前提：本平台独立管理账号，暂不接公司统一认证；使用人数 50+，跨部门。

---

## 一、现状（代码事实，不是假设）

| 项 | 现状 | 影响 |
|----|------|------|
| `platform_users` 字段 | id / username / display_name / password_hash / role / enabled / last_login_at | **没有邮箱、没有手机号**——目前平台不掌握任何可以联系到本人的渠道 |
| 口令散列 | PBKDF2-HMAC-SHA256，12 万次迭代 | 够用，不动 |
| 密码强度 | 仅「至少 6 位」 | 50+ 人规模偏弱 |
| 登录令牌 | HMAC 签名、服务端不存，payload = `userId:expiresAt`，7 天 | **无法按用户撤销**——改完密码，旧登录态还能继续用 7 天 |
| 已有重置能力 | 管理员 `POST /platform-users/{id}/reset-password`；本人 `POST /auth/change-password`（需旧密码） | 忘记密码的人两条都走不通 |
| 邮件能力 | 已接公司 Exchange（`ReleaseMailService`，发版文档用） | 通道现成，但用的是个人账号（见第八节） |
| 客户端形态 | **Electron 打包分发**（见 `AuthFilter` 注释） | **决定了不能走「邮件里点链接」**，见第三节 |

一句话：缺的不是重置逻辑，是**「怎么确认申请人就是账号本人」的渠道**。

---

## 二、选型

| 方案 | 结论 | 理由 |
|------|------|------|
| **邮箱验证码自助重置** | ✅ 采用 | 公司邮箱本身就是一道身份证明，通道现成，零采购成本 |
| 管理员重置 | ✅ 保留为兜底 | 没绑邮箱、邮箱收不到时还得有人能救；但不能作为唯一手段——50+ 人跨部门，管理员会被打断到麻木，且「口头/IM 告知新密码」是最常见的密码泄露路径 |
| 短信验证码 | ❌ | 平台没存手机号，短信通道要采购、按条计费，为一个内部工具不值当 |
| 密保问题 | ❌ | 答案要么能被同事猜到、要么本人也忘了，是公认已经淘汰的做法 |
| 自助注册 + 邮箱验证 | ❌ | 账号仍应由管理员创建。这是内部平台的正确边界，不要顺手放开 |

## 三、关键决策：为什么是**验证码**，不是邮件里的链接

一般 Web 平台的标准做法是「邮件发一次性链接」。这里**不适用**，有两个原因：

1. **客户端是 Electron。** 邮件里的 `https://...` 链接点开落在浏览器里，回不到客户端。要么额外写一套服务端渲染的重置网页（和现有前端割裂），要么让用户复制长令牌串粘回客户端（会被邮件客户端折行）。
2. **公司邮件安全网关会预取链接。** Exchange/ATP 这类网关会自动访问邮件里的 URL 做扫描——一次性链接会在用户点击之前就被消费掉，用户点进去只看到「链接已失效」。这是企业内网邮箱环境里非常常见的坑。

所以：**邮件里发 6 位数字验证码，用户回到客户端里填**。全程不离开客户端，也不怕网关预取。

> 代价是验证码熵低（10⁶），必须靠限流兜住——见第五节。
> 如果将来出 Web 版，可以再加一个链接入口，令牌表结构不用改（`token_hash` 存什么都行）。

## 四、数据库改动

### 4.1 `platform_users` 加三个字段

```sql
ALTER TABLE platform_users
  ADD COLUMN email VARCHAR(255) DEFAULT NULL COMMENT '找回密码用，唯一',
  ADD COLUMN password_changed_at DATETIME DEFAULT NULL COMMENT '改密时间，用于踢掉旧登录态',
  ADD COLUMN must_change_password TINYINT(1) NOT NULL DEFAULT 0 COMMENT '管理员重置后强制改密',
  ADD UNIQUE KEY uk_platform_users_email (email);
```

- **邮箱必须唯一**，否则验证码发给谁不确定。
- MySQL 的 UNIQUE 索引允许多个 NULL，所以存量账号邮箱为空**不会互相冲突**，可以平滑加索引，不用先补数据。
- 建表语句写在 `PlatformUserService.ensureSchema()` 里（沿用现有惯例：`CREATE TABLE IF NOT EXISTS` + 幂等 `ALTER`，别新开迁移体系）。

### 4.2 新表 `platform_password_resets`

```sql
CREATE TABLE IF NOT EXISTS platform_password_resets (
    id VARCHAR(64) PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    purpose VARCHAR(16) NOT NULL DEFAULT 'RESET' COMMENT 'RESET=忘记密码 BIND=绑定邮箱',
    code_hash CHAR(64) NOT NULL COMMENT 'HMAC-SHA256(secret, userId:purpose:code) 的 hex，不存明文',
    target_email VARCHAR(255) DEFAULT NULL COMMENT 'BIND 时是待绑定的新邮箱',
    expires_at DATETIME NOT NULL,
    attempts INT NOT NULL DEFAULT 0 COMMENT '已尝试次数，满 5 次即作废',
    used_at DATETIME DEFAULT NULL,
    invalidated_at DATETIME DEFAULT NULL COMMENT '被后发的验证码顶掉',
    request_ip VARCHAR(64) DEFAULT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    KEY idx_pwd_reset_user (user_id, purpose, created_at),
    KEY idx_pwd_reset_ip (request_ip, created_at),
    KEY idx_pwd_reset_expire (expires_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

> 实现时比原方案多了 `purpose` 和 `target_email` 两列：绑定邮箱（5.3）也要发验证码，
> 逻辑和忘记密码完全一样，多开一张表等于把限流、限次、作废这些规则各写两遍，迟早分叉。
> `target_email` 是必需的——验证码发到哪个邮箱就只能绑哪个，不比对的话，
> 拿发到自己邮箱的码去绑别人的邮箱是成立的。

**为什么是 HMAC 而不是直接存 SHA-256：** 6 位数字只有 100 万种可能，直接 SHA-256 的话，谁读到库都能秒算一张彩虹表把验证码反查出来。用 `HMAC-SHA256(签名密钥, userId + ":" + code)`——密钥复用 `AuthTokenService` 已经落库的那个——没有密钥就反查不了。

**为什么不用 PBKDF2：** 那是给人设的口令用的（低熵、可字典撞）。验证码有效期只有 10 分钟且限次，慢哈希只会拖慢每次校验，没有收益。

**清理：** 过期记录保留 7 天用于审计，之后按 `expires_at` 定时清（复用现有定时任务体系）。

## 五、接口设计

新增三个接口，都要加进 `PermissionRules.PUBLIC_PREFIXES`——**忘记密码的人本来就登录不了**。

### 5.1 `POST /auth/forgot-password`（公开）

```jsonc
// 请求：用户名或邮箱都收，用户不用记自己填的是哪个
{ "account": "yangjunjun" }
```

```jsonc
// 响应：恒定 200，恒定文案
{ "message": "若该账号存在且已绑定邮箱，验证码已发出，请查收（10 分钟内有效）" }
```

**账号不存在、账号被停用、账号没绑邮箱——一律返回同一句话。** 分开报就等于送了一个免费的账号枚举接口。邮件**异步发送**，让响应时间也保持一致，否则耗时差本身就是一个枚举信道。

命中时的动作：作废该用户所有未使用的验证码 → 生成新验证码 → 入库 → 异步发信。

### 5.2 `POST /auth/reset-password`（公开）

```jsonc
{ "account": "yangjunjun", "code": "482913", "newPassword": "..." }
```

- 校验通过：更新 `password_hash`、`password_changed_at = now`、`must_change_password = 0`，标记验证码 `used_at`，作废该用户其余未用验证码。
- 校验失败：`attempts + 1`；满 5 次即把这条验证码作废（**作废验证码，不锁账号**——锁账号意味着任何人都能拿别人的用户名把人锁死）。
- 响应 `200 { "success": true }`。

**不自动登录。** 重置成功后前端跳回登录页要求重新登录。自动登录只是省一步，却把「拿到那封邮件 = 直接进系统」的窗口拉长了。

### 5.3 `POST /auth/bind-email`（需登录）

给存量账号补邮箱，以及本人换邮箱。

```jsonc
// 第一步：发确认码到新邮箱
{ "email": "someone@pwrd.com", "password": "当前密码" }
// 第二步：确认
{ "email": "someone@pwrd.com", "code": "123456" }
```

**必须验当前密码 + 必须往新邮箱发确认码。** 少任何一步，一个被借用的登录态就能把邮箱改成自己的，然后走忘记密码永久夺号——那样这个功能就从「找回密码」变成了「送出账号」。

### 5.4 管理员侧改造

现有 `POST /platform-users/{id}/reset-password` 增加一个模式：

```jsonc
{ "sendEmail": true }              // 推荐：管理员不接触密码，直接给用户发验证码
{ "newPassword": "临时密码" }        // 保留：没绑邮箱时的兜底
```

走 `newPassword` 分支时，自动置 `must_change_password = 1`。

## 六、限流与防爆破

6 位验证码只有 10⁶ 种可能，安全性完全由限流提供。无 Redis，**直接查 `platform_password_resets` 表统计即可**，量级很小。

| 维度 | 规则 | 目的 |
|------|------|------|
| 同账号发码 | 60 秒内 1 次；1 小时内最多 3 次 | 防邮件轰炸 |
| 同 IP 发码 | 1 小时内最多 10 次 | 防批量枚举 |
| 单个验证码 | 最多 5 次尝试，失败即作废 | 防爆破 |
| 验证码有效期 | 10 分钟 | 缩小窗口 |

综合起来：一小时内最多 15 次猜测，命中概率约 **0.0015%**，可接受。

**建议一并做（本次改动的自然延伸）：** 登录接口目前没有失败限流，同账号 5 分钟内失败 5 次锁 15 分钟。忘记密码做了防爆破而登录不做，等于留了条更宽的路。

## 七、改完密码要踢掉旧登录态

这是当前架构的一个真实缺口：令牌是无状态 HMAC，密码改了旧令牌照样能用满 7 天。**被盗号的人改了密码，以为安全了，其实攻击者的登录态还在。**

好消息是修起来几乎不要钱——`AuthFilter` 本来就对**每个请求**都执行 `userService.get(userId)` 来判停用状态，加一个字段比较不增加任何查询。

改动：

1. `AuthTokenService.issue()` 的 payload 从 `userId:expiresAt` 改成 `userId:issuedAt:expiresAt`。
2. `verify()` 按 `:` 切分：3 段是新格式；2 段是旧令牌，`issuedAt` 记 0。**存量令牌照常可用**，不会因为发版把全组踢下线（这正是 `AuthTokenService` 注释里明确要避免的事）。
3. `AuthFilter` 取到 user 后：若 `password_changed_at != null && issuedAt < password_changed_at` → 401「密码已修改，请重新登录」。

旧格式令牌的 `issuedAt = 0`，会在该用户第一次改密时失效——这正是想要的效果。

**顺带：**`must_change_password = 1` 的账号，`AuthFilter` 除 `/auth/me`、`/auth/change-password`、`/auth/logout` 外一律 403。只靠前端跳转是拦不住的——客户端是 Electron，后端地址可填，DevTools 一开就绕过去了。

## 八、邮件通道

### 8.1 先落地：用公司邮箱

当前范围收缩到本部门，先不申请服务账号，**用 `yangjunjun@pwrd.com` 这个公司账号发**。
配置独立成一段，别和 `release-doc.mail` 混在一起——将来换服务账号只改这一段：

```yaml
auth-mail:
  enabled: true
  host: ${AUTH_MAIL_HOST:mail.mx.wanmei.net}
  port: ${AUTH_MAIL_PORT:587}
  username: ${AUTH_MAIL_USER:yangjunjun@pwrd.com}
  password: ${AUTH_MAIL_PASSWORD:}      # 走环境变量，不写进 yml
  from: ${AUTH_MAIL_FROM:yangjunjun@pwrd.com}
  code-ttl-minutes: 10
```

TLS 放宽策略复用 `ReleaseMailConfig` 的写法（公司 Exchange 证书主机名不匹配）。

已知的两个代价，现阶段接受：人一离职或改密码通道就断；收件人看到重置邮件来自同事个人地址。
等推广到部门外时再换服务账号。

### 8.2 为什么不用私人邮箱（trav_yang@sina.cn）

作为对照可以测，但**不建议做正式通道**：

| | 公司邮箱 | 私人新浪邮箱 |
|---|---|---|
| SMTP 配置 | 已在跑（发版邮件），零调试 | 要开 SMTP、要用「客户端授权码」而非登录密码 |
| 投递到 @pwrd.com | 内网投递，不过外部网关 | 外部进公司，**反垃圾网关很可能拦或丢进垃圾箱** |
| 后端能否连上 | 部署在公司网内，必通 | 取决于公司出网策略，很可能不通 |
| 收件人观感 | 同事地址，可信 | 外部个人地址 + 「重置密码」+ 验证码 = 钓鱼邮件的典型特征 |
| 合规 | 正常 | 公司内部平台的认证通道走个人私邮，出事说不清 |

最后一行是决定性的：验证码邮件是**认证链路的一环**，不是通知邮件。

### 8.3 实测结论（2026-09-04）

用 `scripts/test_auth_mail.py` 在家里的机器上跑，两条通道的报错**含义完全不同**：

| 通道 | 结果 | 含义 |
|------|------|------|
| 公司 | `[Errno 8] nodename nor servname provided` | **DNS 都没解析出来**。`mail.mx.wanmei.net` 是纯内网域名，家里网络碰不到。跟通道好坏无关，这条没测出结论 |
| 新浪 | `535 5.7.12 SMTP access disabled` | 连接和 TLS **全通了**，是账号本身没开 SMTP 服务，要在新浪网页版开启并生成客户端授权码 |

**公司通道其实已经有证据，不用等回公司。** 后端日志里有一条真实的成功发信：

```
2026-09-02T16:20:21 [release-mail] 已发送 to=yangjunjun@pwrd.com subject=【发版通知】…
```

后端所在机器 → 公司 SMTP → `@pwrd.com` 收件人，**这正是忘记密码要走的那条链路，已经跑通过**。

### 8.4 但这条通道不是「一定成功」的

同一份日志里，成功前两分钟连着两次失败：

```
2026-09-02T16:18:05 [release-mail] 发送失败: Got bad greeting from SMTP host: mail.mx.wanmei.net, port: 587, response: [EOF]
2026-09-02T16:18:13 [release-mail] 发送失败: 同上
2026-09-02T16:20:21 [release-mail] 已发送            ← 进程重启后
```

`Got bad greeting … [EOF]` 是 TCP 连上了、服务器立刻把连接掐掉——常见于反垃圾节流或网络抖动。
现有日志一共只有 3 条发信记录（2 失败 1 成功），样本太小，说不上是规律，但**失败模式是真的**。

这件事对发版邮件无所谓（失败了手动重发一次），对验证码邮件不一样——**用户正在等这封信**。所以实现上必须：

1. **发送失败重试 2~3 次**，间隔递增（如 2s / 5s / 15s）。
2. **失败要落日志且可统计**。否则用户说「没收到」，你分不清是通道抖了、还是进了垃圾箱、还是他填错了邮箱。
3. **响应仍然恒定**——发失败也不能返回不一样的文案，否则又成了账号枚举信道。发信是异步的，接口本来就不该等发信结果。
4. **前端文案留出路**：「2 分钟内没收到？检查垃圾箱，或联系管理员重置」。

### 8.5 部署约束

`mail.mx.wanmei.net` 只在公司网内可解析，因此：**后端必须部署在公司网内，忘记密码功能才可用**。
现在本来就是这样（还要连内网 MySQL、`wiki.shdev.net`、`jira.shdev.net`），但要记一笔：
将来若平台要做公网访问，这条认证邮件通道会跟着失效，得先换成公网可达的发信服务。

### 8.6 新浪通道：不建议继续测

开 SMTP、拿授权码只要两分钟，但测通了也解决不了问题：投递到 `@pwrd.com` 会不会被公司反垃圾网关
拦下来仍然未知，而且它不会成为正式通道（第 8.2 节）。时间花在重试和可观测上更值。

如果确实想留个备份通道：新浪邮箱网页版 → 设置 → 客户端 pop/imap/smtp → 开启 SMTP → 生成授权码，
然后 `python3 scripts/test_auth_mail.py --channel sina --to yangjunjun@pwrd.com`，
**重点看它进的是收件箱还是垃圾箱**。

### 8.7 邮件正文要素

显示名、验证码、有效期、申请时间、申请来源 IP、「不是本人操作请忽略并联系管理员」。
**正文里不出现密码，也不出现完整用户名。**

## 九、存量账号怎么补邮箱

50+ 人不可能一次性收齐，按三条路并行：

1. **管理员批量补录**：账号管理页加邮箱列，可编辑。管理员填的邮箱视为可信，不需要用户确认（账号本来就是管理员建的）。
2. **登录后提示**：`/auth/me` 增加 `emailBound: false`，前端每次登录弹一次「绑定邮箱，以便忘记密码时自助找回」，可跳过但不消失。
3. **新建账号时必填邮箱**：`POST /platform-users` 把 email 设为必填，从源头堵住。

没绑邮箱的人走管理员重置——这也是为什么第二节里管理员重置必须保留。

## 十一、密码策略（顺带收紧）

现在只校验「至少 6 位」，50+ 人的平台建议提到：

- 至少 **8** 位
- 不能是纯数字、不能是纯字母
- 不能包含用户名
- 挡掉最常见的几十个弱口令（`123456`、`password`、`qwerty`、`abc123`…）

只在**新建账号、改密、重置**时校验，**不碰存量密码**——存量的下次改密时自然收敛。别做强制过期，那只会让人把密码改成 `xxx1`、`xxx2`。

## 十二、明确不做

- 不做密保问题
- 不做短信验证码
- 不做自助注册
- 不做重置成功后自动登录
- 不做密码定期强制过期

## 十三、分期与工作量
