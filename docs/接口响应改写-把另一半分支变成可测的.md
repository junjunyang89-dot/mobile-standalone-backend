# 接口响应改写:把"另一半分支"变成可测的

> 目标:让服务端开关的两种状态都能测,顺带解决故障注入。
> **不用改 APP。**

---

## 一、先说机制验证——这一步差点做不成

开关矩阵的前提是**能真的把开关掰到另一个状态**。我先验了三条路:

| 办法 | 结论 |
| --- | --- |
| 直接改手机上的 SharedPreferences | ❌ 进程内存里有缓存,改文件不生效;force-stop 后改再启动,`PWAppConfigManager.loadConfig` 拉回配置又会无条件覆盖 |
| 改服务端配置 | ❌ 全局的,不是按用例;而且测试环境在家访问不了 |
| **代理层改写响应** | ✅ **可行** |

第三条能成,是因为链路已经是现成的:

- 平台的抓包就是 mitmproxy,走 `adb reverse`(USB 直连,不依赖网络环境)
- `app/src/debug/res/xml/network_security_config.xml` **已经信任用户证书**
- 全仓没有 certificate pinning

所以 **改写 `getAppConfigs` 的响应,零 APP 改动。**

---

## 二、它顺带解决的另一类问题:故障注入

开关只是第一个用途。同一套机制还能:

- 让某个接口**超时**(`delayMs`)
- 让它**返回 500**(`status`)
- 让它**返回空列表**(`body`)

而"接口异常时 App 怎么表现"同样是一段几乎没被执行过的代码,
和开关的另一半分支是同一类问题。

---

## 三、最危险的失败方式,以及为此付出的设计

**改不到却当作改了。**

规则指向的字段不存在(接口改版、路径写错),如果静默放过——
整批用例会以为自己在测 B 分支,实际还在测 A 分支,**而且全绿**。

这比不改写糟得多:**它生产的是一个错误的结论,没有任何迹象。**

所以定了四条:

### 1. 一处改不到,整条规则不生效

不是"能改的先改"。部分生效会把响应改成一个**既不是 A 也不是 B** 的形状,
而测试会以为自己测的是 B。

### 2. 默认不创建新字段

App 只读它已知的字段,凭空造一个它根本不会看,但规则会显示"已生效"。
那是一次**被当成生效的空操作**。要新建得显式写 `"create": true`。

### 3. 规则文件有过期时间

**忘了关的改写规则会污染之后所有的测试结果,而那种污染没有任何迹象**——
人只会看到一批莫名其妙的失败,查半天才想起来代理上还挂着东西。
默认 2 小时过期,过期后一条都不生效。

### 4. 生效必须留痕

- 写到 `<flows>.overrides` 文件,平台能显示在执行日志里
- 被改写的响应带 `x-qa-override: <规则id>` 响应头,从手机上抓包也看得出来

人看到一个诡异的响应,第一个该能回答的问题是**「这是不是平台改的」**。

## 四、怎么用

规则文件:`~/.mobile-standalone/captures/api-overrides.json`

```jsonc
{
  "expiresAt": 1790700000,          // 不写就是 2 小时后
  "rules": [
    {
      "id": "sysweb-off",            // 必填,留痕用
      "match": {"path": "/getAppConfigs"},
      "set": {"data.appConfigs.myTabSysWebSwitch": "0"}
    },
    {
      "id": "mall-timeout",
      "match": {"path": "/mall/list"},
      "delayMs": 30000
    },
    {
      "id": "config-500",
      "match": {"path": "/getAppConfigs"},
      "status": 500
    }
  ]
}
```

- `match.path` 用**包含**匹配,不用写全(真实路径常带 `/api/v2/` 前缀)
- `match.host` 按后缀匹配,但 `evilwmpvp.com` 不会被当成 `wmpvp.com` 的子域
- `match.method` 留空＝不限制

开抓包时自动带上,文件不存在就是不改写。

### 开关矩阵怎么跑

同一批流程跑两遍:一遍规则文件里把开关设成 `"1"`,一遍设成 `"0"`,
结果分两组对比。哪些用例只在一种状态下挂,就是那条没人走过的分支的问题。

`myTabSysWebSwitch` 尤其值得先跑——**它直接决定「我的」页面用 X5 还是系统内核**。

## 五、验证

- **508 个源文件真实编译通过**,0 错误;全量 1450 个单测,1416 通过、12 失败(老的 fixture/网络问题,与本次无关)
- **新增 22 个 Python 单测**,全过
- 真跑了一遍端到端的规则解析 + 改写,输出符合预期

### 反向验证

| 退回什么 | 结果 |
| --- | --- |
| 改不到时静默放过 | **4 条红** ✅ |
| 默认允许创建新字段 | **3 条红** ✅ |
| 去掉过期保护 | **1 条红** ✅ |
| 域名改成宽松包含(`evilwmpvp.com` 能冒充) | **1 条红** ✅ |
| **去掉 `copy.deepcopy`(原子性)** | **一条都没红** ❌ |

最后一条要说清楚:那个 `deepcopy` 就当前控制流而言是**多余的**——
失败时走的是 `continue`,压根不会把改动写回,所以直接在原对象上改,返回的响应体也还是原样。
我留着它是防止将来有人把控制流改成"边改边写回",但**它没有被测试覆盖**,
所以不该把它算成一道验证过的防线。代码注释里也这么写了。

### 还有一处我做错了

测试最初往仓库目录里写临时文件,而那个目录不允许删除,5 条测试直接报错。
改成 `tempfile` 了——**测试本来就不该往仓库里写东西**,留下的垃圾文件迟早会被提交进去。

## 六、还没做的

### 1. 平台侧的 UI 和矩阵执行

现在规则要手写 JSON 文件。下一步应该是:
- 规则在平台里可视化配置
- 「执行矩阵」:同一批流程 × N 组规则,各跑一遍,结果分组对比

我没有一起做,是因为**机制先验证了才值得包装**。现在机制通了,包装是确定的工作量。

### 2. 改写留痕还没接进执行报告

`.overrides` 文件已经在写了,但平台还没读它。
**这一步必须补上再大规模用**——一次被悄悄改写过的执行,结论是不能信的,
而现在这件事只有翻文件才知道。

### 3. iOS / 鸿蒙

`adb reverse` 是 Android 独有的。iOS 要手机和电脑同局域网 + 手动配代理
(`PacketCaptureService` 的注释里已经写明了这个限制)。
