# 模拟器卡 + 滑动失败：这是同一个原因

你报的两件事——**「滑动失败: up #1」** 和 **「整体操作非常卡」**——不是两个问题，是一个问题的两个表现。

## 一、根因：这台 AVD 只给了 1 个核

`~/.android/avd/Medium_Phone.avd/config.ini` 里：

```ini
hw.cpu.ncore=1        ← 1 个核
hw.ramSize=2048       ← 2G 内存
image.sysdir.1=system-images/android-36.1/google_apis_playstore/arm64-v8a/
```

单核 + 2G 跑 **Android 16 + Google Play 服务**。镜像是 arm64，在你这台 M 系 Mac 上是有硬件加速的，所以慢的不是虚拟化，就是资源给少了。手动点都卡，键盘敲数字更卡（Gboard 每敲一下都要重绘）。

**这也是滑动失败的直接原因。** `adb shell input swipe` 里的 `input` 不是内核调用，是一个**要现拉起 JVM 的 app_process 程序**——正常机器上光启动就一两秒，单核机上五六秒是常态。而我原来的超时写的是 **5 秒**：

```java
if (!process.waitFor(5, TimeUnit.SECONDS)) {   // ← 顶穿了
    process.destroyForcibly();
    return false;                               // ← 上层报「滑动失败」
}
```

命令根本没跑完就被掐了，返回 false，上层报「滑动失败: up #1」。看起来像手势没生效，实际上手势压根没发出去。重试还是 5 秒，还是超——所以你看到连着两次「滑动失败」。

这类超时最坑的地方就是**报错方向是错的**：它让你去查手势、查坐标、查驱动，而真正的问题是机器慢。

## 二、已经改好的

### 1. AVD 配置（我直接改了，备份在同目录 `config.ini.bak.20260906`）

```ini
hw.cpu.ncore=1  →  4
hw.ramSize=2048 →  4096
```

**要关掉模拟器再重开才生效。** 如果之后用 Android Studio 的 Device Manager 编辑过这台 AVD，它可能把配置写回去——那就在 Device Manager → 这台 → Edit → Advanced 里把 CPU cores 和 RAM 一起调了。

### 2. `adb shell input` 的超时改成按操作时长算

| 命令 | 原来 | 现在 |
| --- | --- | --- |
| `input tap` | 3 秒 | 20 秒 |
| `input swipe` | 5 秒 | `max(20s, 滑动时长 + 15s)` |
| `input text` | **没有超时** | 20 秒 |

`input text` 原来是裸 `waitFor()`，设备卡住就永久挂住整个执行线程——这个比超时太短还危险。

**更重要的是失败现在有话说了。** 以前失败只留一个 `false`，日志里什么都没有；现在超时和非零退出都会把设备端的输出打出来，并明说「设备太慢，命令没跑完就被掐了」。下次再遇到就不用猜了。

### 3. 平台启动模拟器时覆盖核数/内存

`EmulatorLauncher` 现在带 `-cores` / `-memory` 启动，不看 AVD 里写的是多少：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `app.emulator.cores` | `4` | 0 = 用 AVD 自己的 |
| `app.emulator.memory-mb` | `4096` | 0 = 用 AVD 自己的 |
| `app.emulator.disable-animations` | `true` | 开机后自动关系统动画 |

**关动画不只是为了快**（虽然肉眼确实快很多）。主要好处是 `uiautomator dump` 不会再抓到**转场动画中间那一帧**——动画期间控件的 bounds 在移动，抓到的树坐标全是错的，而这种错「偶尔出现、重跑就好」，是最难查的一类。

关动画在设备第一次被认到时后台跑一次，每台只做一次，失败不影响设备进池子。

## 三、另一件事：录制不该从桌面开始

你这条流程的前几步是「桌面上滑 → 打开抽屉 → 点完美世界电竞」。**就算滑动不失败，这几步也是错的**：

- 回放时桌面未必停在第一屏，抽屉可能本来就开着
- 图标位置随装了什么应用而变，只能靠坐标点（就是上一版那个 `fragile` 会标红的情况）
- 换台机器换个 launcher，整段作废

而这三步想说的其实只有一句话：**「打开这个应用」**。平台本来就有 `LAUNCH_APP` 关键字，走包名，跟桌面长什么样完全无关。

所以 `POST /ui-recordings` 现在**默认先把应用拉起来，并记一步 `LAUNCH_APP` 当第 1 步**：

```jsonc
{ "deviceId": "emulator-5554", "appId": "DOMESTIC_ESPORTS",
  "platform": "ANDROID", "name": "登录冒烟",
  "launchApp": true }   // 不传就是 true
```

- 参数刻意留空，回放时 `LAUNCH_APP` 自己去应用字典按平台取包名——写死包名的话，换个 debug/release 包就得改流程
- 拉不起来不算失败（比如字典里没配这个平台的包名），只把这一步标成 `fragile` 并说明原因，人可以手动切到应用首屏接着录
- 只有「就是要从当前这一屏接着录」时才传 `launchApp: false`

**你这条流程建议重录一遍**：开录时应用会自己起来，前面那三步桌面操作根本不会出现。

## 四、键盘输入卡：别在模拟器窗口里敲

模拟器的软键盘是最吃性能的一块（Gboard 每个按键都是一次完整重绘）。平台的「输入」走的是 `adb shell input text`，**一次性把整串塞进焦点控件，完全不碰软键盘**。

所以录制时：**先在左边截图上点一下输入框，再用右边那个输入框填内容点「输入」**，不要切到模拟器窗口去敲。这条你的录制页已经做对了，提示语也在（"输入：先在左边点输入框，再填内容点「输入」"）。

## 五、前端要改吗

**可以不改。** `launchApp` 不传就是 true，行为直接生效。

想给人选的话，在开录表单里加个开关：

```
☑ 开录前先启动应用（推荐）
   关掉的话就从模拟器当前这一屏接着录
```

对应请求体里的 `launchApp`。

另外，第 1 步现在会是一条 `keywordCode: "LAUNCH_APP"` 的步骤，`elementKey` 为空、`locatorValue` 为空——你的 `stepTitle(st)` 要能显示它（如果现在是按 `elementNameZh` 显示的就没问题，后端填了「启动应用」）。

## 六、验证情况

- **446 个源文件真实编译通过**，0 错误
- **全量 1228 个单测**：1186 通过、20 跳过、12 失败——12 个全是缺 `/doc/app-8999.docx` 测试资源和需要网络的 AI 客户端测试，改动前后完全一致
- **没验到的**：这几处都是设备侧行为（超时、启动参数、关动画），单测碰不到。要看效果得：
  1. **关掉模拟器，重开**（config.ini 的核数/内存才生效）
  2. 重启后端
  3. 重新录一条，确认第 1 步是「启动应用」而不是桌面滑动
  4. 试跑

如果滑动**还是**失败，现在日志里会明确写是超时还是命令报错，把那条日志发我。
