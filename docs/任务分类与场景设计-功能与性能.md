# 任务分类与场景设计（功能基础质量 / 性能测试）

本文档说明：在「功能基础质量测试」下增加**具体场景**（启动应用程序、登录、搜索等），并按 **平台（Android/iOS/鸿蒙）** 走不同执行路径；**性能测试**同理拆成不同子类。这样创建任务时能明确「这个任务具体要做什么」。

---

## 一、设计目标

- **功能基础质量测试**：不再只是一个笼统类型，而是包含多类**具体场景**，例如：
  - 启动应用程序（按 Android / iOS / 鸿蒙 走不同实现）
  - 登录
  - 搜索
  - 后续可扩展：设置、支付、分享等
- **性能测试**：拆成多种**性能子类**，例如：启动耗时、内存、帧率、流量等，每种也可按平台区分。
- 创建任务时：用户选择「任务类型」+「具体场景/子类」+「平台」，系统能明确执行哪条逻辑，任务名称/列表也能体现「在做什么」。

---

## 二、是否可行

**结论：可行，且与当前架构兼容。**

- 现有已有「任务类型」`taskType` 和「场景」`ScenarioDefinition`（如 login_android、login_ios），创建任务时可选场景或填 platform。
- 扩展方式：在现有「类型 + 平台」基础上，增加一层**场景/子类**（如 启动应用程序、登录、搜索），执行时按「类型 + 场景 + 平台」三重分支即可。

---

## 三、推荐方案：任务增加「场景键」+ 扩展场景列表

### 3.1 数据模型

- **Task 表**增加字段（二选一即可）：
  - **方案 A（推荐）**：`scenario_key`（VARCHAR），例如：`launch_app`、`login`、`search`。  
    含义：在「功能基础质量测试」下，具体做哪一类功能（启动/登录/搜索）；性能测试下可表示「启动耗时」「内存」等。
  - **方案 B**：继续用现有「场景 ID」思路，把 `scenario_id` 存到 Task（若当前没有则新增），一个 scenario_id 对应「一件事 + 一个平台」，例如 `launch_app_android`、`login_ios`。

- **平台**：已有 `platform`（Android/iOS/HarmonyOS），执行时根据 **taskType + scenario_key（或 scenario_id）+ platform** 走不同代码路径。

### 3.2 功能基础质量测试：场景与平台

| 场景键 scenario_key | 含义           | Android | iOS | 鸿蒙 |
|---------------------|----------------|---------|-----|------|
| launch_app          | 启动应用程序   | ✓       | ✓   | ✓    |
| login               | 登录           | ✓       | ✓   | 可扩展 |
| search              | 搜索           | ✓       | ✓   | 可扩展 |

- 执行层：根据 `taskType == FUNCTIONAL_QUALITY_TEST` + `scenario_key` + `platform` 分支，例如：
  - `launch_app` + Android → 走 Android 启动检测（如冷启动耗时、是否闪退等）；
  - `launch_app` + iOS → 走 iOS 启动逻辑；
  - `launch_app` + HarmonyOS → 走鸿蒙启动逻辑；
  - `login` + Android/iOS → 沿用或扩展现有登录测试（如 LoginTestService）；
  - `search` → 后续实现搜索场景的步骤与校验。

### 3.3 性能测试：子类与平台

- 性能测试类型（现有如 `PERFORMANCE_BASELINE_TEST`、`SCENARIO_PERFORMANCE_TEST` 等）下，同样用 **scenario_key** 区分子类，例如：
  - `startup_time`：启动耗时
  - `memory`：内存
  - `fps`：帧率
  - `network`：流量
- 执行时：`taskType`（性能类）+ `scenario_key` + `platform` 决定跑哪一套性能采集与断言。

### 3.4 前端展示与创建任务

- **创建任务**：
  - 先选「任务类型」（如 功能基础质量测试 / 性能基础质量测试）；
  - 再选「测试场景/子类」（如 启动应用程序、登录、搜索 或 启动耗时、内存）；
  - 再选 平台、设备、应用（按需）。
- **任务列表/详情**：展示「任务类型 + 场景名称 + 平台」，例如：「功能基础质量测试 - 启动应用程序 - Android」，用户一眼能看出任务在做什么。

---

## 四、与现有代码的衔接

- **FunctionalTestScenarioService**：当前已有一批 `ScenarioDefinition`（如 login_android、login_ios）。可扩展为更多场景，例如：
  - `launch_app_android` / `launch_app_ios` / `launch_app_harmonyos`
  - `login_android` / `login_ios`
  - `search_android` / `search_ios`
  每个 definition 带：id、name、platform、taskType、**scenarioKey**（如 launch_app、login、search）、description。
- **Task**：创建时写入 `task_type` + `scenario_key`（或 scenario_id）+ `platform`（已有）。
- **TaskService.executeTestTask**：在 `FUNCTIONAL_QUALITY_TEST` 分支内，先看 `task.getScenarioKey()`（或从 scenarioId 解析），再按 scenario_key + platform 调用不同执行器（如 LaunchAppTestService、LoginTestService、SearchTestService 等）；性能测试同理在性能分支里按 scenario_key + platform 分发。

---

## 五、实施步骤建议

1. **表结构**：Task 表增加 `scenario_key`（或统一用 scenario_id），并做一次数据迁移（旧任务可置空或默认如 `login`）。
2. **场景配置**：扩展 FunctionalTestScenarioService（或新建通用 ScenarioRegistry），注册「功能」与「性能」的各类场景，包含 scenario_key、platform、taskType、展示名。
3. **执行分支**：在 TaskService / TestScriptExecutor 中，按 taskType + scenario_key + platform 分支，实现或接入「启动应用程序」「登录」「搜索」等具体逻辑（Android/iOS/鸿蒙分别实现）。
4. **API**：创建任务接口支持传入 scenario_key（或 scenario_id）；列表/详情返回场景信息，便于前端展示「具体做什么」。
5. **前端**：创建任务时增加「测试场景/子类」选择；任务列表与详情展示「类型 - 场景 - 平台」。

这样即可做到：**创建了任务就知道具体要做哪一类测试、在哪个平台上执行**，功能与性能都按「分类 + 场景 + 平台」清晰扩展。
