# 性能基础质量测试 - 前端对接说明

本文档说明前端为支持「性能基础质量测试」及「应用内遍历测试」报告展示需要做的调整与数据获取方式。

**baseUrl 示例：** `http://localhost:3000/api`（以实际部署为准，一般含 `/api`）

**联调文档**：需与后端联调、自测时，请同时参考 **`性能基础质量测试-联调文档.md`**（含请求/响应示例、联调步骤、自测检查点、常见问题）。

---

## 前端需要做哪些调整（摘要）

1. **创建任务**：用 `POST /api/tasks/test`，body 含 `taskType: "PERFORMANCE_BASELINE_TEST"`、`platform`、`deviceId`、`appId`，可选 `config.traversalMinutes`（执行时长）。
2. **任务列表**：用 `GET /api/tasks` 拉取性能任务（可传 `taskType=PERFORMANCE_BASELINE_TEST`），不要仅用 `/functional-test/tasks`。
3. **测试场景列**：直接展示接口返回的 `scenarioName`。
4. **运行后状态**：点击运行后**轮询** `GET /api/tasks/{taskId}`（3～5 秒一次），直到 `status` 非 `RUNNING`，再刷新。
5. **性能报告**：仅通过 `GET .../functional-test/tasks/{id}/performance-report` 取 JSON 渲染，不用 iframe/静态路径。
6. **整体评估 / 遍历统计 / 资源数据**：用报告 JSON 的 `conclusion`、`issueSummary`、`resourceSummary`、`resourceSamples`、`screenshotTimeline` 等渲染。
7. **操作详情表格**：用 `operations` 数组，列对应操作类型、操作前/后图（URL 用 `.../performance-screenshots/{screenshotBeforeIndex|screenshotAfterIndex}`）、响应时延、完成时延、黑白块、维测数据。
8. **任务详情/概览**：继续用 `GET .../functional-test/tasks/{id}/overview`，执行日志用 `executionLog`。

---

## 一、创建性能测试任务

- **接口**：`POST {baseUrl}/tasks/test`  
  **不要**使用 `POST {baseUrl}/functional-test/tasks`（该接口不创建性能任务）。
- **请求体示例**：
  ```json
  {
    "taskType": "PERFORMANCE_BASELINE_TEST",
    "platform": "ANDROID",
    "deviceId": "设备ID",
    "appId": "应用ID",
    "config": "{\"traversalMinutes\": 5}"
  }
  ```
- **说明**：
  - `taskType` 必填，固定为 `PERFORMANCE_BASELINE_TEST`。
  - 仅支持 **Android**，设备与应用需为已安装的 Android 应用。
  - **执行时长**：通过 `config.traversalMinutes` 传入（1～60 分钟），不传则使用后端默认（如 2 分钟）。前端建议在创建表单中提供「执行时长」选项（如 2/5/10/30/60 分钟）。

---

## 二、任务列表与状态

- **性能任务列表**：使用 **`GET {baseUrl}/tasks`**，可传 `taskType=PERFORMANCE_BASELINE_TEST` 筛选。  
  **注意**：`GET {baseUrl}/functional-test/tasks` **不包含**性能任务，不要仅依赖该接口。
- **任务状态**：来自接口返回的 **`task.status`**，取值：`PENDING`、`RUNNING`、`COMPLETED`、`FAILED`、`STOPPED`。前端可映射为「待执行」「运行中」「已完成」「失败」「已停止」。
- **测试场景列**：列表中的「测试场景」使用接口返回的 **`scenarioName`**（或任务详情的同名字段）。后端会为性能任务填充如「性能基础质量测试(Android)」，无需前端再传。

---

## 三、运行任务与状态轮询（必做）

- **运行**：`POST {baseUrl}/tasks/{taskId}/run`。调用成功后后端**立即**将任务状态置为 **RUNNING**，测试在后台执行（可能 5～60 分钟）。
- **为何列表显示「已停止」**：若点击运行后**不重新请求**任务状态，页面会一直显示上一次的旧状态。必须通过**轮询**获取最新状态。
- **推荐做法**：
  1. 调用 `POST .../tasks/{taskId}/run` 成功后，开始**轮询** `GET {baseUrl}/tasks/{taskId}`，建议每 **3～5 秒** 一次。
  2. 当 `status === 'RUNNING'` 时，展示「运行中」；当变为 `COMPLETED` / `FAILED` / `STOPPED` 时停止轮询，并刷新列表或详情。

---

## 四、性能报告数据来源

- **接口**：`GET {baseUrl}/functional-test/tasks/{id}/performance-report`  
  - 返回 **200**：body 为**最新一次执行**的完整结果 JSON（结论、遍历统计、资源数据、问题统计、操作明细等）。
  - 返回 **404**：任务不存在、非性能任务、或尚未有执行结果。
- **不要**把性能报告当作静态路径（如 iframe src）请求，必须用上述接口取 JSON，再由前端渲染。

---

## 五、报告内容与字段映射

拿到 `performance-report` 的 JSON 后，可按以下结构渲染。

### 5.1 整体评估

| 展示项 | 数据来源 |
|--------|----------|
| 测试结论 | `conclusion` |
| 问题总数 / 饼图 | `issueSummary.totalIssueCount`；分类数量见 `issueSummary.responseDelayCount`、`completionDelayCount`、`stutterCount`、`blackWhiteBlockCount`、`avCount` |
| 按操作类型的问题统计表 | `issueSummary.byOperationType`，键为「启动操作」「滑动操作」「点击操作」「观看视频」，值为各计数字段 |

### 5.2 遍历统计

| 展示项 | 数据来源 |
|--------|----------|
| 遍历时长、启动/点击/滑动次数 | `traversalDurationMinutes`、`launchCount`、`clickCount`、`swipeCount` |
| 截图时间轴 | `screenshotTimeline`（每项含 `index`、`timestampMs`）；图片 URL 见下文「截图」 |

### 5.3 资源数据（CPU、内存、网络、温度）

| 展示项 | 数据来源 |
|--------|----------|
| 汇总（峰值/最小/平均） | `resourceSummary.cpuApp`、`resourceSummary.memoryPss`、`resourceSummary.networkRxBytes`、`resourceSummary.networkTxBytes`、`resourceSummary.temperature`，每项含 `peak`、`min`、`avg` |
| 曲线数据 | `resourceSamples` 数组，每项含 `timestampMs`、`cpuPercent`、`memoryPssKb`、`networkRxBytes`、`networkTxBytes`、`temperatureTenthsC`（温度 0.1℃） |

### 5.4 操作详情（应用内遍历测试表格）

表格每行对应 **`operations`** 数组中的一条；列与数据来源如下。

| 列名 | 数据来源 | 展示说明 |
|------|----------|----------|
| **操作类型** | `operations[i].index` + `operations[i].actionLabel`（或再结合 `type`） | 示例：`1.点击-'频道列表'`、`2.滑动-向上滑`。`type` 为 `launch`/`click`/`swipe`，`actionLabel` 为「向上滑」「点击-\"关注\"」等，可拼成「序号. + actionLabel」。 |
| **操作前** | `operations[i].screenshotBeforeIndex` | 有值时，图片地址：`GET {baseUrl}/functional-test/tasks/{任务id}/performance-screenshots/{screenshotBeforeIndex}`，用 `<img src="...">` 展示；为 null 时显示占位或「无」。 |
| **操作后** | `operations[i].screenshotAfterIndex` | 同上，将 `screenshotAfterIndex` 代入 URL 中的 `{index}`。 |
| **响应时延** | `operations[i].responseDelayMs` | 单位 ms，直接展示如「65ms」；为 null 时显示「-」。 |
| **完成时延** | `operations[i].completionDelayMs` | 单位 ms，展示如「2325ms」；为 null 时显示「-」。 |
| **卡顿/音视频/黑白块** | `operations[i].whiteScreenMs`；卡顿/音视频细项当前后端为 0 | 白屏时长：`whiteScreenMs` 有值则展示「白屏时长: Xms」，否则「白屏时长: 0ms」。卡顿率/丢帧等后端暂未采集，可显示「-」或 0。 |
| **维测数据** | `operations[i].cpuAvgDuringStep`、`operations[i].memoryPssKbDuringStep` | 「打开」或悬浮可展示该步 CPU 均值、内存 PSS 等；数据均在当前 `operations[i]` 中，无需额外接口。 |

- **行顺序**：与 `operations` 数组顺序一致；`operations[i].index` 为步骤序号（从 0 起），可用于表格行号或标题。

### 5.5 截图

- **遍历条 / 时间轴截图**：第 `i` 张图（`i` 从 0 起，且 `i < screenshotCount`）的地址为：  
  **`GET {baseUrl}/functional-test/tasks/{任务id}/performance-screenshots/{i}`**  
  可直接用作 `<img src="...">`（需带 cookie 或后端允许跨域时使用）。
- **操作详情中的「操作前」「操作后」**：使用该行对应的 `screenshotBeforeIndex`、`screenshotAfterIndex` 代入上式中的 `{i}` 即可。

若操作详情没有截图，请确认：① 后端已开启按间隔截图（`performance.screenshot-interval-seconds > 0`）；② 前端确实用上述 URL 拼了 `screenshotBeforeIndex`/`screenshotAfterIndex`。

## 七、接口汇总

| 用途 | 方法与路径 |
|------|------------|
| 创建性能任务 | `POST {baseUrl}/tasks/test` |
| 任务列表（含性能） | `GET {baseUrl}/tasks`（可传 `taskType`、`platform`、`status` 等） |
| 单任务状态/详情 | `GET {baseUrl}/tasks/{id}` |
| 运行任务 | `POST {baseUrl}/tasks/{taskId}/run` |
| 任务概览（含执行日志） | `GET {baseUrl}/functional-test/tasks/{id}/overview` |
| 性能报告 JSON | `GET {baseUrl}/functional-test/tasks/{id}/performance-report` |
| 某张截图 | `GET {baseUrl}/functional-test/tasks/{id}/performance-screenshots/{index}`（index 为数字，从 0 起） |
