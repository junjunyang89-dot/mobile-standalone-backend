# 冷启动耗时 + 基线取中位数

> 先说清楚:**性能测试这块不是从零开始,而且你要的「接入流程编排」已经是现成的。**
> `PerformanceTestService.runScenarioPerformanceTest` 就是「`config.flowId` → 跑 `UiFlowExecutor` → 同步采样」。

---

## 一、补了什么

### 1. 冷启动耗时 —— 一个存在于对比表、却从没被采集过的指标

`MetricComparator` 从一开始就认识 `coldStartMs`:有中文名「冷启动耗时」、有单位 ms、
`MetricDirection` 也判对了方向(越小越好)。

**但没有任何采集器产生过它。** `ResourceSummary` 里只有 CPU / 内存 / 流量 / 温度 / FPS。

也就是说:**最贴近用户感受的那个指标,报告里一次都没出现过。**

现在补上了。Android 走 `adb shell am start -W -S -n <包名>/<启动页>`,
你们的启动页我从 Manifest 里确认过是 `.ui.activity.launcher.LauncherActivity`。
系统自己算好的,不用埋点、不用改源码。

**默认跑 5 轮取中位数**,`config.coldStartRounds: 0` 关掉。

### 2. 基线从「最近一次」改成「中位数」

`MetricBaselineService.latestOf` 原来取的是那个版本**最后一次**的值。

原注释给的理由是「平均会把一次异常采样摊进去,结论变糊」——**这个理由是对的**,
但中位数同时解决了两件事:它不受离群值影响,**也不取决于哪一轮碰巧跑在最后**。

为什么非改不可:告警阈值是 15%,而 CPU、冷启动的单次波动本来就能到这个量级。
靠单次采样去比,**这套报告会经常报假劣化**——
而注释里自己写了「报到第三次就没人看了」,单轮采样正在让这条防线失效。

跑过一次时中位数就等于那一次,所以不会因为改成中位数而少掉任何数据。

## 二、几个刻意的选择

### 取 TotalTime,不取 ThisTime

你们的包有 `LauncherActivity` 闪屏再进主页。`ThisTime` 只算链路上**最后一个** Activity,
会把闪屏那段漏掉——数字好看,但不是用户等的那段时间。

### 「切到前台」必须识别出来并作废那一轮

如果 force-stop 没生效,`am start` 只是把应用切到前台,`TotalTime` 只有几十毫秒。
混进中位数会把整体拉低,报出「启动变快了」——

**而假的好消息没有人会去核。** 它会一直留在报告里。

### 第 1 轮当预热丢掉

force-stop 之后页缓存还在,但 ART 的 JIT 缓存、各种懒加载单例的状态跟后面几轮不一样,
第 1 轮系统性偏高。轮数少于 3 时不丢——丢了就没样本了。

### 冷启动必须在采样器起来**之前**测完

它要反复 force-stop + 重启五次。如果和资源采样重叠,这五次启动的 CPU 尖峰会被算进
整条曲线的均值和峰值——于是「开了冷启动测量」的那次 CPU 看着就是比没开的高,
而两次跑的明明是同一个包。基线一比,报一条不存在的劣化。

### 流程里有 HOT_START 就跳过

流程测的是热启动,先把进程杀五遍会破坏它的前置状态。
这种冲突不报错,只会让那条流程的数据**悄悄变成另一回事**。

### iOS / 鸿蒙明确返回「不支持」,不编数

没有 `am start -W` 的等价物。**一个缺失的指标是显眼的,一个错的指标会被当真。**

## 三、这个数字量到哪为止(重要)

`TotalTime` 量到**第一帧画出来**,不是「首页数据加载完、能用了」。

一个先画骨架屏再请求数据的版本,在这个指标上会显得很快。
要量「真正能用」只能在代码里埋点——你们有三端源码,这是能做的,但要 APP 组配合。
**先别把这个数字当成那个数字。**

---

## 四、必须说死的前提

**模拟器上测性能等于零。**

你现在主力是模拟器——我前几天刚把它从 1 核 2G 调到 4 核 4G,这恰恰说明它的性能表现
取决于宿主机当时的状态,跟被测应用没多大关系。

- 性能数据必须**真机**
- 必须**同一台真机**。机型一换,CPU、FPS 完全不是一个量级(`MetricBaselineService` 已经按机型分开存了,这条是对的)
- 测的时候别在同一台机器上干别的

代码里加了一条:各轮波动超过 30% 时会在日志里明确告警,说这次数字参考价值有限。

## 六、还没做的(按优先级)

### 1. 鸿蒙会静默产出假数据 —— 这是 bug,不是缺功能

- `PerformanceCollectorResolver.resolve()` 只分 iOS / 非 iOS,**鸿蒙走 Android 分支**
- `AdbPerformanceCollector.available()` **只检查 deviceId 和包名非空**,对鸿蒙设备返回 true
- 于是对一台 hdc 设备发 adb 命令 → 采不到 → null 或 0

**0 会进基线。** 下个版本再测,`MetricComparator` 会报
「上个版本是 0,这次是 X,**新出现的**」——一条完全虚构的劣化。

`HdcClient` 已经有了(`HarmonyOSDriver` 在用),补一个鸿蒙采集器是有路的。
**在补之前,至少该让它采不到就明确报不可用,而不是写 0。**

### 2. 源码埋点

三端源码在手,最大的价值不是能自己打包,是能拿到**精确的启动/渲染完成时间**。
但这要 APP 组配合,属于第二步。

## 七、前端要改吗

报告 DTO 多两个字段:

| 字段 | 说明 |
| --- | --- |
| `coldStartMs` | 中位数,毫秒。null = 没测或不支持 |
| `coldStartDetail` | `{supported, medianMs, samples[], rejected[], notes[]}` |

**`samples` 建议展示出来。** 光给一个中位数,人没法判断这次稳不稳;
把 5 轮原始值摆出来,一眼能看出是 1800/1820/1810 还是 1800/2400/3100。

`rejected` 里是被丢掉的轮次和原因,排查用。

任务 config 多两个可选项:`coldStartRounds`(默认 5,0 = 关)、`launchActivity`(不传就现场 resolve)。

**后端要重启。** 不用跑 SQL。
