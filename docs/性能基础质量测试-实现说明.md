# 性能基础质量测试 - 实现说明

## 一、功能概述

性能基础质量测试在指定时长内对应用进行**自动遍历**（启动、点击、滑动），并**采集资源数据**（CPU、内存），产出：

- **执行日志**（`execution_log`）：步骤级文案，供前端「执行日志」展示。
- **结果数据**（`result_data`）：JSON 结构，包含遍历统计、资源汇总、问题统计、采样序列与操作明细，供前端「整体评估」「遍历统计」「资源数据」「操作详情」等使用。

当前**仅支持 Android**，依赖 **adb**；建议开启 **Appium**（`appium.enabled=true`）以便使用 WebDriver 获取窗口尺寸并执行滑动/点击。

---

## 二、配置项（application.yml）

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| `performance.traversal-minutes` | 遍历时长（分钟） | 2 |
| `performance.sample-interval-seconds` | 资源采样间隔（秒） | 3 |
| `performance.response-delay-threshold-ms` | 响应时延阈值（毫秒），超过计为「响应时延」问题 | 3000 |
| `performance.completion-delay-threshold-ms` | 完成时延阈值（毫秒） | 5000 |
| `performance.back-key-interval` | 每 N 次操作按一次**返回键**，便于从播放页/详情页退回继续遍历；0=不按 | 5 |
| `performance.screenshot-interval-seconds` | 遍历期间**每隔 N 秒截一张图**（后台线程，尽量不阻塞点击/滑动）；0=不截 | 1 |

## 三、执行流程

1. 校验设备与应用（仅 Android、包名非空）。
2. **冷启动**：先执行 `adb shell am force-stop <包名>` 强制结束应用进程，等待约 0.8 秒，再启动应用。**每次执行性能测试都会重新启动应用，不在上次运行基础上继续**，保证数据可复现、结果可对比。
3. 使用 `PlatformDriver.launchApp` 启动应用，等待约 3 秒。
4. 获取窗口尺寸：若已启用 Appium 则从 WebDriver 取，否则通过 `adb shell wm size` 解析。
5. 启动**后台采样线程**：按 `sample-interval-seconds` 间隔采集 **CPU**（dumpsys cpuinfo）、**内存**（dumpsys meminfo）、**网络**（/proc/net/dev 整机 rx/tx 字节）、**温度**（dumpsys battery），写入 `resourceSamples` 与 `resourceSummary`，供「资源数据」CPU/内存/网络/温度曲线与汇总展示。
6. **主循环**（至达到 `traversal-minutes`）：
   - 交替执行「滑动」与「点击」（中心点或上下左右滑动）。
   - 记录每步开始/结束时间，计算响应时延；步骤结束后采样一次 CPU/内存，写入 `operations`。
   - **周期性按返回键**：若配置 `back-key-interval > 0`，则每 N 次操作后发送一次 `KEYCODE_BACK`（adb），用于从播放页、全屏、详情页退回，避免长时间卡在同一页，便于继续遍历其他页面。
   - **按间隔截屏**：若配置 `screenshot-interval-seconds > 0`，在**独立后台线程**中每隔 N 秒调用 `takeScreenshot`，保存到 `/tmp/screenshots/perf_{taskId}/img_0.png, img_1.png, ...`，并将 `screenshotCount`、`screenshotTimeline`（index + timestampMs）写入结果。与主遍历**共用同一 driver**，截图时可能产生短暂串行（通常 0.3～1 秒/张），对业务影响较小；若设备较慢可将间隔调为 2～3 秒。
7. 停止采样与截图线程，汇总：
   - `resourceSummary`：**CPU、内存、网络、温度** 的 peak、min、avg（资源数据四类）。
   - `issueSummary`：响应时延、完成时延、黑白块、卡顿/音视频，按操作类型统计。
   - 每条 `operations` 关联**操作前/操作后**截图索引（`screenshotBeforeIndex`/`screenshotAfterIndex`）、**加载完成时延**（`completionDelayMs`）、**白屏时长**（`whiteScreenMs`），供「操作详情」表格展示。
8. 将 `PerformanceTestResultDto` 序列化为 JSON 写入 `task_executions.result_data`，执行日志写入 `execution_log`。

## 四、result_data JSON 结构（PerformanceTestResultDto）

前端可据此渲染「整体评估」「遍历统计」「资源数据」「操作详情」。

| 字段 | 类型 | 说明 |
|------|------|------|
| `traversalDurationMinutes` | int | 遍历时长（分钟） |
| `totalOperations` | int | 总操作次数 |
| `launchCount` | int | 启动次数 |
| `clickCount` | int | 点击次数 |
| `swipeCount` | int | 滑动次数 |
| `conclusion` | string | 测试结论文案 |
| `resourceSummary` | object | `cpuApp`、`memoryPss`、`networkRxBytes`、`networkTxBytes`、`temperature`：各含 `peak`、`min`、`avg`（温度单位为 ℃） |
| `issueSummary` | object | `responseDelayCount`、`completionDelayCount`、`stutterCount`、`blackWhiteBlockCount`、`avCount`、`totalIssueCount`、**`byOperationType`**（见下） |
| `resourceSamples` | array | `{ timestampMs, cpuPercent, memoryPssKb, networkRxBytes, networkTxBytes, temperatureTenthsC }`，用于画 CPU/内存/网络/温度曲线 |
| `operations` | array | 操作明细：`index, type, startTimeMs, endTimeMs, responseDelayMs, completionDelayMs`（加载完成时延）, `cpuAvgDuringStep, memoryPssKbDuringStep, pageName, actionLabel, screenshotBeforeIndex, screenshotAfterIndex, whiteScreenMs`。**screenshotBeforeIndex/screenshotAfterIndex** 对应「操作前」「操作后」截图（请求 `GET .../performance-screenshots/{index}`）；**whiteScreenMs** 为本步白屏/黑屏时长（ms）；**completionDelayMs** 即「加载完成时延」。 |
| `screenshotCount` | number | 遍历期间截图的张数（0 或未开启时为 null） |
| `screenshotTimeline` | array | `{ index, timestampMs }` 数组，供前端时间轴展示；图片通过 `GET .../performance-screenshots/{index}` 获取 |

**`issueSummary.byOperationType`** 为**对象（Map）**，与前端「按操作类型的问题统计表」一致：键为 **"启动操作"、"滑动操作"、"点击操作"、"观看视频"**，值为 `{ responseDelayCount?, completionDelayCount?, stutterCount?, avCount?, blackWhiteBlockCount? }`。示例：

```json
"byOperationType": {
  "启动操作": { "responseDelayCount": 0, "completionDelayCount": 10, "stutterCount": 0, "avCount": 0, "blackWhiteBlockCount": 0 },
  "滑动操作": { "responseDelayCount": 2, "completionDelayCount": 0, "stutterCount": 2, "avCount": 0, "blackWhiteBlockCount": 2 },
  "点击操作": { "responseDelayCount": 5, "completionDelayCount": 19, "stutterCount": 0, "avCount": 0, "blackWhiteBlockCount": 0 },
  "观看视频": { "responseDelayCount": 0, "completionDelayCount": 0, "stutterCount": 0, "avCount": 0, "blackWhiteBlockCount": 0 }
}
```

- **完成时延**：本步 `endTimeMs` 到下一步 `startTimeMs` 的间隔，超过 `completion-delay-threshold-ms` 计为一次问题。
- **黑白块**：对按间隔保存的截图做像素采样，若 80% 以上为极黑或极白则计为一次，并按截图时间归因到对应操作类型（启动/点击/滑动）。
- **卡顿**、**音视频**：当前为 0；卡顿需后续接入帧率/掉帧数据，音视频为预留。

## 五、前端是否需要做调整

### 必须做的（若要在前端创建并查看性能测试）

| 项 | 说明 |
|----|------|
| **创建任务** | 需要支持「性能基础质量测试」这一任务类型。创建时调用 **`POST /api/tasks/test`**（不要用 `POST /api/functional-test/tasks`，该接口仅创建功能体验测试），请求体传 **`taskType: "PERFORMANCE_BASELINE_TEST"`**，以及 `platform`、`deviceId`、`appId` 等。设备需选 **Android**，应用选已安装包。 |
| **任务列表** | 若列表按任务类型展示，需能显示「性能基础质量测试」（后端返回 `taskType: "PERFORMANCE_BASELINE_TEST"`，前端可映射为「性能基础质量测试」）。 |
| **任务详情 / 概览** | **`GET /api/functional-test/tasks/{id}/overview`** 已支持性能任务，与功能测试、兼容性测试共用同一套结构：`summarySectionTitle` 为「性能测试结果」，`testResultItems`、`executionLog` 等字段一致。**现有详情页若已按 overview 通用渲染，无需改结构**，只需保证性能任务也走该接口（不要因任务类型而排除或 404）。 |

### 任务状态与前端轮询（解决「任务在跑但页面显示已停止」）

- **状态何时更新**：  
  - 用户点击「运行」→ 后端 **立即** 将 `task.status` 置为 **RUNNING** 并落库，然后返回 200；实际测试在**后台异步**执行（如 10 分钟性能压测）。  
  - 测试**正常结束**后，后端将状态置为 **COMPLETED**；异常结束置为 **FAILED**。  
  - 只有用户点击「停止」时，才会置为 **STOPPED**。  

- **为什么列表会显示「已停止」**：  
  列表/详情中的「状态」来自接口返回的 **task.status**。若前端在点击「运行」后**不重新请求**列表或任务详情，页面会一直显示**上一次**的数据（例如上次执行结束后的 STOPPED/COMPLETED），看起来就像「任务在跑但显示已停止」。  

- **长压测如何拿到最新状态**：  
  - 在调用 **`POST /api/tasks/{taskId}/run`** 成功后，建议**轮询** **`GET /api/tasks/{taskId}`**（通用任务接口，性能任务也用此接口查状态），每 **3～5 秒** 请求一次。  
  - 当 `status === 'RUNNING'` 时，前端展示「运行中」；当变为 `COMPLETED` / `FAILED` / `STOPPED` 时停止轮询，并刷新列表或详情。  
  - 性能任务列表若来自 **`GET /api/tasks`**（支持按 taskType 筛选），刷新该列表也会得到最新 status；**不要**仅依赖 **`GET /api/functional-test/tasks`**，该接口不包含性能任务。

### 可不改 / 与现有一致

- **运行任务**：`POST /api/tasks/{taskId}/run`，与现有任务一致。
- **执行日志**：overview 里已带 `executionLog`，与功能测试相同，用「时间 + Level + 消息」展示即可。

### 性能报告数据从哪来（解决「性能报告没有数据」）

- **不要**把性能报告当成静态资源路径（如 `tasks/{id}/executions/latest/performance-report` 作为 iframe/src），否则会 404。
- **正确做法**：调用接口 **`GET {baseUrl}/functional-test/tasks/{id}/performance-report`**。  
  - 返回 200：body 为**最新一次执行**的 `result_data` 解析后的 JSON 对象（结论、遍历统计、资源汇总、问题统计、resourceSamples、operations 等），前端用此数据渲染「性能报告」区块（表格、曲线等）。  
  - 返回 404：任务不存在、非性能任务、或尚未有执行结果。

### 执行时长可配置（解决「没有选择执行时间」）

- 创建性能测试任务时，在请求体 **config** 中传入执行时长（分钟）：**`config: "{\"traversalMinutes\": 5}"`**（示例为 5 分钟）。  
- 调用 **`POST /api/tasks/test`** 创建任务时，body 示例：`{ "taskType": "PERFORMANCE_BASELINE_TEST", "platform": "ANDROID", "deviceId": "xxx", "appId": "yyy", "config": "{\"traversalMinutes\": 5}" }`。  
- 后端会按 1～60 分钟限制；未传或无效则使用服务端配置默认值（如 2 分钟）。  
- **前端建议**：在创建性能任务的表单中增加「执行时长」下拉或输入（如 2 / 5 / 10 / 30 / 60 分钟），提交时把选中值写入 `config.traversalMinutes`。

### 遍历截图（每秒一张，是否会卡住业务）

- **能力**：遍历期间可按配置**每隔 N 秒截一张图**（默认 1 秒），在**独立后台线程**中执行，主线程只做点击/滑动，尽量不阻塞。
- **是否卡住**：截图与主遍历**共用同一 Appium/驱动**，设备端通常一次只处理一个命令，因此截图执行时（约 0.3～1 秒/张）可能与一次点击/滑动产生短暂串行，整体上**不会明显卡住业务**；若设备或网络较慢，可将 `performance.screenshot-interval-seconds` 设为 2 或 3 降低频率。
- **结果**：截图保存到 `/tmp/screenshots/perf_{taskId}/img_0.png, img_1.png, ...`，结果 JSON 中带 `screenshotCount`、`screenshotTimeline`（每条的 `index`、`timestampMs`）。前端展示「遍历条」时，用 **`GET {baseUrl}/functional-test/tasks/{id}/performance-screenshots/{index}`** 作为第 index 张截图的图片地址（0 起）；`index < screenshotCount`。

### 「操作详情」数据如何获取（按文档对接即可）

「操作详情」表格的数据全部来自性能报告 JSON 中的 **`operations`** 数组；报告本身通过 **`GET {baseUrl}/functional-test/tasks/{id}/performance-report`** 获取。

| 表格列 | 数据来源 | 说明 |
|--------|----------|------|
| **操作类型** | `operations[i].type` + `operations[i].actionLabel` | `type` 为 `launch` / `click` / `swipe`，可映射为「启动应用」「点击」「滑动」；`actionLabel` 为具体描述（如「向上滑」「点击-\"关注\"」），可并排或作为副标题展示。 |
| **操作前** | `operations[i].screenshotBeforeIndex` | 有值时，图片 URL：**`GET {baseUrl}/functional-test/tasks/{id}/performance-screenshots/{screenshotBeforeIndex}`**；无值（null）可显示占位或「无」。 |
| **操作后** | `operations[i].screenshotAfterIndex` | 同上，将 `screenshotAfterIndex` 代入上述 URL 中的 `{index}`。 |
| **加载完成时延** | `operations[i].completionDelayMs` | 单位毫秒，直接展示如「2325ms」；为 null 时表示最后一步或未计算，可显示「-」或 0。 |
| **黑白块** | `operations[i].whiteScreenMs` | 本步白屏/黑屏时长（ms），展示如「白屏时长: 0ms」或「白屏时长: 120ms」；为 null 时展示「白屏时长: 0ms」。 |
| **维测数据** | 同一条 `operations[i]` 的 `cpuAvgDuringStep`、`memoryPssKbDuringStep` 等 | 「打开」后可展示该步的 CPU 均值、内存 PSS 等；数据均在当前 `operations[i]` 对象中，无需额外接口。 |

- **数据来源接口**：先调 **`GET .../performance-report`** 拿到整份报告（含 `operations`），再按上表从 `operations` 中取字段；截图列用同一任务的 **`GET .../performance-screenshots/{index}`** 作为图片地址。
- **行顺序**：与 `operations` 数组顺序一致，`index` 为步骤序号（0 起），可用于「1.启动应用」「2.启动应用」等标题。

**为什么「操作详情」没有截图？** 请逐项核对：
1. **后端必须开启按间隔截图**：配置项 **`performance.screenshot-interval-seconds`** 必须 **> 0**（如 1）。为 0 时不会截屏，`screenshotTimeline` 为空，`operations` 里 `screenshotBeforeIndex`/`screenshotAfterIndex` 全为 null。
2. **前端必须用索引拼图片 URL**：「操作前」「操作后」列应使用 `operations[i].screenshotBeforeIndex`、`operations[i].screenshotAfterIndex` 拼出图片地址：**`GET {baseUrl}/functional-test/tasks/{任务id}/performance-screenshots/{index}`**（注意是 `/api/functional-test/tasks/...`，且 `{index}` 为数字）。用 `<img src="上述URL">` 或等价方式展示；为 null 时显示占位或「无」。
3. **任务 ID 与最新执行**：截图接口按**任务 id** 读 `/tmp/screenshots/perf_{任务id}/img_{index}.png`，且只认**最新一次执行**的 `screenshotCount`；若刚跑完性能测试，请确保前端请求的是该任务的 id，且报告数据来自 `GET .../performance-report`（同一任务）。

### 可选增强（做「整体评估 / 遍历统计 / 资源曲线」等完整报告时）

- 性能报告区块：用 **`GET /functional-test/tasks/{id}/performance-report`** 取回 JSON 后，按 `PerformanceTestResultDto` 解析并展示：测试结论、遍历统计、资源汇总、问题统计表、`resourceSamples` 曲线、**`operations` 操作详情表**（按上表列映射）、以及 `screenshotCount`/`screenshotTimeline` 对应的截图时间轴（图片 URL：`.../performance-screenshots/0`～`.../performance-screenshots/(screenshotCount-1)`）。

## 六、接口与前端（汇总）

- **创建任务**：`POST /api/tasks/test`，body 含 `taskType: "PERFORMANCE_BASELINE_TEST"`，设备选 Android。
- **运行任务**：`POST /api/tasks/{taskId}/run`。调用成功后后端立即将任务状态置为 RUNNING，测试在后台执行。
- **任务状态（长压测必读）**：列表/详情的「状态」= `task.status`（PENDING/RUNNING/COMPLETED/FAILED/STOPPED）。长压测期间前端需**轮询** `GET /api/tasks/{id}` 每 3～5 秒获取最新状态，否则会一直显示旧状态（如「已停止」）。
- **任务列表**：性能任务请用 **`GET /api/tasks`**（可传 `taskType=PERFORMANCE_BASELINE_TEST`）；`GET /api/functional-test/tasks` 不包含性能任务。
- **任务详情 / 概览**：`GET /api/functional-test/tasks/{id}/overview`，已支持性能任务；完整性能数据在最新执行的 `result_data`（任务详情接口中为 `resultData`）中。
- **执行日志**：使用 overview 或任务详情的 `executionLog` 展示。
- **遍历截图**：性能报告 JSON 中的 `screenshotCount`、`screenshotTimeline`；第 i 张图 URL 为 `GET .../functional-test/tasks/{id}/performance-screenshots/{i}`（i 从 0 开始）。
- **操作详情**：报告 JSON 的 `operations` 数组即表格数据源；每列的字段与图片 URL 见上文「操作详情数据如何获取」。

## 七、数据库：长时运行结果保存失败（显示「失败」但实际一直在执行）

**原因**：`task_executions.result_data` 若为 MySQL **TEXT** 类型（约 64KB），长时间性能测试产生的 JSON（操作明细 + 资源采样 + 截图时间轴）会超出长度，写入时报错，整次执行被标为 **FAILED**。

**处理**：
1. **推荐**：执行迁移，将字段改为 **MEDIUMTEXT**（最大 16MB）：  
   **`src/main/resources/db/migration_result_data_mediumtext.sql`**  
   在库中执行：`ALTER TABLE task_executions MODIFY COLUMN result_data MEDIUMTEXT ...`
2. 若未执行迁移，保存失败时会把该次执行仍标为 **COMPLETED**，并在结果中写入简短说明与错误信息，便于排查。
