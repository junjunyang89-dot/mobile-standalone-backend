# 流程录制：后端改了什么（前端对接说明）

> 形态：**人在平台的截图上点 → 平台记一步 → 再驱动设备真的点一下 → 刷新截图**。
> 产物是一条流程草稿 + 一批待审元素。

## 为什么是「在截图上点」而不是「监听人在设备上点」

要把一次点击翻译成「点了哪个元素」，必须拿到**点击那一刻**的控件树。而 `uiautomator dump` 要 300~800 毫秒，人点得比这快得多 —— 等 dump 出来页面已经翻篇了，映射到的是下一屏的控件。

反过来让人在截图上点就没这个问题：截图和控件树是同一时刻冻结的，点中的一定是当时那个控件。代价是慢一点，换来的是**每一步都对、而且每一步都被人确认过** —— 后者正好接上你「元素要人工过一遍」的原则。

---

## 一、数据层的改动（很小）

**没有新建表，没有新建分类树。** 你说的那套结构，`ui_elements` 里本来就有：

| 你说的 | 用的字段 |
| --- | --- |
| 「模拟器定位元素」这一类 | `source` 加了一个值 **`RECORDED`** |
| 分完美电竞 / POGPOG | `appId`（已有） |
| 再分安卓 / 鸿蒙 / iOS | `platform`（已有） |
| 人工审核后「挪过去」 | `status: CANDIDATE → ACTIVE`（已有，页面上已有「提升为 ACTIVE」按钮） |
| 审核时看图 | `previewImage`（已有字段，以前没人写，现在录制会写） |

**`source` 是事实，审核不改它。** 审核动的是 `status`。改了 source 就丢了溯源，以后再想知道「这批是怎么来的」就没依据了。所以不存在「搬家」，也不需要「共同存在」这个状态 —— 一个控件一条记录。

录制落库时一律：`source=RECORDED`、`status=CANDIDATE`、`catalog=AUTOMATION`、**`pageId` 留空**。

> 页面归属只能人来定。机器猜出来的会毁掉这个字段的价值，而它是你后续维护的唯一抓手 —— 这也是审核时最主要的工作。

**去重**：录制入库前按 `appId + platform + locatorType + locatorValue` 查一次，已有就复用那条（连人工录的也一样复用），不新建。不做这一步的话，同一个按钮录十条用例就是十条记录，一周库就爆了。

另外设备锁多了一种占用类型 `RECORD`（"流程录制"）—— 录制期间设备是被占住的，调度器不会往这台派任务。`GET /devices/occupancy` 里会看到 `kind: "RECORD"`。

## 二、录制接口

### `POST /ui-recordings` — 开始

```jsonc
// 请求
{ "deviceId": "emulator-5554", "appId": "app-esports", "platform": "ANDROID", "name": "登录冒烟" }

// 200
{
  "recordingId": "rec-xxx",
  "deviceId": "emulator-5554",
  "appId": "app-esports",
  "platform": "ANDROID",
  "startedAt": "2026-09-06T14:02:11",
  "screenshotUrl": "devices/emulator-5554/inspect/screenshot?t=1788...",
  "steps": []
}

// 409 —— 设备正被别人占着，或这台已经在录了
{ "message": "设备正被占用：测试任务「登录冒烟」（自 14:00 起）" }
```

`appId` 必填 —— 录出来的元素要落到具体应用下面。

`screenshotUrl` 是相对路径，跟真机点选采集用的是同一个接口，**同样要带认证去取**（前端已有 `fetchDeviceInspectScreenshotObjectUrl`，直接复用）。

### `POST /ui-recordings/{id}/tap` — 录一步（核心）

```jsonc
// 请求：相对截图的 0~1，跟点选采集完全一样，前端换算可以照搬
{ "xRatio": 0.42, "yRatio": 0.68 }

// 200
{
  "step": {
    "index": 3,
    "keywordCode": "CLICK",
    "elementKey": "btn_login",
    "elementNameZh": "登录",
    "locatorType": "id",
    "locatorValue": "com.pwrd.xxx:id/btn_login",
    "matchCount": 1,
    "previewImage": "ui-element-previews/rec-xxx.png",
    "params": {},
    "existingElementId": "uie-abc",
    "existingElementStatus": "ACTIVE"
  },
  "screenshotUrl": "devices/.../inspect/screenshot?t=...",
  "totalSteps": 3
}
```

几个字段的用法：

- **`existingElementId` 有值** = 这个控件元素库里已经有了，这一步直接复用，不会新建。UI 上可以标个「复用」，让人知道这一步不用审。
- **`matchCount > 1`** = 这个定位在按下那一刻命中多个节点，执行时只会用第 1 个。**标红**，跟点选面板里那个逻辑一致。
- **没命中控件时**会退回坐标点击：`locatorType: "coordinate"`，同样会有 `elementKey`（早期版本这里不给 key，结果这种步骤回放时直接倒在「缺少 elementKey」上，见 `录制回放点不中-改动说明.md`）。能跑，但换个分辨率就废了。
- **`fragile: true`** = 这一步的定位靠不住，`fragileReason` 是给人看的一句话。**要在步骤列表里当场标出来** —— 人可以立刻退回去换个带文字的控件重点一次，而不是等收工甚至等回放失败才发现。

**顺序是「先记录后执行」**：点击会让页面立刻变化，而这一步该记的元素属于变化之前那一屏。所以返回的 `screenshotUrl` 已经是**点完之后**的新画面，前端拿到就重新拉图。

### `POST /ui-recordings/{id}/step` — 手动补一步

等待、返回、断言这些不是「点一下」的操作：

```jsonc
{ "keywordCode": "ASSERT_ELEMENTS_EXIST", "elementKey": null,
  "params": { "elementKeys": ["btn_login"], "mode": "all" } }
```

### `POST /ui-recordings/{id}/undo` — 撤销最后一步

```json
{ "totalSteps": 2, "message": "已撤销记录。设备上那一步的实际操作不会回退，界面还停在原处，必要时先在手机上退回去再接着录" }
```

**这句话请务必在 UI 上显示出来。** 只撤记录，设备不会退回去 —— 人如果以为界面也回退了，接着录出来的就是一串错位的步骤，而且当时看不出来。

### `POST /ui-recordings/{id}/refresh` — 重新拍一张

人在设备上手动操作过（比如手动退回上一页）之后，用它把截图对上。返回整个会话。

### `GET /ui-recordings/{id}` — 当前状态

返回会话全量（含 `steps[]` 和最新 `screenshotUrl`），刷新页面后恢复现场用。

### `POST /ui-recordings/{id}/finish` — 收工

```jsonc
// 请求（可省，不给就用开始时的 name）
{ "flowName": "登录冒烟-录制" }

// 200
{
  "flowId": "uif-xxx",
  "flowName": "登录冒烟-录制",
  "steps": 12,
  "elementsCreated": 5,
  "elementsReused": 7,
  "warnings": [
    "元素「最新」的定位在录制那一刻命中 3 个节点，执行时只会用第 1 个——审核时建议收紧"
  ],
  "message": "已生成流程草稿。新建的 5 个元素是待审候选……"
}
```

生成的流程：**`catalog=AUTOMATION`**、**`environment=TEST`**、`enabled=true`、**`releaseStage=TESTING`**（本版新录的东西，跑老包的回归批次会据此排除它）。

> `catalog` 用 AUTOMATION 而不是 SHARED 是有意的：`RunTrack.catalogs()` 里 **SHARED 是两条轨道都收的**，
> 用 SHARED 会让刚录完的草稿出现在**线上回归的勾选列表**里 —— 而它元素还没审、页面归属空着、一句断言都没有。
> 生产那一侧还有 `environment=TEST` 兜底，但「测试环境的回归」是漏的。
> 想让它两边都能用，人在流程编排里改成 SHARED 就行，是主动的一步。
>
> **元素的 catalog 仍然是 SHARED**，那是另一回事：元素是页面上的控件，不属于任何轨道，
> 限制成 AUTOMATION 只会让以后线上回归的流程没法复用它。

拿到 `flowId` 建议直接跳到流程编排页去编辑 —— 录出来的是草稿，加断言、加参数是下一步的事。

### `DELETE /ui-recordings/{id}` — 放弃

释放设备，丢弃已录的步骤。

## 三、元素管理页要加什么

后端筛选**全都是现成的**（`source` / `status` / `platform` / `appId` 都能筛，页面上也已经有这些下拉）。你只需要：

1. **来源下拉加一项**「录制」→ 值 `RECORDED`
2. **加一个「待审」快捷入口** —— 本质就是预设筛选 `source=RECORDED & status=CANDIDATE`，不是一个物理分区
3. **审核界面**：列表带上 `previewImage` 缩略图。人只需要四个动作 —— **确认 / 改名 / 选页面 / 丢弃**。选页面是重点，因为录制时是空的
4. 「提升为 ACTIVE」按钮已经有了，不用动

这样一次审十几个是几分钟的事，不是一下午。

## 四、录制页面的交互，几个建议

- **左边截图、右边步骤列表**，跟真机点选采集的布局一致。截图的点击换算可以直接照搬 `DeviceInspectDrawer.onShotClick`
- 每次 tap 之后**立刻重新拉图**（返回值里给了新的 `screenshotUrl`），否则人会对着旧画面继续点
- **步骤列表要能看到 `matchCount` 和「复用/新建」**，这两个信息决定了收工后要审多少东西
- **坐标兜底的那些步骤要显眼** —— 它们是这条流程里最脆的部分
- 录制中途可以随时 `finish` 保存一段 —— 会话在内存里，**后端重启会丢**，别让人一口气录一小时

## 五、执行时怎么对待没审核的元素

**照跑，只在执行日志里记一条提醒。**

这一条是被迫也是应该的：以前 `UiFlowExecutor` 解析元素只认 `status=ACTIVE`，于是**录制生成的流程必然一步都跑不了** —— 录出来的元素是 CANDIDATE，而想验证录得对不对就得先跑一遍，想跑一遍又得先把每个元素审掉。这是个死结。

**审核该换来的是「能进正式执行」的资格，不该是「能不能跑起来」。**

解析顺序：

1. 先把所有平台名（含历史别名）按 **ACTIVE** 找一遍 —— 同名之下选用的那条永远优先，人审出来的元素不会被一条随手录的候选盖掉
2. 再收未审核的（CANDIDATE），执行日志里记一条「还没审核，正式执行前建议补上页面归属并选用」
3. **DEPRECATED 仍然拦**，并且换了文案 —— 那是人明确决定「别再用了」，悄悄拿来用等于把那个决定作废

顺带把「无 ACTIVE 元素」这句话改了：元素真的不存在时说「元素库里没有这个元素」，不再误导人去点「选用」。
