# 平台体检与演进建议

> 2026-09-04。基于当前工作区代码（404 个 java 文件 / 约 77000 行）与 `dumps/` 里 2026-08-30 的数据快照。
> 三条主线：安全、架构、以及「多项目每周迭代怎么做 diff」。

---

## 0. 先说结论

**架构骨架的方向是对的**——`NodeIdentity` + `WorkerHeartbeatAgent` 已经预埋了控制面/执行节点分离，`@Scheduled` 都带了本地执行守卫，失败归因（`FailureDiagnosisService`）和接口源码级 diff（`ApiChangeAnalyzer`）这两块做得比同类平台好。问题不在设计品味，在于**「只有我一个人在用」这个假设被写进了太多地方**，而你接下来要做的三件事（加真实数据、推给 50 人、跑全量自动化）会同时把这些假设全部证伪。

**今天就该做的三件事**（都在半天以内）：

1. 补 `AuthFilter` 的路径归一化——现在**任何人不用登录就能造管理员账号**（第 1.1 节，附自测命令）
2. `CaseAskCodeSearch` 的 rg 命令加一个 `--`——现在**只读账号就能在后端执行任意命令**（第 1.2 节）
3. 把 MySQL 从公网 IP 上撤下来（第 1.3 节）

前两条我复核过，不是 agent 的猜测。

## 一、安全

### 1.1 🔴 鉴权可以被 `..` 绕过 —— 未登录即可提权到管理员

`auth/PermissionRules.java:127` 的 `normalize()` 只做了「去 query、补前导斜杠、去尾斜杠」，**不消除 `..` 段，也不做 URL 解码**。而 `auth/AuthFilter.java:92` 用的是 `request.getRequestURI()`——Tomcat 这里返回的是**原始未归一化**的 URI，可 Spring 的路由映射用的是归一化之后的路径。**两者看到的不是同一个路径，鉴权就形同虚设。**

项目 `context-path: /api`（`application.yml:4`），且 pom 里**没有 spring-boot-starter-security**，所以没有 `StrictHttpFirewall` 兜底。攻击长这样：

```
POST /api/health/../platform-users
{"username":"attacker","password":"xxxxxx","role":"ADMIN"}
```

`AuthFilter` 看到的是 `/health/../platform-users`，`startsWith("/health")` 命中 PUBLIC_PREFIXES，**直接放行**；`DispatcherServlet` 归一化后打到 `PlatformUserController.create()`——而那个 controller 里没有任何角色校验，`AuthFilter` 是唯一的边界。同理可以拉全量账号、重置任意人的密码。

**先自测确认**（后端跑起来后，10 秒的事）：

```bash
curl -i -X POST 'http://localhost:3000/api/health/../platform-users' \
  -H 'Content-Type: application/json' \
  -d '{"username":"pentest","displayName":"越权测试","password":"abc123","role":"ADMIN"}'
```

返回 401 就说明这条路走不通（Tomcat 版本行为不同）；**返回 200 并且账号真建出来了，就是确认命中**。记得把测试账号删掉。

**修法**：`pathOf()` 改用 `new UrlPathHelper().getPathWithinApplication(request)` 取解码归一化后的路径；同时 `normalize()` 里对含 `..` 或 `%` 的路径直接拒绝（正常业务路径不会有）。

顺带同源的第二个问题：PUBLIC_PREFIXES 用 `startsWith` 而不是**按路径段**匹配（`PermissionRules.java:85`），意味着以后任何新增的 `/health-check`、`/bug-images-admin` 这类路由会自动变成免鉴权。改成 `p.equals(pre) || p.startsWith(pre + "/")`。

### 1.2 🔴 只读账号就能在后端执行任意命令

`service/CaseAskCodeSearch.java:396`：用户可控的 `query` 作为**位置参数**拼进 ripgrep 命令行，前面既没有 `--` 也没用 `-e`：

```java
"--glob", "!**/build/**",
query,                      // ← 这里
root.toString());
```

`-F` 只影响 pattern 怎么解释，**不影响参数解析**——`--pre=/bin/sh` 仍然会被 rg 当成选项，然后对每个被搜文件执行 `/bin/sh <文件>`，以后端进程身份。而 `/ask` 在 `PermissionRules.java:48` 的 `READ_ONLY_POST_SUFFIXES` 白名单里，**VIEWER 就能调**。

**修法**：`"--glob", "!**/build/**", "--", query, root.toString()`。一个 token 的事。

### 1.3 🔴 MySQL 挂在公网 IP 上，用 root，密码明文

`application.yml:15`：`jdbc:mysql://118.25.144.133:13306/...`，`username: root`。这是公网地址，不是内网。全网都能连的 MySQL + root 账号，只要密码被撞出来或者从任何一份拷贝出去的 yml 里泄露，整个平台的数据（含所有人的口令散列）就没了。

`.gitignore` 覆盖了 `application*.yml`，`git ls-files` 里确实没有它们——**所以不是仓库泄露**，是运维问题。但 `target/classes/application-*.yml` 有编译产物副本，拷贝构建目录就会带出去。

**修法**：撤到内网或加白名单；建一个只对 `mobile_standalone` 库有权限的专用账号，别用 root；密码走环境变量（`application-prod.yml` 已经是 `${DB_PASSWORD:...}` 的正确写法，其余照抄）。

### 1.4 🟠 鉴权失败时是「放行」而不是「拒绝」

`auth/PlatformUserService.java:98` 的 `isBootstrapping()`：`countAll()` 抛异常就 `return true`，而 `AuthFilter.java:61` 见到 true **整套鉴权关闭**。

这不需要 0day。连接池打满、MySQL 抖一下、`platform_users` 被误锁的那几十秒里，264 个端点、真机控制、抓包、Jira/Wiki 凭据对内网所有人完全敞开，而且 `/auth/me` 还会主动回 `role: ADMIN`。**DB 抖动是常态，不是极端假设。**

原注释的出发点（别把人锁在门外）是对的，但方向搞反了：分不清「服务挂了」和「没账号」时，应该 fail-close 回 503。真正的「还没建账号」用一个启动期判定一次的标志位就够，不必每个请求现查库。

### 1.5 其余（按严重度）

| 问题 | 位置 | 说明 |
|---|---|---|
| 🟠 令牌无法吊销 | `AuthTokenService.java:28` | 无状态 HMAC，7 天 TTL。改密码、令牌泄露后旧令牌仍有效整整 7 天（停用账号有效，因为每请求查库）。忘记密码方案的 P1 就是修这个 |
| 🟠 SSRF | `ApiTestRunnerService.java:174` | 接口测试的目标 URL 完全用户可控且响应原样回显。平台在内网，等于给了一个内网扫描器。修法：目标走 `api_environments` 的 baseUrl 白名单，拒绝私网/元数据地址 |
| 🟡 adb/hdc 参数注入到设备 | `DeviceManager.java:601/642/805`、`harmony/HdcClient.java:111` | ProcessBuilder 用的是 argv 数组（服务端不过 shell，✅），但 adb 会把参数拼成一条命令交给**设备上的 sh**。`packageName` 带分号能在真机上执行命令。危害限于被测设备。修法：包名/设备号按 `^[A-Za-z0-9._:-]+$` 校验 |
| 🟡 CORS 通配 + allowCredentials | `config/CorsConfig.java:16` | 单看危害有限（令牌走 header），但和 1.4 叠加就实打实了 |
| 🟡 异常消息直接回前端 | 全局无 `@ControllerAdvice`，187 处 `body(Map.of("message", e.getMessage()))` | MyBatis 异常的 message 含表名列名和 SQL 片段，是现成的 schema 探测通道 |

### 1.6 这些地方做得好，不用改

不是客套，是为了别在错的地方花时间：

- **无 SQL 注入**：mapper XML 和注解里 **0 处 `${`**，全是 `#{}`。jdbcTemplate 的 19 处字符串拼接全是启动期常量 DDL，无请求参数流入
- **静态资源路径穿越防得很好**：6 个 `*ResourceConfig` 全部自定义了 `PathResourceResolver` 做 `toRealPath().startsWith(root)`，比大多数同类项目严
- **上传落盘**：一律 UUID 重命名 + 扩展名白名单，`getOriginalFilename()` 没有任何一处进入路径拼接
- **口令存储**：PBKDF2 / 120k 轮 / 随机盐 / 定长比较，正确
- **日志不泄露**：没有打印口令、token、Authorization 头

## 二、架构：从「一个人调试」到「50 人共用」会先在哪崩

### 2.1 推广前必须解决

**① 设备锁是纯进程内的。** `DeviceLockService.java:57` 是 `ConcurrentHashMap`，类注释自己写了「多实例部署时需换成 DB 行锁」。**进程重启锁就全丢**——正在跑的任务还占着设备，新任务却能抢进去，Appium 会话互踩、截图错乱、两个任务都判失败且看不出原因。这是 50 人共用后最先炸的地方。

**② 重启后 RUNNING 任务变僵尸。** 全库没有任何 orphan 状态回收逻辑，`TaskService.java:60` 的 `runningTasks` 是内存 Map。每周迭代重启一次，库里就留下一批永远「执行中」、谁也停不掉的任务，只能手动改库。50 个人同时看到这个会立刻来找你。

**③ Quartz 用的是默认 RAMJobStore。** `config/QuartzConfig.java:37` 没设 job-store-type，yml 里也没有。**所有定时测试计划存在内存里，重启即全部丢失**；部署两个实例则同一个 plan 被触发两次。

**④ 任务并发没有上限。** `TaskService.java:59` 和 `OnlineRegressionOrchestrator.java:113` 都是 `newCachedThreadPool()`，全库无 Semaphore、无 max-concurrent。50 人同时点「跑用例」就是无限开线程 + 无限起 Appium 子进程。而 Hikari 池只有 10（`application.yml:19`），先到的把连接耗光，后面全挂在 60 秒超时上。

**⑤ 任务没有归属人。** `entity/Task.java` 有 `workerId` 但没有 `createdBy`。`auth/` 那套权限体系没接到任务层——没人知道跑挂的任务是谁提的、谁能停、设备锁被谁占着。

**⑥ 配置里全是私人凭据和本机路径，别人根本起不来。** `application.yml` 真实 364 行，而 `application.yml.example` 只有 37 行。除了 1.3 的 DB，还有 pushplus token、几个明文 API key（`:175` 直接是 `yangjunjun9889`）、Wiki/Jira 口令、`:37` 的内网 Redis IP（别人网络里不通）、`:190` 写死的 `/Applications/DevEco-Studio.app/...`（只对 Mac 成立）。**推广时的现实结果是：你私聊发一份含 root 密码的 yml 给 50 个人。**

这一条比看起来更要紧——它是「推广」这件事本身的阻塞点，不是可以推迟的技术债。

### 2.2 推广后很快会痛

- **schema 没有版本管理**：32 处 `CREATE TABLE IF NOT EXISTS` 散在 25 个 service 的 `@PostConstruct` 里，另加 `src/main/resources/db/` 下 **63 个 sql 文件**，pom 里无 flyway/liquibase，库里无版本记录表。没人知道某个环境跑到哪一版；两个实例同时启动会并发 DDL，MySQL 对同表 ALTER 会 metadata lock 卡死启动；`ApiTestCaseService.java:204` 这类补列失败只 `log.debug` 吞掉，列没加上应用照样起来，直到运行时报 Unknown column
- **零全局异常处理**：53 个 controller 各自 try/catch，没 catch 到的直接吐 500 白页
- **日志无法串联**：无 MDC、无 traceId。50 人并发时日志交错，查一次失败要从几千行里靠时间戳猜
- **无任何运行指标**：pom 里没有 actuator/micrometer。跑了多少任务、成功率、设备占用率，全靠 `top`
- **`/tmp/screenshots` 硬编码**：`DeviceInspectService.java:48` 写死在常量里，`application.yml:76` 的 `inspect-dir` 形同虚设。报告和数据目录都在 `${user.home}/.mobile-standalone/`——**报告存在执行者本机，别人打不开**
- **核心链路零测试**：131 个测试文件，但 `TaskService`、`DeviceManager`、`DeviceInspectService`、`AppiumDriverAdapter`、`OnlineRegressionOrchestrator` 全部 0 测试。行数最大的 8 个类里 7 个没测，每周迭代改这些等于裸奔

### 2.3 长期技术债

行数 Top 5 全在 service 层：`DeviceInspectService` 3415、`AppiumDriverAdapter` 2754、`DeviceManager` 2645、`ReleaseDocService` 2572、`OnlineRegressionOrchestrator` 1697。

`DeviceInspectService` 一个类混了 5 层职责（125 个方法），其中**硬编码某个具体 App 页面特征的启发式规则占了 1000+ 行**——`looksLikePrivacyWarmTip`、`isBottomNavTabLabel`、`isMineContentTabLabel` 这类。每接一个新 App 就要改这个 3400 行的类，且没有一行测试。这也正是上次 Inspector 式控件树改造要解决的问题：把选择权交给人之后，这些规则可以退化成「默认推荐」，而不是继续膨胀。

`service` 根目录塞了 94 个文件（占 service 层 47%），发版文档、问题跟踪、设备驱动、AI 用例四个完全不同的业务域没有包边界；`apitest` 子包和根目录的 `ApiTestRunnerService` 并存，同一个域被劈成两半。

controller 层反而很干净（平均 157 行），不是优先项。

## 三、「APP 自动化、接口自动化全部跑起来」差什么

### 3.1 最狠的一条：UI 自动化的定时入口是断的

Quartz 那条路 `TaskDispatcher.java:112` 只认 `scenarioId`，而 `FunctionalTestScenarioService.java:40` 里功能场景已经返回空列表，`caseIds` 路径直接报「已下线」；`TaskService.java:455` 里 STABILITY / INSTALL_UNINSTALL / UI_ADAPTATION 三种任务类型还是 `// TODO` 空实现。唯一能跑批量的 `OnlineRegressionOrchestrator` **没有任何 cron 入口，只有手动 POST**。

**「无人值守」目前字面意义上不成立。** 最小改法：让 TestPlan 支持 flowIds，Quartz Job 直接调 `orchestrator.startRun`。

### 3.2 没有 setUp/tearDown，失败会污染下一条

`UiFlowExecutor.java:238` 的 `restoreDeviceToggles` 只还原「不保留活动」一个开关；复位流程只存在于 `OnlineRegressionOrchestrator.java:235`，而且是**人在编排里手选一个 flow**，不是框架保证。单任务和 Quartz 路径完全没有复位概念。

跑全量到第 5 条以后，红的原因大概率是第 3 条留下的弹窗。**「每条用例前强制冷启 + 回首页」必须下沉成框架行为。** 另外也没有 driver 会话健康检查/自动重建，Appium 一挂当前批次全红。

### 3.3 真正的瓶颈不是平台能力，是用例基数

数据快照（2026-08-30）：

| | 数量 |
|---|---|
| ui_elements | **1523** |
| ui_flows | **23** |
| ai_test_cases | 116 |
| api_test_cases | **307** |
| api_test_collections | **9** |
| env_variables | **4** |
| online_regression_accounts | 4 |

**1523 个元素配 23 条流程**——元素采集跑在前面，用例编排没跟上。接口侧 307 条用例只有 9 个集合，大部分用例不在任何集合里，**跑不到**。环境变量只有 4 条，说明数据驱动还没铺开。

这意味着：先定 20-30 条核心路径的用例清单并写出来，优先级**高于继续加平台能力**。现在「全部跑起来」的问题是没有量可跑。

### 3.4 元素单点定位，改版一次就成片红

1523 个元素里只有约 292 条有 fallback（**≈19%**）。`lastVerifiedAt` 字段存在但没有任何巡检任务刷新。备选定位也失败就直接失败，没有运行时自愈；`FailureDiagnosisService.java:721` 的候选定位采纳要人点。

每周版本迭代 + 81% 单点定位 = 每次改版都有一批红，而每条红都要人复核，**这会直接吃掉自动化的全部收益**。需要：批量补 fallback + 一个夜间元素体检任务 + 高置信度的 ELEMENT_BROKEN 自动采纳。

### 3.5 接口侧的三个缺口

登录 token 靠「登录用例排第一」这个约定，没有登录态复用/过期重取；18 个后端服务各自的 host/token 要逐个配 `ApiTestEnv`，`api_projects.success_code_path/value` 基本没填；没有前置 SQL 造数和跨集合的数据准备/清理编排。

## 四、多项目、每周迭代的 diff 怎么做

这是这次最值得投入的方向，因为**已有的拼图质量很高，缺的只是把它们串起来**。

### 4.1 已经有的四块（别重复造）

1. **源码级接口 diff**（`service/apichange/ApiChangeAnalyzer.java`，1169 行）——不比 swagger，**直接解析 Java 源码 AST**，两版之间比接口级 `ADDED/REMOVED/MODIFIED`、字段级 `TYPE_CHANGED`、入参级 `required` 变化，风险分档 `BREAKING > NEW > IMPL > COMPATIBLE`，且特意排除了「新接口的入参」这类噪音。这块是全平台最强的一部分
2. **分支名 → Jira 单号的零人工关联**（`BranchIssueKey.java:36`）——从 `fch/20260804/APP-8928` 抠出单号自动挂需求
3. **版本与单据同步**（`ReleaseDocService` + `VersionArchiveService`）——从 Wiki 汇总页按版本标题捞出该版本全部 Jira 单
4. **成熟的执行层**（`OnlineRegressionOrchestrator` + `apitest` 包）

### 4.2 缺的四样

**① 一张「版本 × 项目 × 分支」的事实表，而且要自动填。**

这是最要命的一条。`application.yml:230` 那串 `branch-keywords` 暴露了你们的真实组织方式：**约 18 个后端微服务 + 4 个客户端项目的多仓单体发版，一个 Jira 需求单常常同时改好几个仓**。而「这个版本改了哪些仓、哪些分支」这个事实，**目前只以人手写的自由文本存在于 Jira 注释里**，平台靠一本硬编码的关键字词典去正则逆向解析（`ReleaseDocService.java:1137`，代码里全是「双保险」「残留清理」的注释，说明源数据很脏），**解析完还不落库**，只用来渲染文档。

同时 `api_projects` 表里 28 行的 **`repo_path` 和 `base_branch` 全是 NULL**（`dumps/mobile_standalone_complete.sql:286`）。也就是说 4.1 那套接口变更分析在库里**一个项目都跑不起来**，实际只能靠 `analyze-dirs` 手动指两个目录。

> **最便宜、收益最大的一步**：把 28 行的 `repo_path` 填上，再把 `ReleaseDocService` 已经解析出来的「仓名: 分支」结构化落一张表。填完之后，那套源码级接口 diff 立刻能对 18 个后端仓批量跑。**这一步大概半天，是整个 diff 方案的地基。**

**② 一套统一的模块命名。** 现在有三套互不相通的「模块」：周改动看板取路径前两段（`ChangeReviewService.java:492`）、`ai_test_cases.module` 是自由文本、`project_modules` 树是空表。变更影响面分析的本质就是「改动 → 模块 → 用例」，中间这一跳现在断着，所以周改动看板只能退化成关键字 `contains` 匹配。

接口侧其实**已经跳通了**（改动 → endpoint → `api_test_cases`，靠 path 后缀匹配，`ApiChangeController.java:126`），缺的是 UI 侧和客户端侧——**客户端仓的 diff 落不到任何模块或流程上**，而客户端恰恰是 APP 自动化要覆盖的部分。

**③ 「测过了」的判据，而不是「有用例」的判据。** 全平台唯一连着执行结果的是 `AiTestCaseService.lastRunOf(flowId)`。`markCoverage` 数的是用例条数，周改动看板的「已覆盖」是人手点的**而且存在浏览器 localStorage**（换台机器就没了，也做不了跨周趋势）。要回答「哪些没测到」，需要一个统一的 `最近执行(用例|流程|接口, 版本) → 通过/失败/未跑` 视图，让「覆盖」从人工标记变成查询结果。

**④ 反向驱动执行的通道。** 现在所有执行入口都是「人在页面上勾选」。缺一个 `影响面 → 建议测试集` 的生成器：给定一次版本的变更集，自动产出该跑的 `flowIds` + 接口集合 id，一键起跑。`ApiTestCollectionService.findOrCreateTestCollection(project, requirementNo)` 已经是这个形状的雏形，把输入从「人选需求」换成「分析出的影响面」就成立了。

### 4.3 建议的三步走

每一步都能单独产生价值，不用等全套做完：

**第一步（约 1 天）：把地基填上，让接口 diff 真的跑起来**
填 `api_projects.repo_path` / `base_branch`；把 Jira 注释解析出的「版本 × 仓 × 分支」落成一张表；给这张表加一个定时任务，每次发版文档同步时自动更新。
→ 产出：每周版本一键出「这版哪些接口变了、哪些是 BREAKING、每个变更接口有几条用例」。这一条本身就够写周报了。

**第二步（约 2 天）：把「覆盖」变成查询结果**
建一个执行结果视图（用例/流程/接口 × 版本 → 最近一次通过/失败/未跑）；周改动看板的状态从 localStorage 迁到服务端。
→ 产出：漏测判断不再靠人手打关键字，能出跨周趋势。

**第三步（约 3 天）：模块命名统一 + 影响面驱动执行**
先只做客户端仓：给 `project_modules` 填上真实模块树，建立「客户端目录路径 → 模块」的映射规则，让 `ui_flows` / `ai_test_cases` 挂到同一套模块 id 上。然后做「变更集 → 建议 flowIds + 接口集合」的生成器。
→ 产出：改了什么就自动跑什么。

**明确不建议现在做的**：把接口 diff 扩展到 Go 仓和客户端源码。成本高、收益不确定，先用第三步的「目录路径 → 模块」粗粒度映射兜底，跑半年看够不够。

## 五、从调试到推给组内，怎么走

你说的「慢慢加真实数据再推给组内」是对的节奏。建议把准入条件写死，别凭感觉推：

**阶段一：单人可信（现在 → 2 周）**
- 修完第一节的三条红色项
- 配置外置：把 yml 里所有私人凭据、本机路径改成环境变量，把 `application.yml.example` 补成真正能照着配起来的版本
- 引入 Flyway，把 63 个 sql 收编成有版本号的 baseline
- 准入：**另一个人拿着 example 能在自己机器上把平台跑起来**。做不到就还不能推

**阶段二：小范围真实数据（2 → 6 周）**
- 设备锁落库 + 启动时回收 orphan RUNNING + Quartz 切 JDBC JobStore
- 任务加 `createdBy`，接上已有的权限体系
- 任务并发加上限，Hikari 池按并发调
- 补 20-30 条核心 UI 用例，元素 fallback 覆盖率从 19% 提到 60%+
- 打通 UI 定时入口（3.1）+ 框架级复位（3.2）
- 拉 2-3 个同事真实使用，你在旁边看着
- 准入：**连续一周夜间全量无人值守跑完，红的里面至少 70% 是真 bug 而不是用例坏了**

**阶段三：推给全组（6 周之后）**
- 全局异常处理 + traceId + 基础指标
- 忘记密码的 P1/P2 收尾
- 核心链路补测试（至少 `TaskService`、`DeviceLockService`、`UiFlowExecutor` 的关键分支）
- 准入：能回答「谁在跑什么、跑挂了为什么、设备现在谁占着」

**最容易被忽略、但会决定成败的一件事**：3.4 说的元素失效。改版一次成片红、每条红都要人复核，这是自动化平台在测试组里失去信任的最常见死法——不是平台不好用，是**大家发现维护用例比手工测还累**。所以阶段二的准入条件我写的是「红的里面 70% 是真 bug」，而不是「跑通了多少条」。
