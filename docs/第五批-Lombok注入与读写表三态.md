## 一、② Lombok 构造器注入

### 问题

`INJECTED_FIELD` 只认注解式注入:

```java
"@(?:Resource|Autowired)[^;]*?private\\s+(?:final\\s+)?..."
```

而 `@RequiredArgsConstructor` + `private final XxxService xxx;` **一个都认不出**。

**实测被测后端 app-engine:75 个 Controller 里 7 个是这种写法。**

后果是最坏的那一种:`usedServices` 恒为空 → 依赖解析返回空 Deps →
**读写表、Redis key、并发风险、IMPL 档全部归零**,而报告上看着「这个接口很干净」。
不报错,只是悄悄少了半份分析。

### 改成什么样

加两条:类上有 `@RequiredArgsConstructor` / `@AllArgsConstructor` 时,
`private final <类型> <名字>;` 也算注入。

两道防线防噪音——**依赖清单一旦有噪音,后面基于它的表和并发分析就全跟着脏**:

1. **不带等号**:`private final String PREFIX = "abc";` 是常量不是注入
2. **排掉值类型**:String/Integer/List/Map/Pattern… 这些不是依赖

用"值类型黑名单"而不是"名字以 Service 结尾"——因为 Mapper、Client、Manager 也是依赖。

## 二、③ 读写表拆分 + 三态

### 拆读写

原来的正则把动词混成一组:

```java
"(?i)\\b(?:from|join|into|update)\\s+`?(表名)`?"
```

拆成带动词捕获,读写分开。**`delete from` 这个分支不能少**——
少了的话 `DELETE FROM t` 里的 `from` 会被当成查询命中,
**一条删除语句被判成只读**,然后被放到生产上跑。

还排掉了 `ON DUPLICATE KEY UPDATE col = ...`——那里的 `update` 后面跟的是列不是表,
不排的话每条 upsert 都会凭空多出一张写表。

### 三态:这是整件事的关键

```java
WRITES      扫到 insert/update/delete/replace
READ_ONLY   依赖链解析出来了，有读，没有任何写
UNKNOWN     判不了 —— 按会写处理
```

**为什么必须三态。** 直觉上这是个是非题,但静态分析一定有看不透的地方:
走消息队列的、走 RPC 的、动态拼 SQL 的、依赖注入没认出来的。
这些接口的共同表现是「**没扫到写表**」。

两态设计会把它们全部归进「只读」,然后放到生产上跑——
**而这正是这个判据要防的事,结果反而成了它制造的事故**。

还有一个容易漏的:**依赖链解析出来了、却一条 SQL 都没有,也是 UNKNOWN**。
那说明它在调下游服务 / 发消息 / 只碰 Redis,这些同样可能改数据,只是改在别处。
把它算成「只读」和把解析失败算成「只读」是同一个错误。

只有 `READ_ONLY` 能上生产,这是唯一的白名单。

### 但这一轮反向验证抓出了我自己的三个问题

**1. 我写了一条错误的注释。**

原先我在正则上写:「动词顺序不能动,`delete\s+from` 必须排在 `from` 前面,
正则左优先,反过来写会判成只读」。

退化测试时发现**调换顺序根本不影响结果**。单独写了个最小用例验证:

```
delete 在前  -> verb=DELETE FROM   ✅
from 在前    -> verb=DELETE FROM   ✅  ← 顺序不影响
没有 delete  -> verb=FROM          ❌  ← 这才是真正的失败模式
```

原因:正则引擎按**位置**从左往右扫,在 `DELETE` 那个位置上 `from` 压根匹配不上,
两个分支不会在同一位置竞争。

**这正是我上一轮批评过的事:一条说了代码没在做的事的注释,比没有注释更容易误导下一个人。**
注释已改正,并写明了纠正过程。

**2 和 3. 两条测试没能隔离出它要守的东西。**

- 「带初始值的 final 字段不算注入」用的是 `String` / `Integer`,
  **被第二道防线(值类型排除)挡住了**,测不到第一道防线(等号排除)。
  补了一条用 `AtomicInteger` 的——它不在值类型清单里,只有等号那条约束能挡住它。

## 五、还没接线的部分

`WriteEffect` 现在是个**能用但没人调**的纯函数——和上次 `MemoryLeakAnalyzer` 一样,
我这次提前说明,不等你问:

要让它真正起作用,还需要三步:

1. **`EndpointDependencyResolver` 输出读写分开的表**
   (现在 `Deps.tables` 还是一个不分读写的列表)
2. **`ApiEndpoint` 加一个 `writeEffect` 字段**,扫描时算好存进去
3. **前端接口清单显示这个标记**,并且在生产环境建用例时**默认拒绝非 READ_ONLY**

第 3 步的「默认拒绝」不能做成提示框——**提示会被点掉,尤其 50 个人用的时候**。
