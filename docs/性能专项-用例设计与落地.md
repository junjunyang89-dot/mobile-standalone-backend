## 〇、先说这次改了什么代码

动手写用例之前，有两个底子必须先补上，否则写出来的用例拿到的是不可信的数。

### 1. 修掉「两个冷启动耗时」

平台里原本有**两个**冷启动数字，严谨程度不一样：

| | 在哪 | 怎么量的 |
| --- | --- | --- |
| 专项性能 | `ColdStartMeasurer` | `am start -W` 读系统 `TotalTime`，**5 轮取中位数**，iOS 明确返回不支持 |
| 流程关键字 `COLD_START` | `ColdStartHandler` | `System.currentTimeMillis()` 包一次调用，**单轮** |

`ColdStartMeasurer` 自己的注释早就写明白了：**单轮冷启动波动能到 15~20%，而基线告警阈值就是 15%**——
单轮的数会天天报假劣化，而报三次假的之后，第四次真的也没人信了。

所以 `COLD_START` 关键字改成了**多轮取中位数**（默认 3 轮，丢掉第 1 轮预热）。

**iOS 的口径写进了报告文案**，跟着数字一起走：

> 口径：墙钟计时，含 WDA 通信往返，偏高，只看 iOS 自己版本间的趋势，勿与 Android 横比

这句话必须跟着数字，因为**一个没标口径的数字迟早会被人拿去横比**。

### 2. 新增内存泄漏判据

四类场景里只有「长时间挂机」没有现成判据。新增：

- **`MEMORY_CHECKPOINT` 关键字**——催一次 GC、等 1.5 秒、取一次 PSS
- **`MemoryLeakAnalyzer`**——分析这批点，判断是不是泄漏

判据的设计在第四节展开，那里是这次真正花心思的地方。

### P-03 首页信息流滑动（FPS / 卡顿）

```
COLD_START → 等首页加载 → SWIPE ×20（间隔 500ms）→ 结束
```

- **指标**：fps、jankPercent、cpuApp
- **判据**：fps 劣化 >25%（帧率噪声大，`MetricComparator` 已单独放宽到 25%）
- **要补的元素**：首页信息流容器（滑动目标）、首页加载完成的标志元素
- **为什么值得测**：`HomepageFragment` 刚改过嵌套滚动，而且是 sysweb/X5 双路径——
  这两件事都直接影响滑动流畅度

### P-04 「我的」页面滑动 · 双内核对比 ⭐

```
COLD_START → 进入「我的」→ 切 5 个 Tab → 每个 Tab 滑动 ×10
```

- **指标**：fps、memoryPss、cpuApp
- **判据**：同 P-03
- **要补的元素**：「我的」入口（已有 `HOMEPAGE`）、5 个 Tab、各 Tab 的滑动容器
- **特别说明**：这个页面用哪个 WebView 内核**由服务端开关 `myTabSysWebSwitch` 决定**。
  配合上一轮做的接口响应改写，**同一条用例跑两遍**（开关 `"1"` / `"0"`），
  就能直接对比系统内核和 X5 的性能差异。这是整批用例里信息量最大的一条。

### P-05 H5 页面首屏加载（商城 / 钱包 / 资讯）

```
COLD_START → 进入页面 → ASSERT_H5_RENDERED → MEMORY_CHECKPOINT
```

- **指标**：首屏耗时（从点击到断言通过）、memoryPss
- **判据**：`ASSERT_H5_RENDERED` 通过与否 + 耗时对比基线
- **要补的元素**：商城/钱包/资讯的入口
- **为什么值得测**：这批页面**还在 X5 上**，而 X5 白屏是线上已发生的问题。
  顺带能摸到白屏——测性能的同时抓功能问题
- ⚠️ **前提**：`ASSERT_H5_RENDERED` 要求测试包开 `setWebContentsDebuggingEnabled(true)`，
  否则只能报 BLOCKED。这个还没确认

### P-06 内存泄漏 · 反复进出页面 ⭐

```
（进入页面 → 滑动 ×3 → 返回 → MEMORY_CHECKPOINT）× 12 轮
```

- **指标**：12 个 checkpoint 的 PSS 序列
- **判据**：`MemoryLeakAnalyzer`（详见第四节）
- **要补的元素**：目标页面的入口 + 返回
- **建议先测**：商城商品详情、资讯详情、社区帖子详情——
  这三个都是 WebView 页，而 WebView 没 destroy 是最经典的泄漏源
- **只支持 Android**：iOS 拿不到 PSS 等价物，`MEMORY_CHECKPOINT` 会明确记「不支持」并跳过

### P-07 视频 / 直播播放

```
COLD_START → 进入直播 → 播放 3 分钟 → 结束
```

- **指标**：cpuApp、temperature、fps、networkRxBytes
- **判据**：CPU 劣化 >15%；温度噪声大，阈值已放宽到 30%
- **要补的元素**：直播入口、播放器就绪标志

## 四、内存泄漏判据：这次真正花心思的地方

### 为什么专门做它

泄漏是人工几乎测不到的一类问题——手点十次没人有耐心，而用户连着用一小时就卡死了。
它又恰好是机器最擅长的：重复 N 次、记 N 个数、看趋势。

### 朴素判据会天天误报

- **「末值 > 首值」**：两次采样赶上不同的 GC 时机，差个几 MB 是常态 → 天天报
- **「必须一直上升」**：PSS 本来就抖，严格单调几乎不出现 → 永远报不出来

### 用的是双条件，两个都满足才算泄漏

1. **趋势是真的**：线性回归斜率 > 0 **且 R² ≥ 0.5**
   R² 低说明是上下抖，不是持续涨
2. **幅度值得管**：总增长 ≥ 10 MB
   挡掉噪声量级的「上涨」

### 外加三条

- **丢掉前 2 轮预热**——首次进页面要加载图片、建缓存、初始化 WebView，涨是**正常**的。
  把预热轮算进趋势，等于给每次分析塞一个向上的偏置
- **样本不足返回「样本不足」，不是「没泄漏」**——预热后少于 5 个点不下结论。
  不知道和没问题是两回事，把前者说成后者是这套平台里最不该犯的错
- **中途骤降要标出来**——内存涨到系统上限会被 trim，曲线掉下来，
  **真泄漏的斜率会被压平成「看着没事」**。检测到就在报告里标明置信度打折

### 两个容易忽略的实现细节

**取值绕开节流缓存**。`getMemoryPssKb` 有 2 秒节流缓存，打点如果命中，
相邻两轮拿到同一个数，趋势线被抹平成「没泄漏」——**而且没有任何迹象**。
所以新增了 `getMemoryPssKbFresh`。

**催 GC 是异步的**。`am send-trim-memory` 命令返回不代表回收做完了，
所以固定等 1.5 秒再取值。催不动会在报告里说明，而不是默默拿一个偏高的值去做趋势。

## 五、跟版本走的触发

你选了「跟版本走，不定时」。现状：

- `TestPlanService` + Quartz 的定时机制是现成的
- **但 `AppPackService` 打包完成后没有任何回调点**——没有 `publishEvent`，也没有 webhook

所以「出包后自动触发性能专项」这一步**还没打通**。要做的话是在打包成功的地方发一个
Spring 事件，性能专项订阅它。改动不大，但我没有一起做——
**先把用例跑通了再谈自动触发**，否则自动触发的是一批还没验证过的用例。

在那之前，手动触发就够：出包后点一次。

## 六、验证

- **508 个源文件真实编译通过**，0 错误
- **全量 1468 个单测**（新增 20 个），1434 通过、12 失败——失败的是老的 fixture/网络问题，与本次无关
- **新增 20 个泄漏判据单测**，全过

### 反向验证：逐条退回，看测试抓不抓得到

| 退回什么 | 结果 |
| --- | --- |
| 去掉 R² 条件（抖动会被当成泄漏） | **红** ✅ |
| 去掉 10MB 绝对门槛（噪声会被当成泄漏） | **红** ✅ |
| 样本不足也下结论 | **红** ✅ |
| 不丢预热轮 | **红** ✅ |
| 把没采到的轮次当成 0 | **红** ✅ |
| 不标注中途骤降 | **红** ✅ |

**前两条第一次都没抓到。** 查下来是我的测试数据没隔离出对应的守卫——
「抖动」那组的总增长只有 1MB，拦住它的是绝对门槛而不是 R²；
「缺失值」那组的 0 没能翻转结论。补了两组专门算过的数据才隔离开：

- R² 那组：总增长 15MB（先过绝对门槛）、斜率为正，但 R²≈0.00
- 缺失值那组：两个 0 混进去会造出「总增长 150MB、R²=0.63」的假泄漏

**一条测试如果在任何退化下都不红，它就不是在守东西。**

还有一条要说清楚：写完第一版时有个测试失败了，查下来是**我的测试数据只给了 8 轮，
剔掉缺失和预热后只剩 4 个点，判据如实返回了「样本不足」**——
那是判据对了、测试数据错了。改的是数据，不是判据。
