# 六台设备轮着跑 + 空闲时能借来用

## 要解决的两件事

1. **六台设备（真机 + 模拟器）轮着做自动化** —— 不用每次人工挑一台
2. **空闲时组里其他人能借来用** —— 借走期间不再往这台派自动化任务

前提按你确认的：六台都挂在同一台常开的机器上，后端 `role=ALL` 跑在那台机器上，所以不涉及跨节点路由。

## 一、借用 = 拿同一把锁

没有新建一套「预约」字段，而是给已有的 `DeviceLockService` 加了一个占用类型 `MANUAL`。

理由是这两件事要挡的东西完全一样：**借走的设备不能再被派任务，跑着任务的设备也不能被借走。** 同一件事用两套机制表达，迟早会出现「调度器认为空闲、借用记录认为有人」这种两边都觉得自己对的情况。

复用还白捡了两样已经调好的东西：**占用超时自动回收**（借了忘了还，2 小时后自动收回）和**强制释放**（设备详情里原本就有的解锁按钮）。

新接口：

| 接口 | 作用 |
| --- | --- |
| `GET /devices/occupancy` | 全部设备的占用情况一次拿完 |
| `POST /devices/{id}/reserve` | 借用 |
| `POST /devices/{id}/release` | 归还（只有借的人自己能还） |
| `POST /devices/{id}/renew` | 续借 |
| `POST /devices/{id}/disabled` | 人工停用 / 恢复 |

持有者标识用 `manual:用户名` 而不是随机 id —— **借的是人，不是某个标签页**，换个浏览器、刷新过页面照样能还。

续借做成了 `DeviceLockService.renew()` 这个原子操作，而不是「先释放再重新占用」：后者中间有个窗口，调度器正好在那一瞬间扫过就会把设备派给别人，而借的人毫不知情，两边同时操作同一台手机。为省十行代码去冒这个险不值得。

**停用**（坏了、维护中）和「离线」是分开的两件事：离线是客观事实，停用是人的决定。只靠拔线也能不派活，但那会让人以为设备丢了。

## 二、排队与轮转

### 提交时可以不指定设备

流程执行弹窗默认改成**「自动分配（排队）」**，也可以切回「指定设备」。

改默认是有原因的：六台供全组用时，让人自己挑几乎必然挑到别人正在跑的那台，于是「设备正被占用」直接失败，而人的反应是换一台再点一次 —— 几个人同时这么干就变成互相抢。**交给平台排队反而更快。**

不传 `deviceId` 时任务落库时 `device_id` 为空，配置里记下要什么样的设备，然后进队列。

### 轮转用 LRU，不是转指针

`DevicePicker` 是一个不依赖 Spring、不碰数据库的纯函数，逐层过滤后挑**最久没派过活的那台**。

不用 round-robin 是因为设备会上线下线、会被人借走，轮转指针一遇到设备增减就乱；而「谁闲得最久谁上」不用记状态，天然均衡，新接进来的设备（从没用过）会优先被用上。

挑不到时会说清楚是被哪一条挡住的 —— 「6 台里 4 台在忙、2 台环境不对」比「没有可用设备」有用得多。

过滤条件，按顺序：

| 条件 | 说明 |
| --- | --- |
| 在线且未停用 | |
| 平台匹配 | ANDROID / IOS / HARMONYOS |
| 模拟器 | 默认只有**试跑 + 测试环境**才允许派给模拟器 |
| 环境匹配 | 设备绑了环境就必须一致；留空＝两边都能跑 |
| 未被占用 | 跑任务、被人借走都算 |

**环境这一条不能放松**：设备上装的就是某个环境的包，派错了的现象是「登录失败」，指向的方向完全不对 —— 人会去查账号、查网络，最后才想到是包不对。

模拟器的默认规则刚好对上实际用法：**调试拿模拟器凑合，正式跑要真机结果才作数。** 生产环境那一条在调度器里还会再兜一次，因为拦在执行层意味着任务先被派出去、占了一台设备、跑起来才失败 —— 白占一次设备，队伍里的人白等一轮。

### 调度器为什么是轮询

设备空出来有好几种来路：任务正常跑完、被人停掉、执行线程崩了被锁服务判定失效回收、有人归还借用的设备。每一处都去发一个「我空了」的事件，迟早会漏掉一处，而漏掉的现象是**任务永远排在队里没人管**。三秒一轮的轮询没有这个问题。

几个细节：

- **先拿锁再改库**：反过来的话，两个进程（或人手动点的执行）会同时认为这台是空的。`refId` 用 taskId，与 `TaskService.runTask` 里的一致，所以它再 `tryAcquire` 一次是幂等的，释放仍由执行线程的 `finally` 负责。
- **应用推迟到派到设备之后解析**：`apps` 是按设备记录「这台上装的是哪个包」的，排队时还不知道会派到哪台，自然也解析不了。
- **排队 30 分钟仍派不出去就判失败**，并把原因写进执行记录。不设上限的话，一个条件根本满足不了的任务（要 iOS 但池子里一台都没有）会永远排着，界面显示「排队中」，人会一直等到下班。

## 三、界面

- **设备页**：新增「占用」列 —— 空闲时显示「借用」按钮；被借时显示借用人和「续借 / 归还」；被任务占时显示任务名。每 10 秒自动刷新（共用设备时「这台空了没有」随时在变，看着两分钟前的快照去点借用只会得到「正被占用」）。操作列多一个停用开关。
- **流程执行弹窗**：「自动分配（排队）／指定设备」二选一，自动分配下有「允许派给模拟器」开关（生产环境时置灰，因为一律只用真机）。
- 排队中的任务在**试跑结果弹窗**里显示「排队中」，派到设备后自动接上进度 —— 这块不用改，上一轮做的轮询天然覆盖。

## 四、涉及文件

后端：

- `service/pool/DevicePicker.java` — **新增**，挑设备的规则本体（纯函数）
- `service/pool/DeviceTaskScheduler.java` — **新增**，排队调度
- `service/DeviceLockService.java` — 加 `MANUAL` 占用类型、`renew()`、`maxHold()`
- `controller/DeviceController.java` — 借用 / 归还 / 续借 / 停用 / 占用快照
- `entity/Device.java` + `mapper/DeviceMapper.*` — `last_used_at`、`disabled` 两列
- `service/DeviceService.java` — 自动建列、`setDisabled`
- `mapper/TaskMapper.*` — `findQueued` / `countQueued`
- `controller/UiFlowController.java` — `deviceId` 可空＝交给排班

前端：

- `views/Devices.vue` — 占用列、借用/归还/续借、停用开关
- `views/UiFlows.vue` — 自动分配 / 指定设备
- `api/index.ts` — 对应接口与类型

**不用跑 SQL**，两列启动时自动建。

## 五、验证情况

- `DevicePicker` 的 **15 个用例全过**（`src/test/java/.../pool/DevicePickerTest.java`，跟着 `mvn test` 跑，不是一次性脚本），覆盖：LRU 轮转（含「刚派过活的那台不会紧接着再被选中」）、模拟器隔离、环境匹配、离线/停用/在忙的跳过、平台大小写、空池子和 null 入参、以及每种挑不到时的提示文案
- 五个改动的后端文件 + 两个新文件全量 `javac`，错误类型与补丁前基线一致

### 顺带修了一个我自己差点漏掉的 bug

写调度器时我用了 `task.setErrorMessage(...)` —— 但 **`Task` 根本没有这个字段**，`errorMessage` 在 `TaskExecution` 上。

这个错误在本机 `javac` 里的报错是 `cannot find symbol: method setErrorMessage(String)`，**和几千条 Lombok 访问器的噪音一模一样**，肉眼根本挑不出来。

所以顺手写了 `scripts/check_missing_fields.py`：把这类报错按「目标类里到底有没有这个字段」分成两类 —— 有字段的是 Lombok 噪音，没字段的是真 bug。跑一遍就把它揪出来了。改动涉及的所有文件现在都是干净的。

用法：

```bash
javac -proc:none -d /tmp/out @files.txt 2> /tmp/err.txt
python3 scripts/check_missing_fields.py /tmp/err.txt src/main/java
```

（它按类的简单名查字段，所以同名内部类会有个别误报 —— 当前仓库里有 6 条，都在我没动过的文件里。）

### 没验到的

真的挂六台设备跑一遍。调度逻辑是拿构造的设备列表测的，借用/归还的接口没连真库调过。建议先接两台（一真一模拟）验证排队和借用，再扩到六台。
