# X5 白屏：怎么更快发现

> 现象:某些机型上 H5 页面打开就是白屏,同一个地址在浏览器里正常。
> 根在 X5 内核(TBS)。

---

## 一、先说一条可能不中听的判断

**这类 bug 靠测试「首先发现」,是追不上的。**

X5 内核是**运行时下载**的,不在 APK 里——`InitTbsTask` 里还开了
`QbSdk.setDownloadWithoutWifi(true)`,也就是移动网络也会下。所以:

- 同一个包,今天好、明天坏。内核自己更新了
- 触发条件是「机型 × 内核版本」的**组合**
- 你们几台测试机的组合空间,跟几十万用户的差几个数量级

**首次发现应该来自线上,测试的职责是复现和卡住回归。**
这个分工不说清楚,力气会花在追不上的地方。

线上最快的渠道:**H5 页面自己上报首屏渲染成功与否 + UA + 机型**。
X5 的 UA 里带 `TBS/xxxxxx`,一眼能看出内核版本。这样能直接得到
「哪些 TBS 版本 × 哪些机型 首屏失败率高」。**这个不用改 APP,H5 那边就能加。**

## 三、这次做了什么:`ASSERT_H5_RENDERED`

### 为什么不用原有的白屏检测

平台里已有的 `isMostlyBlackOrWhite` 是「整屏 80% 以上是黑或白」。对这个问题**两头都不准**:

- **误报**:合法的白底页面(登录页、空列表)长得一模一样
- **漏报**:白屏时状态栏 + 标题栏 + 底部导航还在,白的那块占不到 80%
- 它判**整屏**,而 X5 白屏白的是 **WebView 那一块**

而且它只在遍历性能测试里用,**没接进流程编排**。

**白屏的本质是「那块 WebView 里没东西」,不是「屏幕偏白」。所以判据应该问 DOM。**

### 这一步最有价值的地方:把白屏分成两类

| 判定 | 含义 | 找谁 |
| --- | --- | --- |
| `BLANK_DOM` | DOM 是空的,页面没加载出来 | **H5 / 接口 / 网络** |
| `BLANK_RENDER` | DOM 有内容,画面却是空的 | **内核渲染层(X5 典型)** |
| `UNVERIFIABLE` | 探针没跑成 | 见下 |
| `RENDERED` | 有内容 | — |

**这两类在截图上完全一样,但要找的人不是同一拨。** 分不开的话,每次白屏都要
H5 和客户端扯皮一轮——而这正是这类问题发现慢、定位更慢的原因。

`BLANK_DOM` 还会按 DOM 节点数再分一次:节点都没几个 = 页面根本没下来;
节点不少却没内容 = 数据没回来。两种查法不一样。

### 「验不了」绝不算通过

切不进 WebView context(最常见原因:release 包没开调试通道)时,判定是
`UNVERIFIABLE`,默认落 **BLOCKED**——沿用之前那套「没跑成 ≠ 跑了没过」。

**不能算通过。** 算通过的话,所有 H5 流程都会挂着一条绿的「已渲染」断言,
而它从来没真的看过一眼页面——**这正是 X5 白屏能在线上活那么久的原因之一**。

### 两个探针细节

- 用 `innerText` **不是** `textContent`。前者只算**渲染出来**的文字;
  用 textContent 的话,一个 DOM 齐全但整体没显示的白屏页会被判成正常。
- 图只数 `naturalWidth > 0` 的。一页全是加载失败的图,看上去就是白屏,
  而 `querySelectorAll('img').length` 会把它们全算成「有内容」。

## 四、写这个时我自己踩的一个坑

参数 `minTextLength` 我写了句 help:「纯图片页面可以调到 0」。

但代码里是 `minTextLength > 0 ? minTextLength : DEFAULT`——**0 被当成「没传」,
silently 换回了默认值 8。文档里承诺的口子根本不生效。**

而直接让 0 生效又会让 `text >= 0` 恒真,**这条断言就变成一条永远绿的摆设**——
那比没有断言更糟,因为它让人以为这一页被看过了。

现在 0 的含义是「一个字就够」:纯图页靠图过,完全空白的页仍然不过。

## 六、怎么用

在任何打开 H5 的流程里,页面打开之后加一步「H5断言已渲染」:

```jsonc
{"keywordCode":"ASSERT_H5_RENDERED",
 "params":{"minTextLength":8, "timeoutSec":10, "onUnverifiable":"BLOCKED"}}
```

**前提**:测试包要开 `setWebContentsDebuggingEnabled(true)`,否则切不进 WebView context,
这一步只会报 BLOCKED。你们有源码,这是一行的事。

## 七、还没做的

### 1. `BLANK_RENDER` 现在判不出来(判据在,输入还没接)

区分「DOM 空」和「DOM 有内容但没画出来」,需要知道 **WebView 那块区域在截图上是不是空白**。
判定逻辑和测试都写好了(`regionBlank` 参数),但**采集那一端还没接**——
现在一律传 null,所以实际只会得到 `BLANK_DOM` / `RENDERED`。

接它需要:拿到 WebView 控件的 bounds + 截图,只看那块区域的像素。
不难,但我不想在没验证的情况下把它算进已完成。

### 2. 执行时记录 TBS 内核版本

读 debug 面板那段现成文本就行,零代码改动。做了之后,线上一报白屏,
你能立刻回答「我们测的时候跑的是哪个内核」——**现在这个问题答不上来**。

### 3. 差分:同一页面 X5 vs 系统内核

最有说服力的判据,因为它直接给出**因果**。`PWSysWebActivity` 已经存在
(Steam 那几个页面在用),说明系统内核路径本来就通。
需要 APP 组在 debug 包加个全局开关(`QbSdk.forceSysWebView()` 或 debug 面板一个切换)。

## 八、给 APP 组的改造清单

1. **测试包开 `setWebContentsDebuggingEnabled(true)`** —— 没有这个,上面这步只能报 BLOCKED
2. **`IS_X5` 和 `getTbsVersion()` 打到 logcat**,固定 tag(现在 `getTbsVersion` 只在
   `PWBuildConfig.isLogEnabled()` 时打一次,tag `TBS_LOG`)
3. **debug 包加「强制系统内核」开关** —— 差分测试的前提
4. **`onReceivedError` 至少落一条日志** —— 现在多数 Activity 是空实现,
   白屏时连个错误都留不下
