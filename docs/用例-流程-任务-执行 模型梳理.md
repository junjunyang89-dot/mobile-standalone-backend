# 用例 / 流程 / 任务 / 执行 —— 模型梳理与调整建议

> 2026-09-05。起因：「自动化测试用例和流程编排是不是重复了」「APP 测试任务还有没有必要存在」。
> 结论先说：**概念不重复，重复的是执行入口**；而乱的根源是一个具体字段——`ui_flows.catalog`。

---

## 一、先回答「重复了吗」

**没重复，字段零重叠。**

| | 回答的问题 | 独有的东西 |
|---|---|---|
| `ai_test_cases` 自动化用例 | **测什么** | 33 列描述字段：module / testPoint / precondition / expectedResult / requirementNo / sides / priority |
| `ui_flows` 流程编排 | **怎么点** | steps / dependsOn / catalog |
| `tasks` 测试任务 | **哪一次跑的** | deviceId / workerId / status / runTrack |
| `online_regression_*` 线上回归 | **一批怎么调度** | 多设备、多账号、装包策略、复位流程、拓扑排序 |

这是「写什么 / 怎么做 / 哪一次 / 一批」四层，不是四个平行的东西。

**但落地断了，这才是你觉得重复的真实原因：**

> **116 条 `ai_test_cases` 里，`flow_id` 非空的只有 1 条。**

也就是 115 条用例是纯文档，一条可执行流程都没连上。两个菜单看起来都在管「用例」，而中间那根 `flowId` 的线几乎是空的。**该做的是把线接上（`setFlowCases` / `linkable-cases` 接口早就有了），不是合并模型。**

## 二、真正重复的：三个执行入口，一个 UiFlowExecutor

| 入口 | 路径 | 实际做什么 |
|---|---|---|
| 1 | `POST /ui-flows/{id}/execute` | 单条流程 → 1 个 UI_FLOW_TEST task，config 里**写死** `runTrack=AUTOMATION` |
| 2 | `POST /online-regression/runs` | 1 批 → N job → M step → **M 个 UI_FLOW_TEST task** |
| 3 | `POST /tasks/test` + `/tasks/{id}/run` | 泛型后门，性能类走这里 |

三个口子最后都调同一个 `UiFlowExecutor.execute`。差别只有：**一条还是一批 / 要不要装包、复位、分账号**。

而入口的分歧被塞进了**资产的字段**里——这就是 `catalog`：

- `RunTrack.catalogs()`：`AUTOMATION 轨 → 取 [AUTOMATION, SHARED]`，`REGRESSION 轨 → 取 [ONLINE, SHARED]`
- 一条流程打了 `AUTOMATION`，就**永远进不了回归批次**
- dump 里那条 `catalog=PERFORMANCE` 的流程，**两条轨道都取不到，是死数据**；6 条 `INSTALL` 同样被两轨排除

`SHARED` 这个值的存在本身就是这个矛盾的补丁——**你已经在用它绕开自己定的边界了**。

## 三、你的三个场景，差别只在三个变量

把你描述的工作流拆开看：

| 场景 | 流程集 | 环境 | 包 | 数据 | 触发 | 结果处理 |
|---|---|---|---|---|---|---|
| **生产巡检** | 核心路径 | PROD | 线上正式包 | 线上 | 定时 | 断言 + **自动告警** |
| **线上回归** | **同上（复用）** | PROD | **上个版本老包** | 线上 | 手动 | 人盯 |
| **版本准入** | 必回归 + 本周新增 | TEST | DEBUG 包 | 测试 | 手动 | 人盯 |
| **准入后验证** | **同上（复用）** | PROD | **同一个 DEBUG 包** | 线上 | 手动 | 人盯 |

第 2 行和第 4 行的流程集是**完全复用**上一行的——你自己说的「用例可以从自动化生产用例那边来」「继续用该测试环境的用例，只不过数据用线上的」。

**所以差别只有三个变量：环境、包、数据。这三个应该是一次执行的参数，而不是三种并列的功能模块。**

你感觉乱，是因为把「参数的组合」做成了「并排的菜单」。

### 现状：这三个维度参数化到什么程度

| 维度 | 状态 | 具体 |
|---|---|---|
| **环境** | 🟡 半参数化 | 执行时能传（config > 设备绑定 > 默认 PROD），但 `ui_flows.environment` **同时又是流程属性**，`isBatchEligible` 按它过滤候选。23 条流程里 19 条 `env_bound=1`。设备的 environment 字段**全是 NULL**，那条路根本没启用 |
| **包** | 🔴 基本没参数化 | 「装哪个包」整个写死在**流程 steps JSON 的 INSTALL_APP 参数里**（buildKey / channelUrl / apkPath）。`ui_apps` 只有 4 条，是**应用字典不是包版本**，没有 version / buildKey / DEBUG-RELEASE 字段。**想换包＝换流程** |
| **数据** | 🟡 通道分裂 | `env_variables`：按环境切、能被 `${}` 引用、但**整个库只有 4 条**（一个账号的手机号+验证码 × 两个环境）。`online_regression_accounts`：4 条、能多设备并发、**但不分环境、且只有编排层能用、不参与 `${}` 替换**。两套合不上 |

**直接后果——你的场景现在有两个跑不了：**

- **「线上回归跑上个版本老包」**：平台没有「包版本」这个实体。`resolvePreviousBuildKey` 只服务于升级测试，普通回归没有「跑老包」这一档。
- **「DEBUG 包通过后切生产环境、同一批用例再跑」**：`env_bound=1` 的 19 条流程会被候选过滤直接判不合格，得**逐条改 env_bound**；而且装包参数写死在流程里，换环境等于换成另一条流程、另一个包来源。

## 四、你最看重的生产巡检，两块能力不够

你说生产是重点、要断言要告警。这两块现在都是短板：

### 断言只有 3 个关键字

- `AssertText`：只有一个 `expected` 参数，判定固定是 `actual.contains(expected)`。**没有 equals / 正则 / 不等于**。
  > ⚠️ 这个 contains 语义是**真实的误判来源**：断言「余额 100」会在页面显示「余额 1000」时**通过**。生产巡检靠这个判「结果对不对」是不成立的。
- `AssertElementState`：断言 checked/enabled，而且**失败时会先点一下再判**，带自我纠正语义，更像操作不像断言。
- `AssertNoError`：给一批错误文案关键词，命中就失败。

没有数值比较、没有元素数量、没有跨步骤取值比对。**现在的生产巡检实际只能测到「App 没崩、页面上有这几个字」。**

### 告警只有一处，且在错的层

`PushPlusNotifyService` 全库只有一个调用方：`OnlineRegressionOrchestrator` 的**批次收尾**。

- `UiFlowExecutor` 里没有任何告警——单跑一条流程失败，不发。
- 失败归因（`FailureDiagnosisService`）的结论**不接告警**，只落库供页面查看。

> **所以生产巡检如果不以「线上回归批次」的形式发起，失败了没有人会知道。** 而巡检恰恰是 `catalog=AUTOMATION` 那 4 条，走的是另一条轨道。

## 五、「APP 测试任务」还要不要

**数据层必须留，功能模块该退役。**

`tasks` + `task_executions`（248 条执行记录）是唯一的执行历史，`online_regression_steps.task_id` 依赖它，失败归因也挂在它上面。删不得。

但作为一个「可以在这里新建测试」的菜单，没必要：

- 216 条 task 里 **212 条是 `UI_FLOW_TEST`**
- `TaskType` 12 个枚举值**只用到 3 个**；3 个已 `@Deprecated`，`STABILITY` / `INSTALL_UNINSTALL` / `UI_ADAPTATION` 是 **TODO 空实现**，`FUNCTIONAL_QUALITY_TEST` 直接抛「已下线」
- 它事实上就是「流程执行历史」，**叫「任务」让人以为能在这创建新类型的测试，而那些类型根本没实现**

**`test_plans` 是纯死代码，可以直接删**：0 条数据，只能调度 6 个硬编码场景（其中 4 个执行分支是 TODO），且完全接不到 `ui_flows`。

## 六、后端怎么调整

一句话：**把「用途」从资产上摘掉，变成执行时的参数。**

### 第一步：让「包」成为一等公民（优先级最高，是你三个场景的公共瓶颈）

```sql
CREATE TABLE app_builds (
    id VARCHAR(64) PRIMARY KEY,
    app_id VARCHAR(64) NOT NULL,          -- → ui_apps
    version_name VARCHAR(64),             -- 4.1.6
    build_type VARCHAR(16),               -- DEBUG / RELEASE
    is_released TINYINT(1) DEFAULT 0,     -- 是不是线上正式版
    source VARCHAR(16),                   -- PGYER / CHANNEL_URL / LOCAL_APK
    source_ref VARCHAR(500),              -- buildKey / url / path
    released_at DATETIME,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    KEY idx_app_builds (app_id, build_type, released_at)
);
```

- 执行请求加 `buildId`
- **装包从流程步骤里挪到执行前置**（批次级别，不是流程级别）
- 「跑上个版本老包」= 选一个历史 build；「DEBUG 包切生产」= **同一个 buildId 换 environment**

这一步做完，你那两个跑不了的场景立刻成立。

### 第二步：环境彻底参数化

- `ui_flows.environment` 从「候选过滤条件」降级成「默认值/建议值」，不再参与 `isBatchEligible`
- `env_bound` 这个补丁字段随之消失
- 设备绑定环境那条路要么启用（现在 devices.environment 全 NULL），要么删掉，别留着让人以为它在生效

### 第三步：`catalog` 退役

- 从「决定能在哪跑」降级成**视图标签**（列表页分组用）
- 执行入口收敛成一个，`track` 变成预设名而不是数据过滤器
- 顺带清掉那条谁也取不到的 `PERFORMANCE` 流程

### 第四步：告警提到执行层

一次执行结束——**不管从哪个入口发起**——都走同一条结果处理链：

```
判定 → 失败归因 → 按「预设」决定要不要告警
```

生产巡检预设默认开告警，人盯的场景默认关。顺带把归因结论带进告警内容（六分类：修元素 / 改编排 / 提单 / 重跑 / 观察 / 人工），值班的人扫一眼就知道要不要立刻处理。

### 第五步：补断言

- `AssertText` 加 `mode` 参数：`contains` / `equals` / `regex` / `notContains`。**这条最紧急**，现在的 contains 会放过真 bug
- 加数值比较（`AssertNumber`：>、<、区间）
- 加元素数量断言（列表条数）
- 跨步骤取值比对（把 `${}` 反过来用：某一步读到的值存成变量，后面断言）

### 第六步：把用例和流程的线接上

1/116 这个数字得改善。这不是代码问题，是录入问题——但可以在流程列表上显示「已挂 N 条用例」（现在有「覆盖用例」列了），在用例列表上显示「未挂流程」并给一键挂接入口。

### 顺带清理

- 删 `test_plans` 及其调度链路
- `TaskType` 里 `@Deprecated` 和 TODO 的枚举值删掉，别让前端还能选

## 七、前端怎么调整

现在三个并排菜单让人以为是三种不同的东西。建议改成 **「资产」和「执行」两类**：

### 资产类（管长期存在的东西，保留）

| 页面 | 职责 | 调整 |
|---|---|---|
| **流程编排** | 管步骤 | 不动。加「已挂 N 条用例」列 |
| **自动化用例** | 管用例 + 挂流程 | 重点补「未挂流程」筛选 + 一键挂接 |
| **元素库** | 管定位 | 不动。加健康报表入口 |
| **应用与包**（新） | 管 App + **包版本** | 新增，对应第一步的 `app_builds` |

### 执行类

| 页面 | 职责 | 调整 |
|---|---|---|
| **执行中心**（新） | 选流程集 + 环境 + 包 + 数据 + 设备 → 跑 | 新增，统一入口 |
| **执行历史** | 只读列表 + 详情 | **由「APP 测试任务」改名而来，去掉「新建任务」** |
| ~~线上回归~~ | | 保留为执行中心的一个**预设入口**（人心智里它是独立一件事，这没错，但底层收敛） |
| ~~测试计划~~ | | 删 |

**执行中心顶部放四个预设按钮**，对应你的四个场景：

```
[ 生产巡检 ]  [ 线上回归（老包）]  [ 版本准入（DEBUG）]  [ 准入后验证 ]
```

点一下，下面的表单自动填好环境/包/数据/告警开关，流程集还是你自己勾。**预设只是把参数组合存起来，不是新的功能模块。**

### 一个具体的前端小改（顺带）

自动化用例列表页的「失败」标签点不进去——`GET /ui-flows/last-runs` 返回的对象里**已经有 `lastRunTaskId`** 了，前端渲染 badge 时把它丢了。改成链接指向 `/tasks/{lastRunTaskId}` 即可。
