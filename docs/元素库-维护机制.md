# 元素库 · 维护机制

> 配套文档：`元素库-人机协同采集方案.md`（讲怎么**录入**），本文讲录进来之后**怎么不让它烂掉**。

---

## 一、先看清现状

2026-08-30 快照：

| | |
|---|---|
| 元素总数 | 1523 |
| **ACTIVE** | **162** |
| CANDIDATE | 1360 |
| 有页面归属 | 1501 / 1523 |
| ACTIVE 里有备选定位 | 102（**62%**） |
| ACTIVE 里有 `last_verified_at` | 15（**9%**） |
| ACTIVE 主定位是 xpath | 54（33%） |
| 来源 | HUMAN_AI 1429 / INSPECTOR_XML 77 / MANUAL 17 |

结论有两条，方向相反：

- **好的**：人工录入这条路走对了，页面归属基本齐全，ACTIVE 被克制在 162 个、62% 有备选定位。这是个健康的元素库。
- **空的**：`last_verified_at` 只有 9% 有值——**没有任何机制知道一个元素是不是还活着**。这就是「怎么定期维护」这个问题的真正答案所在。

---

## 二、第一原则：ACTIVE 越少越好

维护成本 = ACTIVE 元素数 × 改版频率。

1360 个 CANDIDATE **不需要维护**——它们是素材库，坏了不影响任何用例。所以 162 : 1360 这个比例是对的，**不要想着把它反过来**。

由此推出一条规矩：

> **`ACTIVE` 的定义是「有用例在用它」，不是「这个元素重要」。**

一个元素被提成 ACTIVE 的唯一理由，应该是某条用例现在就要引用它。没有用例用的 ACTIVE 元素，是在白白支付维护成本。

---

## 三、不要定期人工巡检

1500 个元素一个人一天也点不完，「每月排查一次元素库」这种计划提出来就不会被执行第二次。唯一可持续的做法是：**让元素在被使用时自证，人只处理系统报出来的那几个。**

三层机制，成本递增，前两层已实现。

### 第一层 · 被动自证（已实现，零成本）

流程每跑到一个元素：

- 用成了 → `last_verified_at = NOW()`，`fail_count` 清零
- 没用成 → `last_failed_at = NOW()`，`fail_count + 1`，`health_note` 记下是哪条流程哪一步失败的

实现在 `UiFlowExecutor` 的步骤循环里记账、执行结束的 `finally` 里一次性落库（`UiElementHealthService.flush`）。

三个刻意的设计：

1. **攒着不立即写。** 执行链路上每多一次 DB 往返都直接加在用例耗时上；同一个元素在一条流程里常被点很多次，逐次写等于把一次执行放大成几十条 UPDATE。
2. **断言类关键字失败不算元素的账。** 断言失败时元素多半是找到了，只是内容不符。记成「元素失效」会让报表里全是冤案，而**报表一旦不可信就没人看了**。
3. **不动 `status` 字段。** 把失效元素改成 `SUSPECT` 看着很自然，但流程执行是按 `status='ACTIVE'` 取元素的——一改，下次执行直接报「无 ACTIVE 元素」，一个本来只是「可能失效」的元素立刻变成确定跑不了的。**监控手段不能反过来弄坏被监控的东西。**「可疑」是一个查询（`fail_count >= 3`），不是一个状态。

### 第二层 · 搭车体检（已实现）

新关键字 **`CHECK_PAGE_ELEMENTS`（页面元素体检）**：dump 一次当前控件树，把本页所有 ACTIVE 元素的定位在树上求值一遍。

- 命中 **1** 个 → 健康
- 命中 **0** 个 → 定位已失效
- 命中 **多** 个 → 定位不唯一，早晚会点错，属于定时炸弹
- 含 `${变量}` 或随机下标 `[X:1-5]` 的定位 → 跳过（静态求值没有意义，别拿它吓唬人）

判定复用的是做 Inspector 双栏时写的 `LocatorMatcher.count()`。

**为什么做成关键字而不是独立巡检任务**：独立巡检任务得自己导航到每一页，也就是要另外维护一套「只为体检而存在」的流程——那套流程一样会腐烂，等于**用一个要维护的东西去维护另一个**。做成关键字就能搭车：已有用例本来就会走到那些页面，在那儿插一步，额外成本只有一次 dump。

**默认不打断流程**（`failOnMissing` 默认 false）。体检是搭车跑的，让它把一条本来正常的用例弄红，人就会把这一步删掉。结果写进健康数据，去报表里看。

参数：

| 参数 | 说明 |
|---|---|
| `pageId` | 只体检这一页；留空则体检该应用该平台下全部 ACTIVE 元素 |
| `failOnMissing` | 发现失效元素时是否让本步失败，默认 false |

**用法建议**：在每条线上回归流程的关键页面后面各插一步，不填 `pageId`（进哪页就体检哪页的元素，反正命中不了的会被跳过统计）。跑一轮回归下来，沿途页面的元素就全体检了一遍。

### 第三层 · 改版前置检查（未实现，等 diff 方案第三步）

客户端仓 diff 里动了某个页面的布局文件或资源 id → 把该页元素标「待复核」。需要先有「客户端目录路径 → 模块/页面」的映射，见 `平台体检与演进建议.md` 第 4.3 节第三步。

## 四、接口

### `GET /ui-elements/health`

| 参数 | 说明 |
|---|---|
| `appId` / `platform` | 可选，过滤 |
| `staleDays` | 多少天没被验证过算陈旧，默认 14 |

返回四张表 + 一个概览。**刻意不合成一个「健康分」**——分数看着好看，但拿到 78 分之后没人知道该干什么，而「这 6 个元素定位已失效」是能直接派活的。

| 表 | 回答的问题 | 该怎么处理 |
|---|---|---|
| `可疑` | 连续失败 ≥3 次的 | 优先修，多半真坏了 |
| `体检异常` | 体检命中 0 个或多个 | 命中 0 = 修定位；命中多个 = 加限定条件 |
| `久未验证` | 超过 N 天没被任何用例碰过 | 要么补用例，要么降回 CANDIDATE |
| `脆弱定位` | 主定位是 xpath，或没有备选 | 改版后优先复核这一批 |

概览给三个数：7 天内验证过的数量、有备选定位的数量、主定位是 xpath 的数量。

### `POST /ui-elements/health/probe`

```jsonc
{ "deviceId": "...", "appId": "...", "platform": "ANDROID", "pageId": "可选" }
```

对着一台真机的当前屏做体检：手动走到某一页，点一下就知道这页元素还活着几个。**这是给「临时想看一眼」和排查用的**，平时该靠第二层搭车跑。

### 新增字段（`ui_elements`，启动时幂等补列）

`last_failed_at`、`fail_count`、`health_note`、`last_probed_at`、`probe_match_count`。

## 五、录入侧只需要调两件事

不改「人工录入」这个原则——人工录入的价值不在「人工」，在于录入时被迫做的那次归类：这个元素属于哪一页、叫什么、干什么用。自动采集产出垃圾不是因为自动，是因为它跳过了归类，你会得到 1500 个 `btn_ok` 谁也不知道属于哪。

1. **录入时强制填第二个定位。** ACTIVE 现在 62%，事后补比录入时顺手填贵一个数量级。优先级：`accessibilityId` > `id` > `text` > `xpath`。
2. **CANDIDATE → ACTIVE 只在「某条用例要用它」时才提。**

---

## 六、顺序：按用例反向驱动，不要按页面正向铺

**不要按页面把剩下的录完，按用例把已录的用起来。**

1360 个候选够写很多用例了，而 `ui_flows` 只有 23 条。继续往下录只会让候选池更大、更陈旧，而陈旧的候选提上来时还得重新验一遍——等于白录。

具体做法：先定 20-30 条核心用例路径 → 走一遍这条路径，路上遇到的元素从候选里提成 ACTIVE（缺的现录）→ 这条用例就活了。每条用例提上来的元素天然是「有人用的」，天然带页面归属，也天然进入第一层的自证循环。

---

## 七、盯这三个数，别盯元素总数

| 指标 | 现在 | 目标 |
|---|---|---|
| ACTIVE 里 7 天内验证过的比例 | 9% | **> 90%** |
| `fail_count >= 3` 的数量 | — | **趋近 0** |
| ACTIVE 里有备选定位的比例 | 62% | **> 80%** |

元素总数不是指标。1523 涨到 3000 不说明任何事情，第一个数从 9% 涨到 90% 才说明这套东西真的在转。

> 顺带：iOS 只有 90 个元素（Android 1433）。如果 iOS 也要跑自动化，那是另一座山，得单独排期。
