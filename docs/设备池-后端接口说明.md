# 设备池：后端改了什么（前端对接说明）

> 目标形态：六台被测设备（真机 + 模拟器）挂在同一台常开机器上，自动化任务排队轮着跑；空闲时组里其他人能借来用。

---

## 一、数据模型的变化

### Device 多了三个字段

`GET /devices` 返回的每台设备现在多这三个：

```json
{
  "id": "emulator-5554",
  "name": "sdk_gphone64_arm64",
  "platform": "ANDROID",
  "version": "14",
  "status": "CONNECTED",
  "environment": "TEST",
  "workerId": "mac-mini-01",

  "isEmulator": true,
  "lastUsedAt": "2026-09-06T10:12:33",
  "disabled": false
}
```

| 字段 | 含义 | 注意 |
| --- | --- | --- |
| `isEmulator` | 是不是模拟器。扫描时读 `getprop` 定性，一次定死 | Java 字段名是 `emulator`，加了 `@JsonProperty("isEmulator")` 固定线上名。仓库里已有 `utils/deviceKind.ts` 兼容两种写法，直接用它 |
| `lastUsedAt` | 上次派活时间，轮转用 | 可能为 `null`（从没派过） |
| `disabled` | 人工停用（坏了/维护中） | 可能为 `null`，当 `false` 处理 |

**两列都是启动时自动建的，不用跑 SQL。**

`disabled` 和 `status=DISCONNECTED` 是两回事：离线是客观事实，停用是人的决定。界面上别混成一个状态。

### 任务多了一种状态：排队中

「排队中」不是新的 status，而是 **`status = PENDING` 且 `deviceId` 为空**。

| 情况 | status | deviceId |
| --- | --- | --- |
| 排队中，还没分到设备 | `PENDING` | `null` |
| 已分到设备、正要起跑 | `PENDING` | 有值 |
| 跑起来了 | `RUNNING` | 有值 |

前端判「排队中」必须两个条件一起看。只看 `PENDING` 会把第二种也算进去，「前面还有几个」就是错的——排队界面上这个数字错了比不显示更糟。

## 二、接口清单

### 1. 设备占用（借用相关）

#### `GET /devices/occupancy` — 全部设备的占用情况

一次拿完，别逐台调 `/{id}/lock`（六台就是六个请求，而这个列表要轮询）。

```json
{
  "occupancy": {
    "emulator-5554": {
      "kind": "MANUAL",
      "kindLabel": "人工借用",
      "label": "杨俊·调登录流程",
      "refId": "manual:yangjun",
      "since": "2026-09-06T10:12:33.123",
      "describe": "人工借用「杨俊·调登录流程」（自 10:12:33 起）",
      "mine": true
    },
    "PGT_AN00": {
      "kind": "TASK",
      "kindLabel": "测试任务",
      "label": "流程[测试环境]-登录冒烟",
      "refId": "task-uuid-xxx",
      "since": "2026-09-06T10:20:01.000",
      "describe": "测试任务「流程[测试环境]-登录冒烟」（自 10:20:01 起）",
      "mine": false
    }
  },
  "maxHoldMinutes": 120
}
```

- **没出现在 `occupancy` 里的设备就是空闲**（不会给你一个 `kind: "IDLE"` 的条目）
- `kind`：`TASK` 跑任务 / `REGRESSION` 线上回归 / `INSPECT` 元素采集 / `MANUAL` 有人借走
- **`mine`** 由后端按登录身份算好，前端不用自己存 `refId`——存了刷新一下就丢，然后自己借的设备自己还不了
- `maxHoldMinutes` = 占用上限（当前 120）。超过会被当成「忘了还」自动回收，界面上可以拿它算倒计时

#### `POST /devices/{id}/reserve` — 借用

```jsonc
// 请求（body 可省）
{ "note": "调登录流程" }

// 200
{ "ok": true, "refId": "manual:yangjun", "message": "已借到「...」。期间不会有自动化任务派进来。最长 120 分钟后自动收回，还在用就点一下续借" }

// 409 —— 已经被别人占了（可能是人，也可能是正在跑的任务）
{ "message": "这台正被占用：测试任务「登录冒烟」（自 10:20:01 起）。等它结束，或换一台" }

// 400 —— 设备不存在
{ "message": "设备不存在: xxx" }
```

**409 是正常路径不是异常**，界面上按提示处理，别弹红色报错。

#### `POST /devices/{id}/release` — 归还

```json
{ "released": true, "message": "已归还，这台重新进入排班" }
```

`released: false` 表示这台不是你借的（或已经还过了）——**HTTP 仍是 200**，按 `released` 判断，别只看状态码。

别人占着的要强制释放，用已有的 `DELETE /devices/{id}/lock`。

#### `POST /devices/{id}/renew` — 续借

```json
{ "renewed": true, "message": "已续借" }
```

把占用起点重置到现在，避免到 120 分钟被自动收走。同样按 `renewed` 判断。

#### `POST /devices/{id}/disabled` — 停用 / 恢复

```jsonc
// 请求
{ "disabled": true }
// 200
{ "ok": true, "disabled": true, "message": "已停用，调度器不会再往这台派任务" }
```

#### `GET /devices/emulators` 等模拟器启停接口

模拟器的总览与启停单独一节，见文末**「附：模拟器的启动 / 关闭」**。

### 2. 排队

#### `GET /tasks/queue` — 当前排队情况

```json
{
  "total": 3,
  "items": [
    {
      "position": 1,
      "taskId": "xxx",
      "name": "流程[测试环境]-登录冒烟",
      "flowId": "flow-1",
      "platform": "ANDROID",
      "runTrack": "DEBUG",
      "createdAt": "2026-09-06T10:30:00",
      "waitedSeconds": 95
    }
  ]
}
```

已按先到先得排好，`position` 就是队里的名次。最多返回 50 条，`total` 是真实总数。

### 3. 执行流程时可以不选设备

`POST /ui-flows/{id}/execute` 的 `deviceId` **变成可选**：

```jsonc
// 指定设备（老行为，不变）
{ "deviceId": "PGT_AN00", "environment": "TEST", "track": "DEBUG" }

// 不传 deviceId ＝ 交给设备池排班
{ "environment": "TEST", "track": "DEBUG", "allowEmulator": true }
```

新增可选字段 `allowEmulator`：不填时按 **「试跑 + 测试环境才允许模拟器」**。生产环境下不管填什么都会被强制关掉。

响应多了 `queued`：

```jsonc
// 排班
{ "taskId": "xxx", "started": false, "queued": true,  "message": "已排队，等到有空闲设备就自动开跑" }
// 指定设备
{ "taskId": "xxx", "started": true,  "queued": false, "message": "已创建任务并开始执行" }
```

**排班的任务不会立刻起跑**，`started` 是 `false`。拿到 `taskId` 之后照常轮询任务状态即可，会经历 `PENDING（排队）→ PENDING（已分到设备）→ RUNNING → COMPLETED/FAILED`。

### 4. 顺带（上一轮加的，如果还没接）

`GET /ui-flows/last-runs?ids=a,b,c` 每条多了三个字段：

```json
{ "lastRunStatus": "...", "lastRunTaskId": "...", "lastRunAt": "...",
  "lastDebugStatus": "FAILED", "lastDebugTaskId": "...", "lastDebugAt": "..." }
```

前面三个是正式执行（**排除试跑**，用来算质量结论），后面三个只有试跑。故意分开的：合成一个的话，「这条流程的质量结论」和「我刚跑的那次怎么样了」必然答错一个。

## 三、调度规则（界面上要能向人解释）

任务排到队里之后，后台每 3 秒扫一轮，按下面的顺序过滤，挑**最久没派过活的**那台：

| 顺序 | 条件 | 挑不到时的提示（接口不返回，但同样的逻辑写在任务失败原因里） |
| --- | --- | --- |
| 1 | 在线且未停用 | 「共 6 台，全都离线或已停用」 |
| 2 | 平台匹配 | 「共 5 台在线，没有一台是 IOS」 |
| 3 | 模拟器是否允许 | 「在线的 3 台全是模拟器，而这次执行不允许用模拟器」 |
| 4 | 环境匹配 | 「有 4 台可用，但没有一台绑的是「测试环境」…」 |
| 5 | 未被占用 | 「符合条件的 4 台都在忙，先排队等」 |

几条前端需要知道的语义：

- **轮转是 LRU**（谁闲得最久谁上），不是转指针。`lastUsedAt` 为空的设备优先——新接进来的设备会先被用上。
- **设备的 `environment` 留空 = 两边都能跑**；绑了就必须一致。界面上「执行时再定」这个选项要让人明白它等于「通配」。
- **模拟器默认只接试跑 + 测试环境**。
- **排队超过 30 分钟仍派不出去，任务判失败**，原因写在执行记录里（`GET /functional-test/tasks/{id}/execution-log` 能看到一条「设备排班」的失败步骤）。

### 会以「任务失败」形式出现的两条硬拦截

这两条不是 HTTP 错误，是任务跑到一半（其实是刚开始）失败，原因在执行记录里：

- 模拟器 + 生产环境 → 「…是模拟器，不能跑生产环境的流程」
- 模拟器 + 性能测试 → 「…是模拟器，性能测试不能在模拟器上跑」

界面上如果能在**选设备的时候**就提示，比等失败了再看好得多。

## 四、权限

`/devices` 整个前缀要求 **TESTER** 及以上（`PermissionRules`）。所以：

- VIEWER 看得到设备列表，但**借用 / 归还 / 停用都会被拦**
- 前端应该按当前用户角色隐藏或置灰这些按钮，而不是让人点了才收到 403

## 七、前端设计时值得注意的几个点

1. **占用状态变化很快**，必须轮询（我用的 10 秒）。看着两分钟前的快照去点借用，只会得到 409。
2. **`GET /devices` 不带占用信息**，两个接口要合着用。可以考虑在 store 里合并成一份视图模型。
3. **排队中的任务没有 deviceId**，任务列表的「设备」列会是空的——要专门显示成「排队中」，否则看起来像数据缺失。
4. **借用是「人」的维度**，不是标签页：同一个人在另一台电脑上登录，照样能看到 `mine: true` 并归还。
5. **别在前端预判「有没有空闲设备」**再决定能不能提交。判断完到真正开跑之间设备状态早变了，判了反而误导——直接提交、进队列，让后端告诉你结果。

## 附：模拟器的启动 / 关闭

### 先说设计取舍：「用完就销毁」只对了一半

你说的流程是 **启动 → 池子显示 → 用 → 销毁**。对**人手动调试**来说这是对的；但对**自动化排队**来说，这个流程会跟设备池打架：

- 冷启动一台 AVD 要 **30~60 秒**。设备池的价值就是「随时有可用的」，用完就关意味着下一个任务每次都要先等一分钟开机。
- 更要命的是：**自动化是无人值守的**。半夜跑的巡检、排队等设备的任务，没有人会去点「启动模拟器」。如果模拟器默认是关的，调度器根本看不见它，任务只能一路排到 30 分钟超时。

而「用完就关」真正想解决的问题其实是**状态脏**——上次的登录态、没关的弹窗，会让同一条用例时过时不过。这个问题有更快也更准的解法：

| 手段 | 耗时 | 干净程度 |
| --- | --- | --- |
| `adb shell pm clear <包名>` | 1~2 秒 | 只清这个 APP，最常用 |
| 启动时 `-wipe-data` | 一次开机 | 整台恢复出厂 |
| 关机再开机 | 30~60 秒 | **并不比上面两个更干净**（快照关掉后本来就不带状态） |

所以推荐的用法是：

- **模拟器常驻**，当设备池的固定成员，跟真机一样参与轮转
- **要干净环境**就清数据，不要关机
- **启停入口给人用**：机器要腾内存了、某台卡死了、临时加一台，这些场景才需要手动关/开

接口两样都给了，怎么用你定。下面是接口。

### `GET /devices/emulators` — 模拟器总览（已扩展）

```json
{
  "emulatorCliAvailable": true,
  "runningCount": 2,
  "maxRunning": 4,
  "avds": [
    {
      "name": "Pixel_7_API_34",
      "state": "READY",
      "deviceId": "emulator-5554",
      "startedAt": "2026-09-06T11:02:10",
      "elapsedSeconds": null,
      "message": null,
      "busy": true,
      "occupiedBy": "人工借用「杨俊」（自 11:20:03 起）"
    },
    {
      "name": "Pixel_5_API_33",
      "state": "BOOTING",
      "deviceId": null,
      "elapsedSeconds": 23,
      "message": "正在开机，通常 30~60 秒",
      "busy": false
    },
    {
      "name": "Tablet_API_34",
      "state": "FAILED",
      "message": "模拟器进程已退出：ERROR: x86_64 emulation currently requires hardware acceleration!",
      "busy": false
    },
    { "name": "Old_API_28", "state": "NOT_RUNNING", "busy": false }
  ],
  "runningUnmatched": ["127.0.0.1:5555"],
  "hint": null
}
```

**四种状态就是前端要画的整个生命周期：**

| state | 含义 | 界面上给什么按钮 |
| --- | --- | --- |
| `NOT_RUNNING` | 没在跑 | 「启动」 |
| `BOOTING` | 进程起了，还没开完机 | 转圈 + `elapsedSeconds` 秒数；可给「中止」（调 stop） |
| `READY` | 开完机、adb 认了，设备池里能看到 | 「关闭」；`busy=true` 时置灰 |
| `FAILED` | 起失败 | 「重试」+ 把 `message` 显示出来 |

每条还可以带 `platform`（`ANDROID` / `IOS` / `HARMONYOS`）和 `version`。鸿蒙走 DevEco 的 `Emulator -list` / `-start` / `-stop`，起来之后 hdc 序列号一般是 `127.0.0.1:端口`。

几个要点：

- **状态的权威来源是 adb / simctl / hdc**，不是「平台记得自己起过谁」。所以后端重启之后，之前起的模拟器仍然显示 `READY` —— 不会出现「平台以为没起、点启动又说已在运行」这种死结。
- `busy` / `occupiedBy` 来自设备占用锁（跑任务和被人借走都算）。**`busy=true` 时关闭按钮必须置灰**，后端也会拒绝。
- `runningUnmatched` 是在跑但问不出 AVD 名的（雷电、夜神这类不认 `adb emu avd name`）。它们照样能跑用例，只是平台管不了它们的启停。
- `maxRunning` 是同时最多起几台（默认 4，`app.emulator.max-running`）。这不是保守：一台 AVD 常占 2~4GB 内存，起超了不会有明确报错，表现是整机变慢、模拟器陆续卡死、用例大面积超时。**建议界面上把 `runningCount / maxRunning` 显示出来**，到上限时把「启动」置灰。

### `POST /devices/emulators/{avd}/start` — 启动

```jsonc
// 请求（可省）
{ "wipeData": false }

// 202 —— 注意是 202 不是 200
{ "ok": true, "state": "BOOTING", "message": "已开始启动，通常 30~60 秒。开完机会自己出现在设备池里" }

// 400
{ "ok": false, "state": "NOT_RUNNING", "message": "已经起了 4 台，到上限 4 了。先关一台再起" }
```

**立刻返回，不等开机。** 冷启动 30~60 秒，同步等的话这个请求必然超时，而超时之后模拟器其实还在起 —— 人会以为失败了再点一次，然后撞上「AVD 已在运行」。前端拿到 202 之后轮询总览接口看状态即可。

`wipeData: true` = 这次开机顺带恢复出厂，用于「状态脏了要个干净环境」。

已经在跑或正在开机时返回 `ok: true` + 当前状态（幂等），不报错。

### `POST /devices/emulators/{avd}/stop` — 关闭

```jsonc
// 200
{ "ok": true, "state": "NOT_RUNNING", "message": "已关闭。设备池里最多再过一轮扫描（约 5 秒）就看不到它了" }

// 409 —— 正被占用
{ "ok": false, "state": "READY", "message": "这台正被占用：测试任务「登录冒烟」（自 11:20 起）。等它结束，或者先归还再关" }
```

用的是 `adb emu kill` 让模拟器自己走关机流程，不是杀进程 —— 直接 kill 有一定概率把镜像写坏，下次启动报 `snapshot is corrupted`。

`BOOTING` 状态下调 stop = 中止启动。

### 启动参数（后端固定加的）

| 参数 | 为什么 |
| --- | --- |
| `-no-snapshot-load` | 每次干净启动。快照能省几十秒，但「上次残留的登录态、没关的弹窗」会让同一条用例时过时不过，这种偶现比多等半分钟贵得多 |
| `-no-audio` | 主控机上没人听，省资源 |
| `-no-window` | 只在 `app.emulator.headless=true` 时加。默认关着——个别机型无窗口下不稳 |

### 一个前端容易踩的坑

**启动后不要立刻去设备池找它。** 时间线是：

```
点启动 → BOOTING（30~60s）→ 模拟器连上 adb → 设备扫描（每 5 秒一轮）→ 设备池里出现
```

也就是 `state` 变成 `READY` 之后，设备池列表还要**最多再等 5 秒**才会有它。界面上要么把这两处数据合起来展示，要么在 READY 之后给一句「马上就会出现在设备池里」，否则人会以为哪里出问题了。

### 排队时自动拉起模拟器（已做）

这是让「六台轮着跑」在**无人值守**时也成立的最后一环：半夜排队的任务不会再一路排到超时，因为不需要有人去点「启动」。

**触发条件**（要同时满足，缺一不做）：

1. 队列里有任务，且这个任务**允许用模拟器**（也就是试跑 + 测试环境）
2. 用现有的池子挑不到设备
3. 这个任务已经**等了 30 秒以上**
4. 当前没有任何 AVD 正在开机
5. 没到 `maxRunning` 上限
6. 要起的那台不在失败冷却里

第 3 和第 4 条是重点，都是在防同一件事：**起太多**。

- **等 30 秒**：真机上那条用例可能十几秒就跑完了，而模拟器开机要一分钟。不等就起，等模拟器起来任务早被真机接走了，白占一份内存。
- **一次只起一台**：队列里堆十个任务时，没有这条就是十台模拟器一起开机 —— 主控机内存吃光、整机卡死，连带把正在跑的真机用例也拖挂。自动扩容最容易出的事故不是起不来，是起太多。

起失败的 AVD 进 **10 分钟冷却**，不反复撞同一堵墙。

**自动回收**：平台自己起的那些，闲够 `idle-reclaim-minutes`（默认 30 分钟）就自动关掉。判断依据是设备的 `last_used_at`；从没派过活的用启动时间当基准，否则一台起来就没人用的模拟器永远不会被回收。

两条约束：

- **只关自己起的**。人手动起的不碰 —— 那是别人有意留着的，平台没有资格替他决定什么时候不用了
- **队列里还有等模拟器的任务时不回收**，否则就是自己拆自己的台

**配置项**：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `app.emulator.auto-start.enabled` | `true` | 总开关 |
| `app.emulator.auto-start.min-queue-wait-seconds` | `30` | 任务等多久才考虑为它起 |
| `app.emulator.auto-start.idle-reclaim-minutes` | `30` | 闲多久自动关；**0 = 不自动关** |
| `app.emulator.auto-start.interval-ms` | `15000` | 检查间隔 |
| `app.emulator.max-running` | `4` | 同时最多几台（手动 + 自动共用这个上限） |

白天连续有人用的话，可以把 `idle-reclaim-minutes` 设成 0 —— 反复开关机比留着更浪费。

**前端要不要做什么**：不用。这块完全在后端自动跑。但界面上有两处值得体现，人才知道发生了什么：

- 模拟器总览里，自动起来的那台会正常经历 `BOOTING → READY`，跟手动起的看起来一样 —— 如果想区分，目前接口没给标记，要的话我加个 `autoStarted` 字段
- 排队列表里的任务，等超过 30 秒后可能会「凭空」多出一台设备来接它。给一句「没有空闲设备时会自动启动模拟器」的说明，能省掉不少疑问
