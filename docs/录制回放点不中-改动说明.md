# 录制出来的流程回放点不中：原因和改动

> 现象：`卡在第 8 步 · 点击`，
> 定位 `xpath://android.widget.LinearLayout[@bounds='[0,1386][1080,1941]']`，
> 现场一个节点都没命中。

## 一、先说清楚：这是我上一版改出来的

上一版我把「录制时挑哪个定位」改成了**优先选唯一命中（`matchCount == 1`）的候选**。当时的理由是「命中多个会点错对象」——这条本身没错，错在拿它当了唯一标准。

`@bounds` 的 xpath 精确到像素方框，**必然只命中一个节点**。于是「优先选唯一的」这条规则会稳定地把全场最差的定位挑出来。我当时确实在代码里排除了 `locatorType == "coordinate"`，但 bounds 是以 `xpath` 的身份混进来的，从后门绕过去了。

**结论：唯一性只能在同一档定位里比较，不能跨档。**一个命中 3 个节点的 id，也好过一个唯一命中的像素方框。

还有一层，让这个 bug 特别难发现：**录制时的点击本来就走坐标**（`clickAt` 里 Android 一律 `adb tap`），所以录的当场每一步都正常，定位烂不烂完全看不出来——要等到回放才炸，而那时页面早翻过去了。

---

## 二、改了什么

### 1. 定位按「质量档」排序，唯一性只在同档内比

新增 `FlowRecorder.locatorTier(type, value)`：

| 档 | 定位 |
| --- | --- |
| 1 | `id` / resource-id |
| 2 | `accessibilityId` / content-desc |
| 3 | 带 `@resource-id` 或 `@content-desc` 的 xpath |
| 4 | `text`、带 `@text` 的 xpath |
| 5 | 其它有条件的 xpath |
| 6 | 带下标的 xpath（`//Button[2]`） |
| 7 | 裸 `className` |
| **90** | **坐标、含 `@bounds` 的 xpath、`/hierarchy/...[1]/...[2]` 绝对路径** |

打分：`档 × 100 + (命中多个 ? 40 : 0) + 推荐序`。
40 比推荐序的取值范围大 → 同档里唯一的排前面；但**再唯一也翻不过一整档**。

**第 90 档直接不参与比较**。它不是元素定位，让它以「元素」的身份进库只会骗人。

### 2. 挑不到就退回明写的坐标点击 —— 并且这次它真的能跑

原来 `best == null` 的分支会记一步 `locatorType=coordinate`、**但不给 `elementKey`**，`finish()` 里也会跳过它不建元素。而 `CLICK` 是 `needsElement` 的关键字，于是这种步骤回放时直接倒在 **「缺少 elementKey」**上——录的时候看着好好的，一跑全是这个错。（之前那份说明里写「这一步能跑」，是我写错了。）

现在：坐标步骤照样建元素（`locatorType=coordinate`、`locatorValue="x,y"`），元素库和执行链路本来就支持这种定位（`coordinate:x,y` → `clickElementPreferCoordinates`）。它带着预览图进待审列表，人一眼能看出这一步是坐标兜底，决定重录还是留着。

### 3. 靠不住的步骤，**录制当场**就标出来

`Step` 加了两个字段，`tap` 和 `GET /ui-recordings/{id}` 都会返回：

```jsonc
{
  "fragile": true,
  "fragileReason": "点的位置上没有可用的元素定位（没有 id / 文案 / 描述），只能按坐标点。换分辨率或界面改版就会失效——建议改点里面带文字的子控件，重录这一步"
}
```

三种情况会置位：

- 挑不到定位，退回了坐标
- 定位命中多个节点（回放只点第 1 个）
- 只剩下标 xpath / 裸 className 这种第 6～7 档

**这是这次最值得做前端的一处**：以前只在 `finish` 的 `warnings` 里说，那时候一屏都翻过去几十步了，只能整条重录；现在下一步还没点就能看见，退回去换个带文字的子控件重点一次就行。

建议在步骤列表里给 `fragile` 的那一行加个显眼的黄底 + 感叹号，鼠标悬停出 `fragileReason`。

`finish` 的 `warnings` 也改成带步号的形式，收工页面照着列表逐条决定：

```
第 8 步「坐标点击(540,1663)」：点的位置上没有可用的元素定位……
第 12 步「最新」：这个定位在按下那一刻命中 3 个节点，回放时只会点第 1 个……
```

### 4. 录制生成的元素，`catalog` 从 `SHARED` 改成 `AUTOMATION`

跟上次改流程的理由一样：`SHARED` 是「两条轨道都收」（见 `RunTrack.catalogs`），一批未审的候选元素不该默认出现在线上回归那一侧的选择列表里。

## 三、前端要动的地方

只有一处是必须的：

1. **步骤列表读 `step.fragile` / `step.fragileReason`，把不稳的那几步标出来**（`POST /tap` 的返回和 `GET /ui-recordings/{id}` 都有）
2. `finish` 的 `warnings` 现在带步号，可以直接按行列出来，不用再自己拼

接口路径、字段名一个没变，其余照旧。

## 四、这次验证到哪一步

- **全量 446 个源文件真实编译通过**（本机 Maven 仓库 + Lombok 注解处理），0 错误
- **新增 `FlowRecorderLocatorPickTest`（13 个用例）**，覆盖分档、跨档比较、同档比唯一性、只剩坐标时返回 null
- **确认这个测试真的能抓到这次的 bug**：把 `pickCandidate` 改回上一版的写法重跑，3 个用例立刻失败（其中就是「唯一的 bounds 顶掉命中多个的 id」那条）。测试不验证一遍它会不会失败，就只是一段自我感觉良好的代码
- **全量 1228 个单测**：1186 通过、20 跳过、12 失败——12 个全在 `InterfaceDocParserTest` / `InterfaceDocImportServiceTest` / 两个 AI 客户端测试里，缺 `/doc/app-8999.docx` 这个测试资源和网络，改动前后完全一致，与本次无关

**没验到的**：真连设备录一遍。这次改的是「挑哪个定位」，只有在真实控件树上才知道挑得对不对。建议在模拟器上找**一个明确有文字的按钮**和**一块纯容器区域**各点一次，看：

- 前者的 `locatorType` 应该是 `id` / `text`，`fragile=false`
- 后者应该是 `coordinate`，`fragile=true` 并带上原因

然后 `finish` 跑一遍回放。**如果还有步骤点不中，把那一步的 `locatorType` / `locatorValue` 发我**——现在每一步都记了定位，能直接看出是挑错了还是控件树本身就没东西可用。
