# 用模拟器调试 —— 平台侧要不要改，改了什么

## 先说结论：平台根本不用改就能认出模拟器

`DeviceManager.scanAndroidDevices()` 是直接解析 `adb devices -l` 的，序列号只要过 `^[a-zA-Z0-9._-]+$` 就收，**没有任何一处排除模拟器**。`emulator-5554` 完全满足。

所以：**起一个模拟器，5 秒后它就出现在设备列表里，可以直接选来跑流程、做元素点选。** 这件事今天就成立。

真正的变数不在平台，在两个地方 —— 一个是你们的 APP 能不能在模拟器上跑起来（这个得实测），另一个是模拟器混进设备池之后会踩的坑（这次改的就是它）。

## 这次改的：三道护栏

模拟器一旦进了设备池，它跟真机长得一模一样，而下面三件事的后果都是「安静地给出错误结果」，比直接报错难查得多。

### ① 新模拟器默认落在测试环境

这是最要紧的一条。现在的逻辑是：

```java
TestEnvironment.normalize(null) → PROD
```

设备的「环境」为空 = 按**生产**跑。也就是说一台刚起的模拟器，第一次跑流程就会去取生产账号变量、连生产接口。

改成：扫描发现的**新模拟器**，`environment` 自动置成 `TEST`。真机不动 —— 真机的环境是人按「这台装的是哪个包」配的，替他猜反而会配错。

> 顺带说一句：新插的**真机**同样是空环境、同样默认生产。这个更大的口子我没动，因为改了会影响你现在的用法。要不要一起改，你定。

### ② 模拟器不能跑生产环境的流程

拦在 `UiFlowExecutor` 解析出环境之后、开跑之前：

> 「Pixel_7_API_34」是模拟器，不能跑生产环境的流程（生产变量是真账号、真数据）。要么去设备页把这台的环境改成「测试」，要么换一台真机跑。

**拦的位置比拦本身重要。** 不拦的话，现象是流程跑到登录那步失败，人会顺着去查账号、查网络、查风控，最后才想起来这台是模拟器 —— 而真正的原因在第一步就定死了。

### ③ 模拟器不能跑性能测试

拦在 `TaskService.executeTestTask`，覆盖三类性能任务。帧率、冷启动耗时、内存，在模拟器上量到的是**宿主机**的数字。而报告会照常生成、每一栏都有值、看着一切正常 —— 这种「安静地给出一份一个结论都不能用的数据」比直接失败危险得多。

### 顺带：一眼看得出是模拟器

- 设备列表：平台列旁边多一个橙色描边的「模拟器」标签
- 流程执行的选设备列表：设备副标题里带「模拟器」—— 挑设备的那一刻是唯一还来得及改主意的时候

## 怎么定性「这台是模拟器」

不靠序列号前缀。`emulator-5554` 只覆盖本地 AVD，雷电、夜神、云真机都是以 `127.0.0.1:5555` 连进来的，前缀一样也判不出来。所以扫描时 dump 一次 `getprop`，按这几条认：

- `ro.kernel.qemu` / `ro.boot.qemu` = 1
- `ro.build.characteristics` 这一行里带 `emulator`
- `ro.hardware` 是 `goldfish` / `ranchu`（AOSP 模拟器）或 `vbox86` / `android_x86` / `ttvm`（雷电夜神这类）
- 兜底：序列号以 `emulator-` 开头

**判错的两个方向代价不对等，所以规则刻意做得保守：**

| 判错方向 | 后果 |
| --- | --- |
| 模拟器当成真机（漏判） | 有人在模拟器上跑了一次生产巡检，看结果就知道不对 |
| 真机当成模拟器（误判） | 那台手机跑不了生产流程，而报错说的是「模拟器不能跑生产」—— 人对着一台真手机看这句话，只会觉得平台坏了 |

所以只认明确标志，不在整份 getprop 里搜 `emulator`（真机上装个模拟器类 APP 就会中招），也不做模糊猜测。属性读不到时只认 `emulator-` 前缀。

定性结果按序列号缓存 —— 设备扫描每 5 秒跑一次，而属性不会变，问一次就够。

## 你的 APP 能不能在模拟器上跑 —— 这个得实测

脚本已经放好：`scripts/try_emulator.sh`

```bash
scripts/try_emulator.sh --list
scripts/try_emulator.sh --avd <你的AVD> --apk ~/Downloads/app-debug.apk --pkg com.pwrd.steam.esports
```

它会：起模拟器 → 等系统就绪 → **对比 APK 里的 native 架构和模拟器的 ABI** → 安装 → 拉起 → 等 10 秒看进程还在不在 → 闪退就把 logcat 里相关的几十行捞出来。

那个 ABI 对比是最值钱的一步：**装上了、点开闪退**这个现象，可能是架构不匹配、可能是缺 Google Play 服务、也可能是 APP 自己的模拟器检测，光看现象分不出来，但看 ABI 和日志能分出来。

几条经验：

- 你的 Mac 是 Apple 芯片，系统镜像一定选 **arm64-v8a**，不要 x86_64。arm64 镜像跑 arm64 的 APK 是原生执行，兼容性和性能都好得多 —— 这是模拟器方案在你这儿值得一试的主要原因
- 先拿 **DEBUG 包 + 测试环境**试，别拿生产包。生产包风控最严，而你要模拟器本来就是为了调试
- 真正过不去的坎往往不是安装，是**登录**。脚本代替不了，得你手点一次

## 建议的用法边界

| 场景 | 模拟器 |
| --- | --- |
| 元素点选采集、流程试跑、调关键字 | ✅ 最该用，收益也最大 |
| DEBUG 包功能回归（测试环境） | ✅ 能跑通就用 |
| 生产环境 UI 巡检 | ❌ 已拦。巡检要的就是真实线上表现 |
| 性能测试 | ❌ 已拦。量到的是宿主机 |
| 上线前的最终回归 | ❌ 别用。真机上才有的问题（厂商 ROM、权限弹窗、推送）恰恰是最该拦住的 |

## 涉及文件

后端：

- `entity/Device.java` — 新增 `emulator` 字段（列 `is_emulator`，JSON 名 `isEmulator`）
- `mapper/DeviceMapper.xml` — resultMap / insert / update（update 用 `COALESCE`，探测不出来时不清掉已知结论）
- `service/DeviceManager.java` — 扫描时定性 + 按序列号缓存；规则抽成可测的 `looksLikeEmulator(serial, props)`
- `service/DeviceService.java` — 自动建 `is_emulator` 列；新模拟器默认测试环境
- `service/UiFlowExecutor.java` — 模拟器 + 生产环境 → 开跑前拦下
- `service/TaskService.java` — 模拟器 + 性能任务 → 开跑前拦下

前端：

- `views/Devices.vue` — 「模拟器」标签
- `views/UiFlows.vue` — 选设备列表里标出模拟器

脚本：

- `scripts/try_emulator.sh` — 可行性验证

**不用跑 SQL**，`is_emulator` 列启动时自动建。

## 验证情况

- `looksLikeEmulator` 的 13 个用例全过，重点覆盖两个**误判真机**的陷阱：真机某个属性值里带 `emulator`、`characteristics` 那一行没有右括号 —— 两种情况都会让「整份 getprop 里搜 emulator」这种写法把真机判成模拟器
- 五个改动的后端文件全量 `javac`：相对补丁前基线，新增的错误符号只有 `JdbcTemplate`、`getEmulator/setEmulator/setEnvironment` 这几个（缺 jar + Lombok 生成的访问器），没有真问题
- `DeviceMapper.xml` XML 解析通过；`Devices.vue`、`UiFlows.vue` 过 `@vue/compiler-sfc`；`try_emulator.sh` 过 `bash -n`，ABI 提取逻辑用一个构造的 APK 实测过
- **没验到的**：真的连一台模拟器跑一遍。我这边够不到你的 adb，定性规则是拿构造的 getprop 输出测的
