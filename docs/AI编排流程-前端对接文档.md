# AI 编排流程 — 前端对接

> 人选好「应用 + 平台 + 涉及哪几个页面」，再用一句话说要干什么，
> 后端用**已有的关键字和已审过的元素**编出一条流程草稿，人去调。
>
> **省掉的是「二十步一个个拖出来、填参数、选元素」这件苦力活，不是省掉调试。**
> 所以产物一律是 **停用的草稿**，落完直接跳流程编排页。

---

## 一、入口放哪

**流程编排列表页，「新建流程」按钮旁边** 加一个「AI 编排」。

弹窗表单：

```
应用      [下拉]  必填
平台      [下拉]  必填   ANDROID / IOS / HARMONYOS
涉及页面  [多选，可拖动排序]  必填
          ↑ 拖动顺序＝流程走的页面路径，后端会按这个顺序告诉模型
要做什么  [多行文本]  必填
流程名称  [输入框]  可选，留空自动生成
                                  [生成草稿]
```

**「涉及页面」要能拖排序**，这是这个表单里唯一不常规的地方。顺序不是装饰——它告诉模型「先在首页、再到详情页」，模型据此判断第几步该有跳转动作。顺序乱了，编出来的流程也乱。

生成中要有 loading，**模型调用大概 10~40 秒**（校验没过会自动重试一次，那就是两倍时间）。别用短超时。

## 二、接口

### 2.1 拉页面列表（填「涉及页面」下拉用）

```
GET /ui-pages?appId={appId}&enabledOnly=true
```

返回 `UiPage[]`，下拉要用的字段：

| 字段 | 说明 |
| --- | --- |
| `pageId` | **提交时要传的就是这个**，不是 `id` |
| `nameZh` | 显示名 |
| `moduleTag` | 可以用来分组 |
| `elementCount` | 这页有多少元素，显示出来帮人判断选得对不对 |

> ⚠️ 下拉的 value 用 `pageId`，别用 `id`。传错了后端会报「这几个页面下没有可用的元素」。

### 2.2 生成草稿

```
POST /ui-flows/ai-compose
Content-Type: application/json
Authorization: Bearer <token>
```

**请求体**

```jsonc
{
  "appId": "DOMESTIC_ESPORTS",       // 必填
  "platform": "ANDROID",             // 必填
  "pageIds": ["page_home", "page_video_detail"],  // 必填，按流程顺序
  "intent": "从首页点进一个视频，发一条评论，验证评论出现在列表第一条",  // 必填
  "flowName": "视频评论",             // 可选
  "knownVars": ["tab_name"]          // 可选，见下
}
```

**`knownVars`**：已经有值的变量名。有些元素的定位里带 `${xxx}`（比如底部导航做成变量的那些），后端会检查这些变量有没有值，没有就在 `notes` 里提示。前端可以把当前环境变量的 key 列表传进来；不传也不影响生成。

**200 成功**

```jsonc
{
  "flowId": "uif-xxxx",
  "flowName": "视频评论",
  "steps": 11,
  "notes": [
    "第 3 步之后补了一步「等待元素 comment_input」——动作后面不等就是在跟渲染赛跑",
    "这些变量没给值，执行前要在环境变量或执行参数里补上：tab_name"
  ],
  "message": "已生成流程草稿（停用中），去流程编排里调通再启用"
}
```

拿到之后：**跳 `/ui-flows/{flowId}`**，并把 `notes` 显示出来（`ElMessageBox` 列成 `<ul>` 就行）。

**`notes` 一定要展示。** 它是「平台替你改了什么 / 你还差什么」，不展示的话人不知道流程里凭空多了几步等待，调试时会困惑。

## 三、错误处理

| 状态码 | 含义 | 前端怎么做 |
| --- | --- | --- |
| `400` | 参数缺失（appId / intent 空） | 表单校验拦住，正常不该走到 |
| `422` | **生成失败**，见下 | **把 `message` 完整显示出来**，别截断 |
| `500` | 模型调用异常、网络问题 | 提示重试 |

`422` 有三种，`message` 里写清楚了：

**① 模型没配**
```
没有配置可用的模型，AI 编排用不了
```

**② 页面选错了 / 元素没审**
```
这几个页面下没有可用的元素（只取 ACTIVE 的）。先去元素管理确认页面归属和状态
```
> 后端**只取 `status=ACTIVE` 的元素**。CANDIDATE 是还没审的，拿它编流程等于把未审内容洗成正式用例。

**③ AI 编的没通过校验（重试一次仍不行）**
```
AI 编出来的流程没通过校验，已重试一次仍不行：
- 第 4 步用了不存在的关键字：TAP_ELEMENT
- 第 7 步引用了元素库里没有的元素：btn_share
多半是描述太笼统，或这几个页面里缺少需要的元素
```

**这一种最有价值，务必原样展示（保留换行）。** 它直接告诉人该怎么改描述或补元素。

> 后端**不返回半成品**：校验没过就不落库。一份自己都验不过的草稿交给人，人得逐条当校验器用，比自己编还慢。

## 四、后端做了哪些校验（前端不用重复做）

**打回重出（人看不到这些草稿）**

- 关键字不存在
- 元素不在库里
- `needsElement` 的关键字没给元素
- 缺必填参数
- 用了勾选范围之外页面的元素
- **断言的是上一步刚点过的那个元素** ← 点击成功本身就说明它在，这种断言什么都验不到

**自动补 / 只提示（进 `notes`）**

- 动作后面没等待 → 自动插一步 `WAIT_ELEMENT`（等的是**下一步要用的元素**）
- 定位里的 `${var}` 没给值 → 提示
- 多余参数 → 提示

## 五、TypeScript 类型

```ts
export interface AiComposeRequest {
  appId: string
  platform: string
  /** 按流程走的顺序，值是 UiPage.pageId */
  pageIds: string[]
  intent: string
  flowName?: string
  knownVars?: string[]
}

export interface AiComposeResponse {
  flowId: string
  flowName: string
  steps: number
  /** 平台替它改了什么 / 还差什么，一定要展示 */
  notes: string[]
  message: string
}

// api/index.ts
async composeUiFlowByAi(body: AiComposeRequest) {
  return this.request<AiComposeResponse>('/ui-flows/ai-compose', {
    method: 'POST',
    body: JSON.stringify(body),
  })
}
```

## 六、几个容易踩的点

1. **`pageIds` 传 `pageId` 不是 `id`** —— 最常见的接错
2. **顺序有意义** —— 多选组件要支持拖动排序，不能用普通 `el-select` 的多选（它不保序）
3. **超时要放宽** —— 模型 10~40 秒，重试翻倍。至少给 120 秒
4. **草稿是停用的** —— 流程列表如果默认「只看启用」，跳过去会看不到。跳转时要么带上筛选重置，要么直接进详情页
5. **`notes` 别吞掉** —— 它是这个功能可解释性的全部
