## 一、`ASSERT_TEXT` 加判定方式

### 原来的问题

判定固定是 `actual.contains(expected)`，**它不是不够用，是会放过真 bug**：

```
断言「余额 100」，页面显示「余额 1000」→ 通过 ✅
```

金额、数量、比分、倒计时全中招。而且失败是**静默的**——用例是绿的，缺陷溜过去了。
生产巡检靠这种断言判「结果对不对」不成立。

### 现在

`ASSERT_TEXT` 新增 `mode` 参数：

| mode | 判定 | 什么时候用 |
|---|---|---|
| `contains`（默认） | 实际包含期望 | 页面上有没有这段话 |
| `equals` | 两边 trim 后完全相等 | **金额、数量、比分、状态文案** |
| `regex` | 期望值当正则，对实际做 find | 「余额 \d+ 元」这类结构校验 |
| `notContains` | 实际不含期望 | 断言页面上没有某段错误提示 |

几个刻意的行为：

- **默认仍是 `contains`，存量流程一个字不用改。** 升级不会让一批本来绿的用例集体变红——那种红跟产品毫无关系，只会让人不信任这次升级。
- **`equals` 两边都 trim。** 控件文案常带首尾空白和换行，不 trim 的话 equals 几乎永远失败，人就会退回去用 contains，等于白加。但**中间的空白是内容的一部分，不吞**。
- **正则写错单独报错**，不混成「断言失败」。这两件事的处理方式完全不同：一个要改用例，一个可能是缺陷。混在一起会让人拿着「断言失败」去查产品，查半天发现是自己正则打错了。
- **读不到文案时**：除了 `notContains` 之外一律判失败。`notContains` 通过是刻意的——元素上没有文案，自然也就不含那段错误提示。
- 认不出的 mode 写法退回 `contains`，不让流程直接跑不了。

判定逻辑抽在 `util/TextAssertion.java`，脱离 Spring 和真机可直接测（`TextAssertionTest`，11 个用例）。**判定逻辑错了的后果是「所有用例都在骗你」，这是最不该只靠肉眼 review 的一段代码。**

### 前端要改的

关键字参数表单会自动多出一个下拉（后端 `params()` 已声明 `enumOf`），**前端零改动即可用**。建议加一句提示：

> 金额、数量、比分这类务必选 equals

## 二、告警从编排层提到执行层

### 原来的问题

`PushPlusNotifyService` 全库**只有一个调用方**：`OnlineRegressionOrchestrator` 的批次收尾。

也就是说——**只有以「线上回归批次」形式发起的执行失败了才有人知道**。而生产巡检走的是单条流程执行那条路（`POST /ui-flows/{id}/execute`），跑挂了没有任何人会收到消息。

**一个没人知道结果的巡检，等于没跑。**

### 现在

新增 `ExecutionAlertService`，挂在 `TaskService` 执行收尾处（和失败归因同一个位置）。不管从哪个入口发起，一次执行结束都走同一条判定。

三条刻意的规则：

1. **编排驱动的任务不单独发。** 用 `parentRefId` 区分（和归因的自动重跑判断同一个依据）。否则一批 20 条流程失败会推 20 条消息，而批次收尾那条摘要才是人真正想看的——收到 20 条的结果是把通知静音。
2. **默认只有生产环境失败才发。** 测试环境是你自己盯着在跑，不需要打扰。可按流程显式覆盖（见下）。
3. **同一条流程 30 分钟冷却。** 元素一失效，同一条流程会连续失败，不设冷却就是一晚上几十条同样的消息。

### 消息里有什么

```
标题：自动化失败 · PROD · 发现页底部登录

流程：发现页底部登录
环境：PROD
设备：xxxx
时间：2026-09-05 03:12:44

失败原因：
点击失败: discover_login_btn (method=AUTO, tried=2)

归因：元素定位失效（改用例，不是产品问题）（置信度 86%）
失败步骤：3. 点击登录
涉及元素：discover_login_btn

详情：http://.../#/tasks/task-xxx
```

**归因分类被翻译成了一句「该谁去做什么」**，值班的人扫一眼就知道要不要立刻处理：

| 分类 | 消息里显示 |
|---|---|
| ELEMENT_BROKEN | 元素定位失效（改用例，不是产品问题） |
| FLOW_OUTDATED | 流程与现状不符（改编排） |
| FUNCTION_BROKEN | **功能确实坏了（需要提单）** |
| ENVIRONMENT | 环境问题（已安排重跑） |
| FLAKY | 偶发抖动（先观察） |
| 其它 | 需人工确认 |

> 归因是异步跑的，告警会**等它最多 60 秒**再发，好把结论带上。
> 归因整个没开（`diagnosis.ai.enabled=false`）时不白等，立刻发——只是消息里没有归因那一段。

### 配置

```yaml
app:
  execution-alert:
    enabled: true
    environments: PROD        # 逗号分隔；想全都告警填 PROD,TEST
    cooldown-minutes: 30
    detail-url-template: "http://localhost:5173/#/tasks/{taskId}"
```

**推送通道本身仍用 `app.online-regression.alert.pushplus-token`**（历史命名，这次不动它，免得你现有配置失效）。也就是说：

- `online-regression.alert.enabled` = 推送通道总开关（现在是 `false`，**要发告警得先打开它**）
- `execution-alert.*` = 什么情况下该发

### 按流程覆盖默认策略

任务 config 里写 `notifyOnFailure`，压过环境默认值：

```jsonc
{ "flowId": "...", "environment": "TEST", "notifyOnFailure": true }   // 测试环境也要告警
{ "flowId": "...", "environment": "PROD", "notifyOnFailure": false }  // 生产但不想被打扰
```

### 整条链路对主流程只读且静默

告警发不出去、归因等超时、PushPlus 挂了——只记日志，**绝不影响任务本身的状态**。告警跑在自己的线程池里，不占执行线程。

## 四、你验证的时候可以这样试

**断言**：找一条有数字文案的流程，把 `ASSERT_TEXT` 的 mode 改成 `equals`，故意把期望值写成实际值的前缀（比如实际「1000」写成「100」），看是不是正确判失败——旧行为下这里会误判通过。

**告警**：
1. 先把 `app.online-regression.alert.enabled` 改成 `true`（推送通道总开关）
2. 确认 `app.execution-alert.environments` 含 `PROD`
3. 单跑一条生产环境的流程，让它失败
4. 应该在 1 分钟内收到微信推送；日志里搜 `[alert] 执行失败告警` 能看到发送结果
5. 再跑一次同一条流程，应该**不再发**（冷却期），日志里是 `[alert] 同一流程在冷却期内`
