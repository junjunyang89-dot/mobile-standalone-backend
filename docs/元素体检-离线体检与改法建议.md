# 元素体检：补上缺的三块 + 一个真实的 NPE

> 先说结论：**`UiElementHealthService` 已经存在,而且第一、二层做得挺完整。**
> 所以这次不是重做,是补它缺的三块。

---

## 一、已经有的（我没动）

| 层 | 怎么触发 | 成本 |
| --- | --- | --- |
| **被动自证** | 流程跑到哪个元素,那个元素就记一次 `last_verified_at`;失败累加 `fail_count` | 零,是跑用例的副产品 |
| **搭车体检** | `CHECK_PAGE_ELEMENTS` 关键字插进已有流程,dump 一次把本页元素全求值 | 低 |
| **报表** | `/ui-elements/health` 四张表(可疑 / 体检异常 / 久未验证 / 脆弱定位) | 人主动看 |

里面那句注释写得很对,值得再强调一次:**刻意不动 `status` 字段**——
把失效元素改成 SUSPECT,下次执行直接报「无 ACTIVE 元素」,
一个「可能失效」立刻变成确定跑不了的。**监控手段不能反过来弄坏被监控的东西。**

---

## 二、补的第一块:离线体检（`POST /ui-elements/health/probe-saved`）

**原料本来就在。** 每次执行失败都会在 `screenshots/{taskId}/pagesource-*.xml`
存一份当时的控件树。不需要设备在线、不用人走到那一页、不用挂关键字——
这是三层里唯一**完全被动**的一层。

### 它刻意不判「失效」——这是整个设计里最要紧的一条

一个元素在这些现场里一次都没出现,有两种可能:

1. 定位真的废了
2. **这些现场压根不是它该出现的页面**

而离线体检**分不出这两者**,因为它不知道每份 xml 是哪一页。所以它只报能证明的事:

| 报什么 | 证据 |
| --- | --- |
| **确认还活着** | 某个现场里命中恰好 1 个 —— 铁证 |
| **不唯一** | 命中多个 —— 回放只取第 1 个,「找到了、点了、没反应」的来源 |
| **没覆盖到** | 一次都没命中 → **不下结论** |

「失效」交给第一层:那里知道是哪个元素在哪一步挂的,`fail_count` 才是够格的证据。

**为什么这么克制**:误报一个「失效」的代价是人去改一条本来好好的定位。
而「不唯一」这一栏是净新增价值——**现在没有任何一层会发现它**,
它不报错、不失败,只是偶尔点错对象。

## 三、补的第二块:改法建议（`LocatorRepairSuggester`）

报了「不唯一」还得说改成什么,否则人还是得自己去翻控件树。

**这一步没用模型。** 控件树是结构化的,线索有三条(resource-id 尾段、原定位里写死的文案、
元素中文名),而「哪条定位更好」平台已经有唯一判据了。两头都硬,中间不需要猜。

典型场景——横排三个商城 Tab,resource-id 全一样:

```
当前: id = com.pw.esports:id/mall_category_tab   → 命中 3 个
建议: xpath //*[@resource-id='...' and @text='刀塔商城']  → 命中 1 个
      「id 在这一屏上不唯一,加文案收窄;同类控件建议把文案做成 ${变量}」
```

最后那半句是刻意的:**正解是一个元素配文案变量**,不是建三个元素。

### 这里我第一版写错了,值得记下来

我沿用了录制那边的排序规则——「唯一性绝不跨档比」。结果第一推荐是
**命中 3 个的裸 id**(第 1 档),而唯一命中的收窄 xpath(第 3 档)排在它后面。

按录制的规则这是对的:那里问的是「该用哪条定位记下来」,答案要偏耐久,
一个命中 3 个的 id 也好过一个唯一命中的像素方框。

但这里问的是**另一个问题**:我们正是因为不唯一才来修的。
推荐一条仍然不唯一的定位等于没修,而人改完会以为修过了。

所以这里**唯一性优先,质量档做次序**。为什么这样安全:
靠位置的候选在上游就被整档剔掉了,压根进不到排序——
像素方框那个陷阱是「唯一性把靠位置的顶上来」,这里没有可顶的。**闸门在上游,不在排序里。**

### 顺手统一了一处会漂移的东西

分档规则原来只长在 `FlowRecorder` 里。现在体检也要用,抽成了 `util/LocatorQuality`。

各写一份的话两份迟早漂移,而漂移的表现是:录制挑出来的定位,体检说它不好。
那时候人不知道该信哪个,**两边都会被当成不准**。「好定位」的定义只该有一处。

## 四、顺带发现的真实 bug（和体检无关,但更该先修）

```java
KeywordContext.firstNonBlank(ctx.str("landedElementKey"), "").trim()
```

`""` **本身就是 blank**,所以 `firstNonBlank` 会跳过它返回 `null`,接着 `.trim()` 就是 NPE。

而 `landedElementKey` 是**可选**参数——也就是说**不填它(最常见的用法)**,
`CLICK_EACH_OPEN_BACK` 这一步必然崩,还崩成一个光秃秃的 `NullPointerException`,
人完全看不出该填什么。

已修。全仓扫了一遍同类写法,只有这一处;`DeviceInspectService` 那处看着像但上游有过滤,是安全的。

**怎么发现的**:这条有现成的单测,而且一直是红的——
只是我这套验证环境的源码清单是旧的,**少了 53 个文件**,那个测试从来没被跑到。
这次把源码树整体同步了(504 个源文件 / 189 个测试文件),之前几份说明里
「451 个源文件编译通过」的说法,覆盖面是不全的。

## 五、验证

- **504 个源文件真实编译通过**(之前只覆盖 451),0 错误
- **新增 20 个单测**(`LocatorRepairSuggesterTest` 13 + `LocatorQualityTest` 7),全过
- **全量 1415 个单测**:1381 通过、20 跳过、12 失败——
  12 个全是缺 `/doc/app-8999.docx` 和需要网络的 AI 客户端,与本次无关
- NPE 那条的判据是**一个本来就红的测试变绿**,不是我自己新写的

### 反向验证（每条改动都退回去看测试会不会红）

| 退回什么 | 结果 |
| --- | --- |
| 排序换回「唯一性不跨档比」 | **2 条红** ✅ |
| 线索匹配改成模糊包含 | 第一次 **一条都没红** ❌ → 补了一条针对性测试,再退回 **1 条红** ✅ |
| 去掉「不推荐靠位置定位」那道闸 | **一条都没红** —— 见下 |

最后一条要说清楚:那道闸**目前的输入到不了**。
候选只从 id / content-desc / 文案 / 收窄 xpath 四种生成,没有一种会是靠位置的。
所以它是**给以后新增候选生成器留的防线,不是已经验证过的防线**。
我留着它(零成本),但不会说它被测到了。

## 六、前端要改吗

新接口一个:

```
POST /ui-elements/health/probe-saved?appId=&platform=&maxScenes=30
```

返回里的字段名刻意是「确认还活着 / 不唯一 / 没覆盖到」,不是「健康 / 异常 / 失效」——
**前端展示时请保留这个措辞**。把「没覆盖到」显示成「失效」,
就把这一层刻意不下的结论替它下了,而那个结论是错的。

`problems[].suggestions` 是改法候选,直接列出来,人点一下能填进元素编辑表单最好。

**后端要重启。** 不用跑 SQL(`ensureSchema` 已有的列不变)。
