# 第四批:磁盘炸弹 + 定时计划静默丢弃

> 这两条是同一类问题:**不报错、界面上看不出来、等到被发现时已经积累很久了**。

---

## 一、截图清理压根不递归

### 问题

```java
// ScreenshotRetentionService，原来的样子
try (Stream<Path> files = Files.list(dir)) {              // ← 不递归
    for (Path file : files.filter(Files::isRegularFile)   // ← 只要文件
```

而那行注释写着「扁平文件,不按任务分目录」——**写的时候是对的**。
后来性能测试开始往 `perf_<taskId>/` 写、兼容性测试往 `compatibility_<taskId>/` 写,
**假设过期了,代码却不会因此报错**。

结果:这些子目录里的图**一张都不清,只增不减**。
性能任务的截图间隔是 1 秒、遍历 2 分钟,单次约 120 张。
6 台设备 × 50 人的量级和单人调试完全不是一回事。

### 但修这个会引入一个新问题——我自己差点造出来

`perf_*` 里的图**不是临时图,是任务报告的证据**:它们的路径被写进了报告 JSON
(`screenshotTimeline`),报告页面正指着它们。

而 `/tmp/screenshots` 的保留期是 **2 天**(`retain-days-inspect`)。

所以"修好递归"这件事本身会把一个磁盘问题**换成一个数据丢失问题**:
> 人打开上周的性能报告看到一片破图,只会觉得"报告坏了",不会想到是清理干的。

递归之前这些子目录一张都不清(所以"报告能一直看到",代价是磁盘只增不减)——
**这个巧合一直在替我们兜着**。

### 改成什么样

**按用途区分保留期**:

| 位置 | 是什么 | 保留期 |
| --- | --- | --- |
| 顶层扁平文件 | 真机点选的临时图,看完就没用 | `retain-days-inspect`(2 天) |
| `perf_*` / `compatibility_*` 子目录 | **报告证据**,报告页正指着 | `retain-days-default`(7 天) |

### 判定逻辑做成了纯函数 `RetentionPlanner`

三条容易做错的规则,现在都被单测钉住:

**1. 目录不能按自己的 mtime 判断。** 这是最容易写错的一条。
目录的 mtime 只反映"最后一次增删子项",**不反映里面内容的新旧**。
按目录 mtime 删的话,一个看起来很旧的目录里可能躺着今天刚生成的截图。
所以:只有当一个目录里的东西**全部**都该删,这个目录才跟着删。

**2. 删除顺序自底向上。** 先删父目录会因为非空直接失败。

**3. 拿不到 mtime 就不删,并且计数。** 和"样本不足不下结论"同一个道理——
留一张多余的图,比删掉一张别人报告里正在引用的图便宜得多。
`keptUnknown` 持续不为 0 会打 warn,因为那说明文件系统有问题。

### 还没做的:`/tmp` 本身

`/tmp/screenshots` 硬编码在 **11 处**,其中包括静态资源 URL 映射
(`ScreenshotResourceConfig`)和鉴权白名单(`PermissionRules`)。

**挪目录是一次迁移,不是改一行**:改了目录就要改 URL 映射,
而库里所有历史 `reportPath` 都指着旧路径——挪完老报告全变破图。
所以我没动。

但你部署到 Mac Studio 时要知道:**`/tmp` 在 macOS 上重启会被清空**。
配了另一块硬盘的话,这个目录值得一起规划进去,当成一次独立的迁移做。

## 二、定时测试计划静默丢弃

### 问题

`TaskDispatcher.executeScenario` 把 deviceId **写死**,然后:

1. 设备被占 → `taskService.runTask` 抛 `IllegalStateException`
2. 异常被外层 `catch (Exception e) { log.error(...) }` **吞掉**
3. 而任务**已经建好了**:状态 PENDING、device_id 已写死

于是这个任务:

- **不在排队队列里** —— 队列条件是 `device_id IS NULL OR = ''`
- **没人重试**
- 界面上**不是失败也不是完成**,就是一条 PENDING 的孤儿

**6 台设备被 50 个人占满是常态**,所以这条路径几乎每次定时计划触发都会走到:
无人值守回归静默失效,而**通过率报表上看不出任何异常**。

### 改成什么样

设备被占时记成 **BLOCKED**,不留 PENDING 孤儿。

用 BLOCKED 而不是 FAILED 是有意的——`Task.TaskStatus.BLOCKED` 自己的注释解释了为什么:

> 不进通过率的分母。把它算成失败的话,模拟器卡一晚上,
> 早上看到的是「通过率 40%」,人会去查用例、查定位、查应用,
> 而那 60% 压根没跑到断言那一步。

现在人在任务列表里能看到「昨晚这条没跑成,原因是设备被占」,而不是什么都看不到。

设备未连接那条分支也补了日志——原先只有一行 `log.warn("设备未连接")`,
现在会说清是哪个计划、哪台设备、什么状态。

### 我没动的:写死 deviceId 这个设计本身

让任务进队列(deviceId 留空)、由调度器按平台挑设备,能从根上解决这个问题。
**但那会改变语义**:计划里指定了 N 台设备就是想在这 N 台上各跑一遍,
留空之后 N 个任务可能都跑在同一台闲着的机器上。

**这是产品取舍,不是 bug**,所以留给你定。
我的建议是给计划加一个"指定设备 / 由池子分配"的选项,默认后者——
6 台设备 50 个人的情况下,钉死设备基本注定排不上。

### Task 上没有存失败原因的字段

所以 BLOCKED 的原因只能拼进任务名(`[未跑成:设备被占]`)。不好看,
但比"状态是 BLOCKED,为什么不知道"有用——人一眼能看到,不用翻日志。

要做干净得给 `tasks` 加一列 `block_reason`,那是 DDL,单独安排。

## 三、验证

- **523 个源文件真实编译通过**,0 错误
- 全量 **1526 个单测**(本批新增 23):1491 通过、**13 失败**(那 13 条是原有问题)
- `RetentionPlanner` **23 个单测全过**

### 反向验证

| 退回什么 | 结果 |
| --- | --- |
| 拿不到 mtime 也删 | **2 条红** ✅ |
| 目录按自己的 mtime 判断(会删掉里面的新图) | **5 条红** ✅ |
| 目录不按深度倒序判定 | **2 条红** ✅ |
| 负数大小算进释放量 | **红** ✅ |
| 去掉输出排序 | **红** ✅(见下) |
| 子目录也用 2 天保留期(报告变破图) | **红** ✅ |

### 一次值得说的反复

「去掉输出排序」我试了**三版测试才抓到**:

1. 第一版断言"文件在目录之前" —— **没抓到**。查下来:文件先全部入集合、
   目录再按深度倒序追加,**顺序本来就是对的,那次排序在这个用例上是多余的**
2. 第二版断言"跑 20 次顺序一致" —— **也没抓到**。
   `HashSet<String>` 对同一组字符串的迭代顺序本来就稳定
3. 第三版断言"整个清单按路径深度递减" —— **抓到了**。
   这才是只有排序能保证的性质

中间我一度想直接删掉那次排序当死代码。但它有个真实作用:
**dry-run 的清单是给人看的,顺序不稳就没法和上次比"多删了什么"**。
所以留下了,并且把注释改成实话——写清第 1 条其实由构造顺序保证、
排序真正在守的是第 2 条。

> **一条测试如果在任何退化下都不红,它就不是在守东西。**
> 而一条注释如果说了代码没在做的事,比没有注释更容易误导下一个人。

### 顺手清掉的自己的垃圾

改的过程中我留下过一个死方法 `unusedLegacyCleanupInspectFiles`
和一段两个分支完全一样的 `if (dryRun) ... else ...`,都删了。
